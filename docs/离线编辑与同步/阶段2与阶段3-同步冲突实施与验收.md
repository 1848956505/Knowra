# 阶段 2 与阶段 3：笔记同步、冲突与删除

> 历史阶段记录：当前完整传输范围及验收结果以 [阶段 4/5](阶段4与阶段5-完整同步与发布验收.md) 为准。

> 日期：2026-09-10。已实现总方案的最小笔记双向链路与冲突、删除恢复处理。完整附件、目录、标签和标注写入同步仍属于阶段 4，容量及发布准入属于阶段 5。本轮未部署云端，也未生成 Mac 安装包。

## 1. 当前可用行为

- 两个独立本地资料库与网页可以同步笔记新建、正文、标题、已有目录和标签引用、收藏、状态、软删除及恢复。
- 本地先以 SQLite 事务保存。后台在启动、本地业务提交后、网络恢复、窗口重新激活、手动操作及定时检查时尝试同步；网络失败不影响本机保存。
- 请求发送前冻结操作 ID、基线、正文及本地修订。响应丢失或应用重启后复用原请求；发送期间的新编辑保留为后继修改。
- 云端使用实体修订检查；业务、不可变正文版本、来源副作用、变更日志和幂等结果共同提交。JSON 与 PostgreSQL 两条路径均已接入。
- 冲突保存共同基线、本机和云端三份内容，暂停该笔记；其他独立笔记继续同步。冲突期间可以继续本地编辑。
- 界面提供采用云端、采用本地、保留为两篇、手动合并；处理前保留恢复记录，可在同步面板导出。云端再次变化时重新产生冲突，不强制覆盖。
- 云端永久删除后保留删除修订。存在本地修改时允许另存新 ID 的副本，不复活原 ID。
- 游标失效、快照过期和数据集世代变化会重新取得一致性快照。已下载页和进度持久保存；本地分支、未确认请求和冲突不会被整库替换。

当前传输范围是笔记。新建本地目录、标签等操作仍可本地保存，但不会作为网络命令上传；引用尚不存在的云端目录或标签时，只阻塞相关笔记并显示原因，可调整到已有目录后重试。附件二进制未加入传输，云端附件元数据不代表文件已下载。标注和知识来源随云端事务作为读取上下文拉取，独立离线写入入口继续受限。

## 2. 使用入口

先运行包含本轮同步接口的云端 API；PostgreSQL 部署须应用 `7_sync_journal` 迁移。旧生产版本没有同步接口，不能仅启动本地服务就认为已经接通云端。

```bash
npm run build:web
npm run start:desktop -- --data-dir /absolute/path/to/isolated-local-library
```

打开输出的本机入口，在底部状态栏点击“连接云端”，填写服务根地址及现有 Basic Auth 凭据。公网地址必须为 HTTPS；本机测试允许回环 HTTP。账号密码仅保存在运行进程内，重启后重新输入，不写入 SQLite、同步请求负载或普通日志。

首次连接会比较已有资料。相同 ID、不同内容且没有共同基线时进入冲突；已有本地新笔记保留并以空基线条件创建。资料库绑定服务地址和服务端 owner，不能直接改成另一服务器混合数据。需要另一服务时使用新的独立资料目录。

“已保存到本机”描述本地落盘；同步按钮独立显示正在同步、待同步数量、冲突或暂停原因。远端内容应用成功后安静刷新界面；编辑器有未落盘草稿或在途保存时推迟界面刷新和冲突选择。

## 3. 持久化与模块

| 位置 | 本轮职责 |
| --- | --- |
| `apps/api/src/modules/sync/journal.js` | 修订、事务变化组、删除记录、世代及游标 |
| `service.js` / `routes.js` | 状态、固定快照分页、增量拉取和单笔原子提交协议 |
| `local-provider.js` | 复用本地领域服务与 JSON 原子事务 |
| `postgres-provider.js` | PostgreSQL 事务上下文、同一连接及日志提交；同资料库提交使用事务锁串行协调 |
| `prisma/migrations/7_sync_journal` | 按 owner 保存日志的 JSONB 行，与业务事务共同提交 |
| `apps/desktop-runtime/src/sync-state.mjs` | 远端基线、拉取落库、冻结请求、确认与冲突处理 |
| `sync-engine.mjs` | 单一协调循环、HTTP、退避、登录暂停及逐笔错误隔离 |
| `apps/web-v4/src/features/sync/` | 状态入口、连接设置、三份内容对照及恢复记录导出 |
| `scripts/reset-sync-epoch.mjs` | 管理员恢复旧备份后的显式世代重建 |

本地 schema 从 1 升到 2，升级前生成 `local.sqlite.before-v2-时间戳.bak`，保留设备 ID、正文及原 outbox。新增 `sync_uploads`、`sync_conflicts`、`sync_recovery`；连接、游标、分页进度和确认信息放在 `metadata` 的 `sync:` 键中，基线继续使用 `sync_base`。

阶段 1 的 outbox 是不可变领域事务记录；阶段 2 从当前笔记与共同基线生成网络请求，冻结后写入独立上传表。确认只推进已发送修订，不能清空后续编辑。目录等未开放传输的事务保留为依赖阻塞，不伪装成已经全量同步。界面待同步数量按笔记计算。

本地生成的来源版本保留稳定 ID；云端生成相同正文的另一版本时，历史列表按内容哈希展示一次并优先选择云端版本。旧本地版本仍可按 ID 读取，已有来源引用不会因展示去重失效。

JSON 文件新增顶层同步元数据，业务快照仍为 schema 5。PostgreSQL 目前采用每个 owner 一行日志并在事务内比较业务快照；保证先行验证的正确性，但读写成本会随数据和历史增长，需要阶段 5 容量测试后再确定发布规模。事务内没有外部文件或网络 IO。

## 4. 当前协议与兼容性

协议版本为 1：`GET /api/sync/status`、`POST /api/sync/bootstrap`、`GET /api/sync/snapshot`、`GET /api/sync/changes`、`POST /api/sync/push`。沿用 `{ data }` / `{ error }` 封装。

当前 push 每次提交一篇笔记，客户端逐笔串行发送，不需要依赖整个批次一起成功。变化分页以完整领域事务组为单位，不拆分事务组。快照固定边界、有效期 24 小时；同库最多保留 32 个有效快照。当前不自动删除幂等结果、变化日志或删除记录。

网页正文 PATCH 必须携带加载时的 `expectedUpdatedAt`，缺失返回 428 `NOTE_VERSION_REQUIRED`；旧版无条件正文写入不能绕过保护。仓库 V4 自动保存已有该参数。两种 repository 保证同一笔记更新时间严格前进，检查与实际写入保持在事务内。新同步接口使用独立整数修订，不用设备时间判断新旧。

服务端可设置 `KNOWRA_SYNC_PUSH_ENABLED=false` 暂停新同步提交，仍允许读取与本地编辑；恢复后按原操作 ID 重试。认证失败暂停自动网络队列；协议不兼容停止同步；网络与临时错误使用有上限的退避和随机延迟，并遵守 `Retry-After`。永久依赖或校验错误只阻塞相关笔记，修改后可重新提交。

本地运行会话新增 `/api/local-runtime/sync`、`/configure`、`/retry`、`/resolve`、`/recovery`，均保留回环来源与会话校验。恢复记录导出包含用户保留的三份正文，可通过记录中的 Markdown 手动恢复；完整数据库和附件仍使用既有校验备份流程。

## 5. 服务器恢复与回滚

通过应用整库导入会自动提升世代。管理员直接还原旧 JSON 或数据库备份时，须先停止业务写入、保存当前恢复点，再显式重建世代，最后启动更新后的服务。

JSON：

```bash
node scripts/reset-sync-epoch.mjs --driver local-json --data-file /absolute/path/to/restored/knowledge-base.json
```

脚本先保存旁路 JSON 备份，仅重建同步元数据，保留业务数据。PostgreSQL：先在受控环境设置 `KNOWRA_SYNC_RESET_DATABASE_URL`，再执行：

```bash
node scripts/reset-sync-epoch.mjs --driver postgres
```

该操作使旧日志世代失效，下次访问按恢复后的业务数据创建新世代。不能只还原旧日志后继续使用相同世代。对无法确认是否曾提交的新建内容也会产生冲突，用户保留为新副本后才能再次上传。

回滚程序前先停止同步并备份 schema 2 数据库和队列。旧本地运行时不能打开 schema 2；不能删除新库再换旧程序来处理未上传内容。本轮没有改变生产配置或执行生产迁移。

## 6. 验收与证据

本轮使用 macOS、Node 26.4.0、真实 SQLite 文件、回环 HTTP、Chromium 与临时 PostgreSQL 17.11；生产资料未参与测试。PostgreSQL 迁移在空的临时 schema 中完整应用，没有用 Mock 代替数据库事务验证。

- 两个独立 SQLite 设备和网页正文更新收敛；同一次云端提交包含正文版本与变化日志。
- 成功响应丢失、发送期间再编辑、数据库关闭重开后的冻结请求重试，没有重复版本或丢失后继编辑。
- JSON 写入故障和 PostgreSQL 日志提交故障，均回滚业务与日志；SQLite 拉取失败不推进游标。
- 双端修改、软删除与修改、永久删除、四种冲突选择、解决期间再次并发，保留三份内容和恢复记录。
- 固定快照、游标过期、末页恢复点、世代改变及未确认新建防复活得到验证。
- 真实 PostgreSQL 两个 API 实例对同一基线竞争，只接受一次；整库导入后旧游标失效。
- 带标注正文缩短或清空时，旧范围返回失效并允许继续保存；两种驱动对找不到原文的证据统一记为 `insufficient`。PostgreSQL 备份导入保留标注修订、排除及分析范围记录。
- 真实页面完成连接、远端正文自动刷新、三份对照及手动合并；另有离线中文保存与强制终止恢复验收。
