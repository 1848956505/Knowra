# 同步世代重建与删除事实保护

2026-10-01。本流程供管理员在停写、备份完成后处理已经恢复的隔离资料副本。世代是传输基线；墓碑是不可逆删除事实，两者不能一起清掉。程序不自动恢复或删除业务主体，也不读取/上传真实用户资料。

## 已知事实仍存在的重建

旧 `reset-sync-epoch.mjs` 在 JSON 路径创建空墓碑日志，在 PostgreSQL 路径直接删除所有日志，导致已知删除 ID 的保护丢失。现在两驱动均重建 epoch、变化页、游标快照、传输回执与设备序号，保留原墓碑身份/事件/时间/修订；旧格式的“修订存在但主体不存在”仍补成最小删除事实。

如果恢复副本中出现已知永久删除 ID，命令报 `SYNC_RESET_DELETED_ID_PRESENT` 并停止。管理员须先从权威事实核对范围和依赖，在隔离副本完成明确处置；不能因错误而关闭墓碑检查。删除事实损坏报 `SYNC_STORAGE_INVALID`，不把损坏内容当作无删除历史。

JSON保留命令原有恢复前备份，权限0600；失败不改变主文件字节。PostgreSQL只读主体ID，在现有全局维护独占锁及单事务内更新日志；业务表不变，任何日志更新失败整体回滚。PostgreSQL执行前仍须自己完成完整可恢复数据库/附件备份，命令没有创建数据库dump。

```sh
node scripts/reset-sync-epoch.mjs --driver local-json --data-file /absolute/path/to/restored/knowledge-base.json
# 明确设置管理员选定且已备份的隔离库连接，勿复用未核实的其他配置：
node scripts/reset-sync-epoch.mjs --driver postgres
```

PostgreSQL连接从 `KNOWRA_SYNC_RESET_DATABASE_URL` 获取。JSON结果含 `datasetEpoch`、`retainedTombstones` 和备份位置；PG结果含 `resetJournals`、`retainedTombstones`。这些计数只表示仍可核实并保留的事实，不证明事实完整。无PG日志时不创建虚构删除历史，服务下次访问从恢复数据建立世代。

## 整机连同删除事实一起回滚（LC34仍未闭环）

1. 先保持服务停写/不接纳设备提交；完整保留恢复候选、资料、附件、墓碑和备份。
2. 取得回滚点之后独立保存的权威删除事实；核实来源、owner/资料集、事件身份、覆盖时间与完整性。仅凭被回滚的数据、目录修改时间、设备缓存或新epoch不能判断哪些对象后来被清理。
3. 在隔离副本核对删除ID、依赖与历史，明确处置冲突主体后再重建世代。当前命令没有导入/签认外部删除事实或自动级联清理功能。
4. 运行真实旧设备/旧备份防复活、引用与恢复验收，再按批准的恢复窗口开放服务。缺少权威源时保持这项待验，不宣称LC34完成。

本轮只完成“重置不再丢失仍已知事实”。独立源丢失或真实生产灾难恢复、异地备份解密等仍有外部条件；不将合成演练视为真实用户/公网恢复。

## 验收入口

`node --test scripts/test/reset-sync-epoch.test.js`：JSON实际CLI、旧格式事实、损坏/主体冲突、旧设备新旧epoch、迟到创建和旧快照导入。真实PG需显式回环Knowra测试库及 `KNOWRA_SYNC_TEST_ALLOW_WRITES=1`，每例独立schema应用全部迁移；实际CLI保留事实/冲突阻断，数据库触发器在后项日志更新失败时证明整体回滚。测试数据全部合成。
