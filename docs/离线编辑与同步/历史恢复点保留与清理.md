# 历史恢复点保留与清理

## 当前规则

当前笔记正文、当前标注和并发控制修订号仍逐次保存。恢复历史是附加数据，不能让普通编辑变成无限积累的全文与锚点快照。

| 数据 | 普通恢复点规则 | 必须保留的例外 |
| --- | --- | --- |
| 笔记版本 | 最近 24 小时每 10 分钟保留最后一个，其后每天一个；最长 30 天，每篇最多 20 个、最多 2 MiB | 当前正文、创建基线、仍被当前标注/知识来源/题目/分析范围/私有任务引用的版本 |
| 标注修订 | 旧自动跟随记录每 10 分钟保留一个；普通恢复点最多 10 条、最长 7 天、每个标注最多 128 KiB | 当前修订、来源凭证或任务按标注 ID＋revision 引用的修订、旧 Evidence 必需的一个历史见证 |

当前标注每次更新都保存可验证的修订快照，再在同一事务中裁剪旧恢复点。这样在任意时刻绑定知识或保存分析范围都有完整的来源见证；不能简单跳过当前历史行，否则“采样空档内绑定知识、离线继续编辑”会使同步失去证据。revision 仍逐次递增，是并发标识；历史表不必存在从 1 开始的连续行。

以上数量和字节限制只约束可淘汰的恢复点。来源保留根不占恢复点配额，也不能为了满足数量硬删。因此总版本数可能大于 20；来源凭证不是无限编辑过程历史。非法/未知时间戳不会自动删除。

## 保存、清理与同步

- 同步/异步标注服务始终记录当前快照；自动跟随的旧记录按时间分桶采样，人工操作按数量和年龄保留。
- `history-retention.js` 只读生成计划，先裁剪标注修订，再计算剩余修订对正文版本的引用。计划不改写记录字段。
- JSON 与 PostgreSQL 在线事务清理本次修改的笔记；同步批次保留本批提交的历史以保持回执一致，后续事务再淘汰过量恢复点。
- SQLite 离线保存只淘汰尚未同步且没有私有引用的历史。冻结上传、未解决冲突或私有状态无法核查时保守保留。已同步历史由云端产生删除事实。
- `history-sync-retention.mjs` 在收到云端删除时保留本机私有任务仍引用的副本及正文依赖；这些退休 ID 不再上传。无引用副本随基线释放。
- 清理不重建同步世代，不删除历史墓碑、不修改既有知识证据和来源凭证，也不操作附件文件。

私有引用不仅包含活动任务，也包含保留的任务回执、会话、授权清单与动作记录。无法读取时自动清理跳过，专用清理命令则失败关闭。已归档业务来源仍作为引用保留，不把“归档”解释为允许物理删除。

## 存量清理命令（local-json）

默认预览；不会修改原数据，也不会顺带执行 schema 升级：

```bash
node scripts/compact-history.mjs \
  --file /opt/knowra/storage/data/knowledge-base.json \
  --report /opt/knowra-backups/history-preview.json
```

应用前先停止写入 API，确认桌面待同步操作已保存/同步。正式应用重新读取数据、核验预览哈希与规则，先生成完整 JSON 备份并逐字节校验，再以数据存储事务提交主体删除与同步墓碑：

```bash
node scripts/compact-history.mjs \
  --file /opt/knowra/storage/data/knowledge-base.json \
  --apply \
  --preview /opt/knowra-backups/history-preview.json \
  --backup-dir /opt/knowra-backups/history-retention \
  --report /opt/knowra-backups/history-applied.json
```

预览最多有效 24 小时；源文件变化、规则变化、引用变化、私有状态损坏都会拒绝应用。报告包含源文件哈希、计划摘要、逐类删除数量/字节、当前业务记录摘要、备份路径及清理后文件哈希。

JSON 普通写入与维护共用 `.write-lock`。活进程持锁不能被接管；确定原 PID 已退出后才回收遗留锁，并由独立回收锁串行化。若进程恰在回收锁阶段退出，需停服核对后人工移除遗留 `.write-lock.reclaim`。维护后的旧内存实例会因文件身份变化拒绝覆盖，必须重启 API 读取新库。

完整备份用于隔离核对和受控恢复，不直接覆盖在线资料库。跨设备已传播删除事实时，恢复继续遵循[同步世代重建与删除事实保护](同步世代重建与删除事实保护.md)。不要删除原始备份，不要清除删除账本来“恢复同步”。

完成后核验：当前笔记/标注/知识来源/附件记录哈希不变，保留历史字段不变，附件可读；新版桌面拉取清理墓碑后无待同步和冲突，重启或再次同步不会上传退休历史。

## 验证与边界

API runner 中的 `history-retention.test.js` 验证分层规则、字节预算、来源引用与时间分桶边界。桌面 `history-retention.test.mjs` 验证真实 SQLite/JSON 连续编辑；`version-retention-sync.test.mjs` 验证两设备、私有副本、冻结上传、故障回滚、重启和继续编辑，包含 PostgreSQL 变体。`scripts/test/compact-history.test.js` 验证预览只读、备份、过期计划、并发写入屏障及原子替换失败。

这一步解决高频历史的无界积累、保留和存量清理。JSON 整库加载/写入、PostgreSQL 同步快照全表读取仍是后续存储改造范围；同步墓碑和私有任务历史也不是本命令的删除对象。后续应将来源凭证与可淘汰恢复点进一步分离，并采用按记录读写和按内容哈希更新的可重建检索索引，不能把向量索引加入每次保存的整库快照。
