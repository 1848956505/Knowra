## 知识首批依据

沿用[资产生命周期规范](../Knowra_资产生命周期规范_v1.0.md) §5.3、§9.5 及[离线同步方案](离线编辑与双向同步开发方案.md) §8、§9.1：

- 移入回收站保留来源笔记、证据和独立下游资产；已确认目标和题目失效后需重新审阅。
- 从回收站恢复保留原归档属性，重新检查来源；恢复不自动确认下游目标或题目。
- 云端删除与旧设备修改相撞时保留完整冲突和恢复资料；旧修改不能隐式恢复已删除对象。
- 真正恢复必须从回收站明确执行，采用本地冲突内容不能替代该动作。永久已删除 ID 继续受已有删除事实保护。

已实际复现离线“删除 → 恢复”在首次同步前被最终态比较吞掉的问题：父知识净零，目标和题目的本地候选状态被云端旧确认状态覆盖。实现复用本地事务 outbox 的生命周期边界，以私有描述符保留发送顺序，不把标识加入同步载荷；普通内容仍沿用最终态同步。描述符、回执消费与主体同 SQLite 事务提交，拒绝损坏队列，冲突采用云端时先保全恢复记录。旧来源不明的 outbox 不冒充可重建的用户动作历史。

已有 schema7／SQLite7／batch2 与知识显式生命周期动作可复用。同步载荷是合并后的业务终态：合法离线“恢复回收站 → 解除归档 → 确认”不能被误判为非法状态跳转。不能只比较恢复前后审核状态，新增 guard 必须保留这一合法链路。

## 同步兼容性

首批新增强制能力 `knowledge-lifecycle-v1`，沿用 schema7／SQLite7／batch2；旧客户端连接新服务、或新客户端连接旧服务均停止同步并明确提示更新，保留本地资料及未确认请求。升级前冻结请求继续按原请求哈希核对权威回执，不通过改写原请求或清空队列来绕过兼容门禁。发布需 App 与服务端配套更新，本轮只在 Unreleased 记录，不改正式版本、不打 tag，也不执行生产部署或安装。

不支持让旧二进制与旧服务共同操作已带新生命周期队列的资料库：旧上传器会忽略净零动作并确认旧 outbox，新版再次打开会拒绝不完整描述符。该错误保留主体与队列，并不证明能自动重建未知历史。真实降级／备份恢复应按明确的受控恢复流程处理，不能将 capability 门禁外推成任意旧程序读写安全。

## 训练人工资产实现边界

六个业务集合已在 schema7 中存在：`learningObjectives`、`examProfiles`、`examFocuses`、`questions`、`questionObjectives`、`questionSources`。本批补齐上行白名单、旧／新引用依赖闭包、最终态领域校验、PostgreSQL 落库映射和强制 `training-assets-v1` 能力协商；沿用 schema7／SQLite7／batch2，并保留首批 `knowledge-lifecycle-v1`。存活题目目标关系保持原 ID，删除后重新关联使用新 ID，避免复活已知永久删除关系。题目来源可经明确编辑替换，历史笔记版本和知识证据摘录仍不可偷偷改写。题目内容或关系修改须推进版本，冲突中采用本地仍对云端新版本重新核验。

四类训练主体复用本地生命周期描述符，明确的回收／恢复即使最终状态净零仍上行，不让旧云端确认态覆盖本机失效结果。新建且从未同步的图先交付合法创建前像，再发送实际删除／恢复边界；不从来源不明的旧 outbox 推断人工动作。

现有 Web 允许“确认目标与考点 → 修改父目标”，终态保留已确认考点。本批用专用 `exam-focus-review-boundaries.mjs` 在实际本地候选→确认事务登记有限的审阅依赖前像，先合法交付确认、再提交后继父修改；不放松新确认门槛。依赖包含必需的不可变来源和引用闭包，远端基线变化进入可恢复冲突。原 frozen 请求绑定与后续新审阅分别保存，回执只消费对应条目；损坏队列停止并保全 SQLite 实体、outbox 和 metadata。临时父前像不提前确认关联题目，也不覆盖后续用户修改。

现有冻结规则没有要求父目标／配置失效后自动将已确认考点改为候选。本批维持已有 Web 状态语义及确认门槛，不自行发明新级联规则。复习间隔、每日题量和掌握阈值等未来选择不阻塞现有人工资产补齐。

## 联网权威永久清理边界与过程验收

仅知识、学习目标、考试配置、考点和题目五类当前手工资产使用专用联网入口；不开放通用笔记／空间物理删除，不将来源摘要改为手工后绕过生成来源保护，不先删 SQLite 再上传 null。

预检及执行读取实际持久化 AI 范围、manifest、attempt、任务描述与提炼 commit，而非依据开关。缺表、坏字段、未知范围、孤儿记录和不可读私有存储均明确阻断，正常已完成 notes-only 历史不伪造活动引用。现有回收站目标仍作为实际引用阻止清理父知识。云端在原清理事务核对 `expectedUpdatedAt` 和可选 `expectedDatasetEpoch`；旧 Web 不传 epoch 的调用兼容，但不能外推同世代保证。

本地预检先安全同步，只在正确云端／owner／epoch／资料集绑定和关联组无脏修改／冻结／冲突时取得原 token；执行不偷偷换新基线。通过共享 FIFO 锁隔离同步、配置、断开和恢复，网络期间不持 SQLite 事务。提交前同事务保存不含凭据的最小待核对记录；收到回复也必须实际拉取 subject 和专属关系的 revision-null 墓碑与已知删除事实后才报成功。未知结果和重启只读对账、不自动重发 DELETE；真正远端拒绝与同世代新预检分别处理。清理期间用户新恢复／编辑保留为 `recovery-required`，不把云端删除事实等同于本地修改已经消失。

初步固定源独审实际发现一个 P2：已提交清理丢响应，再经 513 次真实无关笔记变更触发 journal 裁剪，重启后待核对要求 cursor、bootstrap 又晚于该核对，导致永久阻断。原件与 pending 没丢，也没有重发清理。必要修复先验证同 owner／origin／epoch／资料集，允许只读 snapshot 恢复游标及墓碑，再核对 pending；即使快照保留脏冲突并返回 false，也保全新编辑并完成删除事实对账。原探针先红后绿、独立复验 4/4；未送达仍保留 pending，epoch 改变拒绝套用旧结果。

准确训练 green main `3f4e4ead57b17d60eca19a54a7ab5eac519ed4c5` 融合后的实际结果（与提前验收的训练候选依赖及清理源码 tree 完全一致；清理尚未完整发布验收）：完整本地 API 自定义531＋纯合同21通过，新增本地17、关联49先前通过；融合注册保留知识 3＋6、清理 17＋5 各一次。运行时权威矩阵 24 通过／1 真实 PG 条件跳过；原训练编辑碰撞条件例已激活，题目 restore／edit 的恢复资料跨 SQLite 重启保留。UI/store43、API合同19、生产构建与真实 HTTP／SQLite／Chromium4项页面均通过、零跳过，覆盖五类清理、引用阻塞、离线、丢响应对账和知识／题目提交期间编辑的两次重启。训练最终候选融合后完整 desktop435通过、0失败、14实库环境跳过。首次融合434通过／1失败／14跳过，唯一失败是既有入口测试仍期待“功能未开放”；新增权威入口无预检凭据必须返回409／`LOCAL_PURGE_PREVIEW_REQUIRED`。仅更新该合同预期并增加明确409断言，原 pending 与无删除事实保护保留，原场景1/1与必要完整回归均通过。过程失败保留。准确训练 green main 提交身份已同步，无源码变化、不重复同树完整回归；完整固定 head 独审和实际 PG5＋运行时PG1 CI 仍待执行，不能将本地 PG0 当成通过。
