# 离线编辑与双向同步开发方案

> 日期：2026-09-10  
> 状态：阶段 0–5 工程实现与本机验收已完成，当前范围与发布边界见 [阶段 4/5 验收](阶段4与阶段5-完整同步与发布验收.md)。
> 目标：为 Knowra Mac 客户端提供可靠的离线编辑和单人多设备云端同步；网页端继续参与同一套版本与冲突规则。  
> 第一版边界：单人多设备，不包含多人实时协作、字符级协同编辑及正文自动合并。

## 1. 产品目标与范围

用户在 Mac 上修改笔记后，内容先保存到本机；没有网络也可以关闭、重启应用并继续编辑。联网后自动上传本地修改、下载云端更新。网页与 Mac 同时修改同一对象时保留双方内容，由用户选择或手动合并，不静默覆盖。

首版完整交付包含：

- 本地新建、编辑、移动笔记，维护文件夹和标签。
- 离线插入图片和附件，阅读已经下载的附件。
- 本地创建、取消、恢复重点标记，保留标注与正文版本的关联。
- 回收站删除与恢复的双向同步。
- 自动同步、手动重试、同步状态和冲突处理界面。
- 首次下载、中断续传、崩溃恢复、升级迁移及本地备份导出。

第一版知识管理、试题、作答和 AI 功能维持联网使用；离线时明确禁用需要联网的动作。它们已经存在的来源引用必须随笔记更新或删除正确失效，不能因暂不开放离线编辑而跳过一致性处理。不可变来源版本按引用同步或按需下载；尚未下载的历史内容明确显示“需要联网下载”。

网页端首版仍以在线编辑为主，不承诺浏览器关闭后的完整离线能力。Mac 桌面外壳、安装包和签名发布另行实施，本方案定义其必须提供的本地存储和进程生命周期接口。

## 2. 当前基础与差距

本节基于当前仓库检查，不代表已具备同步能力。

| 当前基础 | 可以复用 | 需要补齐 |
| --- | --- | --- |
| `useNoteAutosave.ts` 按笔记协调保存，并传递 `expectedUpdatedAt` | 保存调度和冲突交互入口 | 持久化本地修订、同步确认与编辑状态分离 |
| `noteDraftRecovery.ts` 使用内存及 `sessionStorage` | 升级时的一次性草稿恢复入口 | 可跨应用重启恢复的本地事务存储 |
| API 正文保存检查版本，已有不可变笔记版本 | 内容版本、来源追溯、拒绝覆盖的基础 | 所有可同步实体统一使用服务端修订号 |
| 附件哈希校验、回收站、标注修订与引用校验 | 完整性校验与领域服务 | 二进制传输队列、删除日志、依赖顺序 |
| 缓存或加载异常时有只读保护 | 故障保护 | 只有本地事务库初始化成功的桌面模式才允许离线写入 |
| local-json 与 PostgreSQL 两种持久化路径 | repository 与事务装配边界 | 两种驱动中的原子变更日志、幂等记录及同步验收 |

实现入口主要为 `apps/web-v4/src/features/editor/`、V4 store 与数据访问层、`apps/api/src/modules/knowledge/`、`apps/api/src/app.factory.js`。具体拆分以实施前的代码定位为准。

领域语义参考 [领域冻结稿](../知识库与试题模块/基础/Knowra%20知识与考卷系统领域冻结稿.md) 及 [重点标记文档](../知识库与试题模块/标注功能/)。同步只传递领域变化，不重新定义知识模型。

## 3. 总体架构与硬性约束

```text
Mac 编辑器 → 本地事务服务 → 本地业务数据 + 待同步队列
                                 ↓
                            后台同步引擎
                                 ↕ HTTPS
网页在线编辑 → 云端应用服务 → 业务数据 + 修订号 + 变更日志 + 幂等结果
                                 ↓
                      Mac 拉取、落库、通知界面刷新
```

1. 本地业务修改和待同步操作必须在同一事务提交。事务成功才显示“已保存到本机”。
2. 云端业务修改、服务端修订、变更日志及幂等结果必须在同一事务提交。
3. 不使用设备时间判断新旧，不用整份 JSON 覆盖实现同步。
4. 网络超时不等于写入失败；重试同一个操作不得产生重复数据或重复副作用。
5. 拉取远端内容不得覆盖本地待同步内容，必须先检查共同基线。
6. 正文、附件、标注和来源证据必须保持引用一致性。
7. 同步不替代备份；错误删除也会同步，仍需独立恢复点。
8. 未初始化、迁移失败、磁盘写入失败的本地库不得进入可写模式。

桌面使用支持事务的嵌入式数据库保存结构化数据，附件放应用数据目录。数据库具体依赖在桌面运行时确定后单独验证，准入检查包括事务、崩溃恢复、迁移和目标平台打包，不在本方案中冻结第三方库。

本地存储由桌面受控服务访问，渲染层只调用受限业务接口；不得暴露任意文件读写或任意代码执行能力。数据目录通过桌面运行时解析，不写入安装目录或仓库 `storage/`。浏览器未来可以增加自己的存储适配器，不与桌面文件路径耦合。

## 4. 同步数据模型

### 4.1 标识与修订

| 字段 | 职责 |
| --- | --- |
| `entityId` | 跨设备稳定 ID；离线创建时生成，服务端校验，已有 ID 不重建 |
| `entityType` | 笔记、文件夹、标签、标注、附件元数据等 |
| `serverRevision` | 云端对同一实体单调递增的整数，作为并发写入条件 |
| `localRevision` | 本机单调递增的编辑序号，用于判断确认后是否还有新编辑 |
| `baseRevision` | 本地操作建立时所依据的云端修订；新建使用明确的空基线 |
| `operationId` | 一次不可变提交的唯一 ID，重试保持不变 |
| `deviceId` | 当前安装实例 ID，仅用于来源、诊断和设备管理，不承担认证 |
| `cursor` | 服务端签发的不透明变更游标，限定数据集及同步范围 |
| `datasetEpoch` | 数据集世代；恢复旧备份或重建日志时变更，阻止旧游标继续使用 |
| `protocolVersion` | 协议兼容检查，与业务 schema 版本分别管理 |

`updatedAt` 保留用于展示及旧接口兼容，不再作为新同步协议的唯一并发依据。服务端不接受客户端指定的新修订号或 owner。

### 4.2 本地表或等价存储

- 业务实体：当前用户可见内容、远端基线修订、本地编辑序号。
- `sync_base`：最后确认的远端快照，支持基线比较；不能只有一个时间戳。
- `sync_outbox`：操作 ID、实体、基线、负载、依赖操作、状态、重试次数、错误分类。
- `sync_state`：服务地址与空间绑定、世代、已应用游标、初始化进度。
- `sync_conflicts`：共同基线、本地版本、远端版本、冲突种类、解决状态。
- `attachment_jobs`：本地文件、哈希、大小、上传或下载状态、失败原因。

同步元数据与业务字段分开保存，避免同步状态污染领域对象。凭据不写入正文、同步负载或普通日志。

### 4.3 服务端记录

- 变更日志：范围内单调排序的序号、实体 ID、动作、修订、事务组、不可变负载或可恢复对应修订的引用。
- 幂等记录：操作 ID、提交来源、请求摘要及完整处理结果；同 ID 不同负载直接拒绝。
- 删除记录：实体 ID、删除修订、删除类型及对应变更序号。
- 设备检查点：用于诊断和保留策略，不将设备自报游标当作授权依据。

首版不自动清理幂等记录和删除记录。后续引入保留期限时必须同时提供游标过期、全量重建和旧操作重放保护，不能只按日期删表。

## 5. 本地保存与任务状态

用户输入可短暂合并后写入本地，但“保存中”必须持续到事务成功；应用退出时等待在途本地提交。异常崩溃只承诺恢复已经落盘的数据，不声称恢复尚在内存里的最后按键。

本地保存流程：验证输入 → 更新实体与 `localRevision` → 写入 outbox → 提交事务 → 更新“已保存到本机” → 唤醒同步引擎。

队列状态为 `pending → sending → acknowledged`，另有 `retry_wait`、`blocked_dependency`、`conflict` 和 `failed_permanent`。应用重启后，所有未确认的 `sending` 按原操作 ID 重试。

同一实体串行提交，不同独立实体允许有限并发。未发送且没有依赖者的连续编辑可合并；一旦进入发送阶段，操作 ID 和负载冻结。发送期间的新编辑创建后继操作，前一个确认后再以返回修订作为后继基线。

确认旧操作只更新其对应基线，不能把之后的新输入标为已同步。禁止清空整篇笔记队列来处理一个成功响应。

同一设备多窗口由单个本地服务协调写入和同步；如运行环境允许多进程，增加实例互斥及可恢复租约。不能让两个同步循环同时发送同一实体的不同基线。

## 6. 服务端协议草案

下列接口名称为开发契约草案，仍沿用 `{ data: ... }` 与 `{ error: { code, message } }` 封装。

| 接口 | 输入与返回 | 关键规则 |
| --- | --- | --- |
| `GET /api/sync/status` | 协议能力、世代、范围及服务状态 | 检查兼容性，不返回其他 owner 数据 |
| `POST /api/sync/bootstrap` | 创建一致性快照，返回快照 ID 与边界游标 | 快照内容固定，可分页续取 |
| `GET /api/sync/snapshot` | 快照 ID、分页令牌 | 返回同一边界下的数据；过期后重新初始化 |
| `GET /api/sync/changes` | 游标、页大小 | 返回变化、下一游标、是否仍有后续 |
| `POST /api/sync/push` | 有限大小的操作批次 | 每个独立操作返回接受、冲突、依赖失败或校验失败 |
| `POST /api/sync/attachments/prepare` | 哈希、大小、媒体信息 | 检查授权范围内是否可复用，或创建上传任务 |
| `POST /api/sync/attachments/complete` | 上传任务 ID | 服务端校验实际内容后发布附件元数据 |

变更日志的一个事务组不得拆到两个可单独应用的分页中；大组返回专用分段令牌，客户端收齐后一次应用。游标只能在对应数据成功落库的同一事务中推进。

普通批次允许部分成功，客户端逐项确认；必须共同成功的领域命令作为一个原子操作提交，例如正文更新引发的来源状态变化。不存在依赖“整个 HTTP 批次恰好全部成功”的隐含规则。

所有云端写入入口都必须产生日志，包括网页编辑、导入、移动、删除、恢复以及领域服务带来的关联更新。同步路由复用应用服务，不能绕过领域校验直接写 repository。网页正文保存同步升级为修订检查；旧接口的版本条件必须在同一写事务中判断，不能先读后无条件覆盖。

错误至少区分 `REVISION_CONFLICT`、`DEPENDENCY_MISSING`、`CURSOR_EXPIRED`、`DATASET_CHANGED`、`PROTOCOL_UNSUPPORTED`、`AUTH_REQUIRED` 和存储失败。认证失败暂停网络队列但保留本地编辑；协议不兼容停止同步，不尝试猜测负载格式。

## 7. 初始化与增量同步流程

### 7.1 首次连接

1. 校验服务地址、认证、空间和协议，将本地库绑定到明确的数据集。
2. 云端生成固定边界快照，客户端分页写入临时区域并持久保存下载进度。
3. 校验 ID、数量、引用和附件元数据完整性，再原子切换为可用本地数据集。
4. 从快照边界游标拉取后续变化，避免漏掉下载期间的网页修改。
5. 正文可用后按需下载附件，提供“下载全部附件”及进度；未下载的附件不宣称可离线使用。

初始化失败保留已有可用库。若首次连接前已有本地笔记，将其作为待上传的新内容处理，不用云端快照覆盖。已绑定其他服务或空间的库必须分库存放，不直接混合。

### 7.2 正常同步

启动、网络恢复、窗口重新激活、本地提交、用户手动操作及低频定时检查均可触发；所有触发合并进入一个协调器。

每轮先拉取远端变化并落库：无本地修改则应用，有本地修改则保存远端快照并检测冲突；随后上传依赖满足的操作，处理逐项结果，再拉取一次收敛。即使拉取后远端再次变化，上传时的条件写入仍负责拒绝冲突。

断网、超时和暂时性服务错误使用有上限的退避与随机延迟；尊重服务端重试提示。永久校验错误展示具体对象和处理方式，不无限重试。关闭应用后首版不承诺后台同步，未完成队列在下次启动继续。

### 7.3 游标失效与服务器恢复

游标过期或世代变化时先保全本地实体、基线、冲突和全部未确认操作，再下载新快照。按实体逐项重新比较，匹配的基线可以继续，无法确认的修改进入待处理冲突，不能无条件重新上传覆盖服务器。

“重新下载云端数据”只替换干净缓存，不能删除待同步内容。恢复服务器备份必须提升 `datasetEpoch`，避免旧游标和旧幂等结果误判；恢复后的旧操作按新基线重新确认，必要时生成新的操作 ID。

## 8. 冲突处理规则

首版采用实体级保守冲突策略，同一篇笔记即使修改不同段落也不自动合并。

| 场景 | 处理 |
| --- | --- |
| 仅本地变化 | 条件上传 |
| 仅云端变化 | 应用云端版本 |
| 双方变化，但业务内容相同 | 确认一致并推进基线；不重复生成版本 |
| 双方修改同一实体且内容不同 | 持久保存基线、本地、云端三个快照，暂停该实体后续提交 |
| 一方删除、一方修改 | 显示删除冲突，保留修改内容供恢复为副本 |
| 文件夹被删、离线新建或移动笔记仍引用它 | 阻塞该操作，提示选择有效目录；不默默丢失笔记 |
| 同名笔记、文件夹或标签 | 按 ID 区分，沿用现有命名校验，不因同名自动合并 |

冲突界面提供“采用云端”“采用本地”“保留为两篇”和“手动合并”。应用任一选择前先保存可恢复副本；解决结果必须基于最新远端修订提交，如果远端再次变化则重新检测，不强制覆盖。

“采用云端”清理被用户明确放弃的待同步操作，但其内容保留在恢复记录中。“保留为两篇”给副本新 ID，复制必要附件关系；标注必须依照副本正文重新验证，知识来源不能自动改指向副本。

存在冲突的笔记可以继续本地编辑，但新内容留在冲突分支，界面持续显示待处理；其他独立笔记仍可同步。

## 9. 删除、附件与标注一致性

### 9.1 删除与恢复

回收站删除和恢复都是带修订的显式操作。离线旧设备再次上线时必须读到删除记录，旧更新不能隐式复活已删除对象。

首版永久删除要求联网，经现有引用校验和协调删除事务处理；客户端收到记录后删除干净副本，有未同步修改则先进入删除冲突。附件物理清理由引用检查及恢复保留策略决定，不随某一个客户端的删除立即执行。

### 9.2 附件

离线插入时先将文件写入受管临时区，完成哈希和大小校验，再原子移动至本地附件区，最后提交元数据与队列。文件写入成功但数据库提交失败形成的孤儿文件由延迟扫描清理。

本地正文通过稳定附件 ID 解析本机文件，不写入设备绝对路径。服务端先接收并验证二进制，再发布可引用元数据；正文操作依赖附件发布成功，不能提前暴露无效远端链接。

首版允许失败后重新上传完整文件，保证操作幂等与哈希去重；大文件分块续传作为后续优化，UI 不宣称已支持。下载采用临时文件、校验及原子替换，下载中断不损坏旧文件。

去重查询仅限授权范围；哈希相同不代表拥有读取权限。磁盘不足保留队列并提示释放空间，禁止删除未上传附件来腾空间。

### 9.3 正文版本、重点与知识来源

标注同步包含当前 anchor、局部排除、修订、生命周期和所依据的正文哈希或版本。离线创建标注依赖对应正文操作确认；服务端返回版本映射后再提交依赖项，不能把本地临时版本当成云端已存在版本。

正文更新后继续执行当前重定位与来源状态校验。无法可靠定位的重点进入待检查状态，不以猜测位置覆盖。取消标注不删除知识点；正文删除或变化按领域规则更新来源状态。

不可变笔记版本与分析范围快照按稳定 ID 和内容校验复用。被知识来源引用的旧版本不得因为同步压缩而清理。离线不启动远端 AI 分析；联网执行前必须明确采用的已确认内容版本。

## 10. UI 与故障恢复

将本地保存状态和云端状态分别呈现：

| 状态 | 用户提示 |
| --- | --- |
| 本地事务尚未完成 | 保存中 |
| 已落盘，等待网络或上传 | 已保存到本机 · 待同步 |
| 正在传输 | 正在同步，可查看待处理数量 |
| 本地操作已确认，已拉取至本轮边界 | 已同步，并显示最近成功时间 |
| 存在并发修改 | 需要处理冲突 |
| 本地写入失败 | 保存失败，保留当前内容并提供导出 |
| 凭据过期 | 已保存到本机 · 请重新连接云端 |

“已同步”表示本机已完成当前已知工作，不承诺其他离线设备没有修改。附件未完成时必须显示剩余任务，不能仅凭正文上传成功宣称全部同步完成。

同步详情展示对象、状态和可执行动作；诊断日志只记录 ID、修订、错误分类和耗时，默认不记录正文或凭据。复用现有 UI 组件和独立滚动布局。

用户退出连接或切换空间时保留原数据集待同步内容。清除本地数据前检查未确认修改，提供导出并明确确认；不能用清缓存作为常规同步修复手段。

## 11. 服务端持久化、授权和兼容

local-json 仍为默认驱动：通过 `dataStore.runTransaction()` 将业务变化、日志、幂等记录和删除记录一起原子替换，控制批次大小并测量日志增长后的写入成本。不能用独立 JSON 文件先后写入模拟跨文件事务。若容量目标不能满足，应先报告测量结果，再决定迁移，不静默切换数据库。

PostgreSQL 在同一数据库事务中执行修订比较、业务写入、日志和幂等结果提交。附件文件和网络 IO 在事务外完成，通过准备、发布和孤儿回收流程协调。

HTTP owner 继续由服务端决定，`deviceId` 和客户端空间参数不构成授权。现有 Basic Auth 在正式登录前保留；同步接口与附件接口必须位于同一保护边界。首版只针对受保护的单用户部署，未来多账号需要独立身份认证和空间访问控制。

协议迁移先上线可兼容服务端，再启用客户端。对不能正确参加并发控制的旧写入端，返回明确升级要求，不能长期允许无条件覆盖。未知实体类型或字段语义导致无法安全应用时暂停并提示升级，不跳过变化后推进游标。

## 12. 建议代码职责

以下目录在实现阶段按实际架构建立，不因本方案提前创建空模块。

| 拟议位置 | 职责 |
| --- | --- |
| `packages/sync-core/` | 无 DOM、无数据库依赖的协议类型、队列状态与冲突判定 |
| 桌面运行时的本地存储模块 | 数据库、附件目录、事务、迁移及受限客户端接口 |
| `apps/web-v4/src/features/sync/` | 同步状态、详情、冲突解决交互 |
| V4 数据访问适配层 | 在线 API 与桌面本地服务的切换；组件不直接操作数据库 |
| `apps/api/src/modules/sync/` | 快照、变化分页、提交编排、幂等和授权范围校验 |
| 现有领域应用服务与 repository | 领域校验、修订写入、驱动事务与变更日志 |

V4 不导入 V3。UI 包装边界保持不变；`packages/web-core` 不加入桌面、DOM 或数据库依赖。同步核心只抽取确实需要共享的机制，不复制整套领域服务。

## 13. 分阶段实施与交付门槛

| 阶段 | 开发内容 | 必须通过的门槛 |
| --- | --- | --- |
| 0：契约与基线 | 盘点全部写入口、冻结首版实体清单、协议和本地事务接口；建立数据备份 | 每一种领域写入有日志覆盖方案；恢复演练可回到原数据 |
| 1：离线保存 | 本地事务库、正文与队列、迁移、编辑器数据适配 | 断网编辑后正常重启和强制终止均能恢复已落盘内容 |
| 2：最小双向链路 | 服务端修订、日志、幂等、快照及正文增量同步 | 两台设备和网页能收敛；丢响应重试不重复写入 |
| 3：冲突与删除 | 三份快照、冲突 UI、回收站、游标过期和世代变化 | 并发修改和删除修改冲突均不丢内容；旧设备不复活数据 |
| 4：完整首版范围 | 文件夹、标签、附件、标注和来源状态依赖 | 网络中断、引用变化和附件失败不会破坏数据关联 |
| 5：发布与恢复 | 多驱动测试、容量测试、客户端升级、灰度开关、运维说明 | 所有首版验收项通过并保存证据，才能称为完整离线同步 |

阶段 2 只是正文试验闭环，不能对外称为完整同步。先以副本数据和独立测试空间验证，再在一台设备小范围启用；服务端可关闭新同步提交，客户端仍保留本地保存及导出能力。

回滚前停止同步写入并备份包含队列的新数据格式。旧客户端不能直接打开不兼容的新库；保留升级前备份并提供导出路径。仅回滚程序而丢弃未上传数据不算合格恢复。

## 14. 验收矩阵

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A01 | 断网新建和编辑，退出重启 | 已确认本地保存的内容、队列和附件全部存在 |
| A02 | 落盘前后分别强制终止进程 | 已提交数据恢复；不出现业务变了但队列缺失 |
| A03 | 服务端提交后丢失响应，再重试 | 只产生一次业务操作和必要版本，返回一致结果 |
| A04 | 上传期间继续输入 | 旧响应不清除新输入，后继操作最终收敛 |
| A05 | 两台设备及网页并发编辑同一笔记 | 双方版本均保留，其他笔记正常同步 |
| A06 | 冲突解决期间远端再次修改 | 再次检测冲突，不无条件覆盖 |
| A07 | 删除与离线修改相撞 | 显示删除冲突，旧笔记不自动复活 |
| A08 | 离线创建目录、笔记、附件及重点 | 按依赖提交，服务端不存在悬空引用 |
| A09 | 上传或下载中断、哈希不符、磁盘满 | 任务可恢复或有明确失败状态，不显示虚假成功 |
| A10 | 快照分页期间持续网页编辑 | 快照与后续增量组合无遗漏，重启可续取 |
| A11 | 应用变更页中途崩溃 | 实体与游标一起回滚或一起提交，无跳页 |
| A12 | 游标过期、服务器恢复旧备份 | 重建基线且保留本地未确认内容，不重放旧覆盖 |
| A13 | 标注来源正文改变、重点取消或恢复 | 定位与证据状态正确，历史知识不会误删除 |
| A14 | 协议不兼容、认证失败、切换空间 | 停止不安全同步，本地数据完整且隔离 |
| A15 | 网页导入、批量移动、删除恢复 | 每条变化可被其他设备拉取，领域副作用不遗漏 |
| A16 | local-json 与 PostgreSQL 故障注入 | 业务、日志、修订和幂等结果始终原子一致 |
| A17 | 本地库迁移失败及版本回滚 | 原库可恢复，未上传数据可导出 |
| A18 | 多窗口并发操作、设备时钟相差一天 | 不重复发送、不依赖设备时间覆盖数据 |

单元测试覆盖状态机与基线判断，服务集成测试覆盖真实事务和故障点，端到端测试覆盖两设备加网页以及中文编辑、附件、标注和回收站。按仓库规则使用 API 显式 runner，不把导入测试文件视为执行。

实现阶段运行受影响的 API、共享包、V4 检查与完整相关 E2E；两种持久化驱动分别记录证据。建议使用 100、1,000、10,000 篇笔记和不同附件体积测量首次下载、增量时延、存储增长与编辑响应；性能准入数字在阶段 0 的目标硬件实测后冻结，不能使用未经验证的承诺。

发布记录必须包含提交、协议/schema 版本、操作系统、持久化驱动、数据规模、故障注入结果及备份恢复路径。文档方案完成不等于实现完成，测试通过也不自动代表生产环境验收通过。
