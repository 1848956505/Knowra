# Knowra 资产生命周期差距与实施方案

> 日期：2026-09-23  
> 依据：[《Knowra 资产生命周期规范》v1.0](../Knowra_资产生命周期规范_v1.0.md)  
> 代码基线：当前工作区，HEAD `3a2e53b`；工作区存在其他未提交改动。本方案依据静态代码核对，不等于线上、真实 PostgreSQL 或多设备验收。  
> 范围：只记录差距与改造顺序，不修改业务代码、不迁移数据、不启用删除入口。

## 1. 判断口径

规范将**业务审核、归档、回收站、来源健康、来源适用性、同步进度**分为不同语义；已归档记录不能直接解释为用户同意删除。所有状态的工作资产原则上都可申请移入回收站，是否能永久清理由真实引用和历史保留条件决定，不能仅靠 `candidate`、`confirmed` 等审核状态判断安全性（规范 §1、§3、§14）。

对每项能力分别检查页面、共享 API、领域服务、JSON 与 PostgreSQL、同步、导入／备份、检索与历史引用。下表的“缺少”指当前代码未提供规范要求的完整业务能力；“待核”表示仅凭本次静态检索不能确认运行结果。规范中尚未实现的训练实体单列，不按已上线功能缺陷计算。

## 2. 当前资产差距

| 资产 | 当前可见能力与代码依据 | 与规范的差距 | 下一步 |
| --- | --- | --- | --- |

| 笔记版本 `NoteVersion` | 版本接口仅列出、读取；同步将其列为不可变，笔记永久删除时协调器删除所属版本。见 `note-version-routes.js`、`modules/sync/entity-contract.js`、`application/note-deletion-coordinator.js`。 | **不满足 §5.5 的维护能力。** 无“清理无引用历史版本”预览／入口，无法逐项说明当前版本、保留点、来源或任务占用原因。 | 先建只读版本引用预览，后加受控裁剪；已有历史不自动按时间删除。 |

| 知识空间 `KnowledgeSpace` | 只提供默认空间创建和列出；没有归档、迁移、清空用户内容、删除与恢复接口。见 `space-routes.js`。 | **不满足 §7.1。** 默认空间外壳可以受保护，但用户仍须能够清空或迁移自有内容；非空范围及历史需明确。 | 待单资产生命周期闭环后设计空间级预检、迁移和组合删除包；不先开放一键删除空间。 |
| 标注排除项 `AnnotationExclusion` | “恢复排除范围”会把记录标为 `archived`，原记录留存。见 `application/annotation-scope-service.js`。 | **语义待校准。** 它是父标注关系的历史操作，不宜机械套用完整资产回收站；需明确随父标注清理与历史引用边界。 | 纳入父标注引用图和删除包，保留操作历史；无需单独增加普通删除按钮。 |

### 训练域及尚未落地的资产

`LearningObjective`、`ExamProfile`、`ExamFocus`、`Question` 已有服务和 API，但仅支持归档／恢复，没有回收站及永久清理；V4 训练页仍是占位页面。它们是**已有领域能力与目标规范之间的差距**，应随正式训练工作域接入完成，不宜先孤立添加 API 删除。依据：`learning-objective-routes.js`、`assessment-routes.js`、`AppRoutes.tsx`。

规范列出的 `KnowledgeRelation`、`KnowledgeTopic`、`ExamBlueprint`、正式 `Exam`、`Attempt`、`Response`、`GradeResult`、`LearningEvidence`、`MasteryState` 等，本次在当前 Prisma 模型与知识模块中未找到对应完整实体／页面。它们属于**未来实现时必须同时满足的生命周期要求**，不是把尚不存在的按钮列为当前页面缺陷。可重建索引、缓存、AI 任务、备份和独立历史包的实际存储与保留范围需在各功能启用前继续盘点。

## 3. 跨资产基础差距与先决条件

1. **生命周期契约：** 当前 `KnowledgeItem.reviewStatus` 同时含审核与归档，`ContentAnnotation` 的取消重点也落为归档。新增删除属性时须保留既有 `archived` 含义，记录删除前归档属性、删除包、权威操作时间和操作基线；旧记录不批量重释。
2. **引用图与预检：** 现有笔记永久删除对几类正式来源有阻断，PostgreSQL 的 `KnowledgeEvidence` 和 `LearningObjective` 对 `KnowledgeItem` 也是 `Restrict` 关系。须补齐当前、历史、共享、派生、任务和待同步引用，给出“可删除／保留哪些副本／需处理哪些依赖／当前无法安全处理”的结构化结果。预览后执行前再次复核。
3. **同步删除事实：** `modules/sync/journal.js` 已记录修订和 `value=null` 变更，`batch-service.js` 能拒绝旧 ID 直接复活；这可作为基础，但不是规范 §9 要求的完整生命周期操作。`knowledge-batch-domain.js` 仍拒绝知识对象 `null` 和 `deletedAt` 变化。要新增显式删除／恢复动作、预期版本、幂等标识、权威顺序、最小墓碑及旧端能力门禁，同时保留对无语义删除载荷的拒绝。先验证 JSON、PostgreSQL、桌面端和旧备份导入的一致性。
4. **正常使用门禁：** 回收站资产在普通列表、搜索、AI 上下文、来源选择、正式确认、新组卷和默认导出均不可被使用。归档退出默认工作范围，但不改写历史统计；历史快照按当时内容展示。客户端隐藏按钮不代替权威领域校验。
5. **永久清理与结果：** 先可靠记录不可逆删除事实，再清主体、专属记录、文件、索引；外部文件／索引用可重试任务，不放进数据库事务。结果需分别报告主体、附件／索引、离线副本和备份，不把 HTTP 成功解释为所有副本清除。
6. **用户可辨认的对象：** 知识库切换状态筛选时当前详情不会自动切换至筛选结果，截图出现“左侧已归档、右侧已确认”的混合状态。加入删除前先修正选择与筛选的一致性，确认弹窗始终显示实际操作对象。

## 4. 分步改造与每步交付

### 阶段 0：冻结语义和安全基线

- 把规范 §1、§4、§8、§9 转成领域状态转换表、引用分类表和统一的删除预检／结果契约；列清 JSON、PostgreSQL、桌面、Web、导入和同步的入口。
- 建立只读引用盘点及阻断原因；核对现有 `deletedAt`、归档记录、同步修订记录和真实数据库关系。旧客户端不理解新状态时先限制写入。
- 先修高风险直删路径：附件必须由权威服务检查所有保留引用；保留笔记已有引用保护。加基线测试，不开放新的永久删除入口。
- 交付：逐实体字段与依赖清单、迁移兼容规则、操作协议草案、只读预检结果、当前保护回归测试。

### 阶段 1：当前工作资产的回收站闭环

1. **笔记和标注：** 保持笔记已有回收站能力，补删除包与子标注独立状态的恢复检查；“取消重点”转为可恢复删除并提供短期撤销，旧归档不转换。证据健康按独立可复核性处理。
2. **知识来源与知识点：** 先拆分 Evidence 的“撤回适用性／技术健康”；再为 KnowledgeItem 增加回收站、恢复及全状态可请求删除。删除后停止新使用并标明关联目标／题目处理路径，不级联删除独立资产。恢复回到原归档属性，审核与来源重新校验。
3. **已保存分析范围：** 增加可管理列表、回收站与恢复；在用任务和被引快照先保护。
4. **现有组织资产：** 标签删除纳入删除事实和撤销回归；文件夹先增加明确的“保留内容并移动”流程，再做可恢复组合删除。
- 每个小步均包含共享 API、领域服务、JSON／PostgreSQL、桌面同步与 V4 UI 的同一语义；能力未闭环时相应按钮保持禁用或不展示。
- 交付：规范 LC-01～09、LC-11～12、LC-19、LC-35～36 对应的功能与测试，实际受影响页面状态验证。

### 阶段 2：受控永久清理与空间管理

- 按对象开放经预检安全的永久清理；有引用但缺独立历史包的情况继续阻断，并提供查看／处理引用的可执行路径。不按 `candidate` 或 `confirmed` 设一刀切白名单。
- 做最小墓碑、删除任务与文件／索引重试；笔记版本先提供受保护裁剪预览，附件按共享引用计数清理。补导入旧文件与恢复旧备份时的删除边界。
- 空间提供空容器删除、用户内容迁移或显式组合删除包；默认空间外壳与自有内容分开。
- 首版不启用自动 30 天清理，不自动删除既有归档；待测得保留范围和清理可靠性后再设计策略。
- 交付：规范 LC-10、LC-20～30、LC-33～36 的异常、并发、重试及多端验收报告。

### 阶段 3：随训练工作域实现完整生命周期

- 接入学习目标、考试配置、考点、题目时，同步提供归档、回收站、恢复与受控清理；题目历史先有独立完整快照，再允许删除题库原题。
- 实现正式试卷、训练记录和学习证据时，以整次训练记录为默认清除单元；暂停／撤回相应证据贡献，重算掌握度，历史试卷和评分说明不被无声改写。
- 尚未实现的知识关系、主题与蓝图按规范 §6～7 建模，关系删除只影响关系，不删除两端资产。
- 交付：规范 LC-13～18 及未来实体对应的历史快照、贡献重算和清理测试。

### 阶段 4：基于实际数据的留存与 GC

- 先测量正文、版本、来源、附件、索引、同步日志及备份体积，再决定自动回收站到期清理、版本裁剪和缓存 GC 的优先级。
- 墓碑首次不按固定天数自动过期；只有设备安全水位、旧端重建基线与导入保护被验证后才讨论压缩。备份保留期限单独管理。

## 5. 启用新删除能力的统一验收门槛

每个对象上线前按规范 §13 检查：删除范围与引用已列清；所有写入入口受权威校验；回收站、恢复、永久清理、同步及失败重试形成闭环；普通查询／检索／导出不再使用删除对象；旧设备和备份不能复活已清理 ID；UI 准确报告保留副本与部分完成。测试须覆盖 API、自定义 runner、V4 Vitest、桌面本地存储与真实页面状态；涉及 PostgreSQL 的结论以实际数据库测试为准，不能用 JSON 结果代替。

本文件是实施顺序与验收清单。规范 v1.0 仍为语义基准；若实施中发现规范与现有领域不变量冲突，先记录具体冲突并修订规范，再改变数据契约。
