# AI 基础架构与接入方案

状态：v0.1 技术设计草案。内置助手优先、统一适配层首接兼容 OpenAI API 服务已获用户确认；具体服务尚未选择。

## 1. 总体结构

```text
V4 助手 / 选区操作 / 知识审核 / 出题界面
                    ↓ 同源 API
AI HTTP：配置状态、会话、任务、预览、执行、取消、事件
                    ↓
应用编排：范围授权 → 上下文 → 模型调用 → 结果校验 → 动作计划
            ↓                         ↓
ProviderGateway                  ToolExecutor
            ↓                         ↓
供应商适配器                  现有笔记/知识/训练领域服务
                                      ↓
                              JSON / SQLite / PostgreSQL

任务/动作/用量持久记录贯穿编排；检索提供来源；MCP 后续复用 ToolExecutor。
```

模型只生成文本、结构化建议或工具请求。读取哪些资料、是否获准、如何提交、能否重试及什么算完成，由服务端确定。无需把现有 HTTP API 直接全部暴露给模型。

## 2. 代码边界与建设位置

下表除“复用”行外均为建议新增路径，实施前按职责细化，不在本轮创建代码目录。

| 路径 | 职责 |
| --- | --- |
| `apps/api/src/modules/ai/http/` | 会话/任务/动作 API 与流式事件，遵循 `node:http` 和项目响应封装 |
| `apps/api/src/modules/ai/application/` | 有界工具循环、场景工作流、授权、预算、生命周期与恢复 |
| `apps/api/src/modules/ai/domain/` | AIJob、AIAction、权限与错误类型、状态转换及 schema |
| `apps/api/src/modules/ai/infrastructure/providers/` | 协议适配、超时取消、模型能力与错误归一化 |
| `apps/api/src/modules/ai/infrastructure/` | repository、运行租约、事件与用量存储；双驱动实现 |
| `apps/api/src/modules/retrieval/` | 后续切片、索引、召回及引用定位；P1 先复用现有搜索 |
| `packages/web-core/src/ai/` | 共享 DTO、API 客户端、纯状态工具；无 React/DOM/CSS |
| `apps/web-v4/src/features/ai/` | 助手、来源卡、动作预览、任务记录、配置界面 |
| `apps/desktop-runtime/src/` | 活动资料集 AI 服务、SQLite 持久化、路由及能力声明 |
| `apps/desktop-shell/src/` | 受限凭据 IPC、退出时任务处理；凭据不进入 renderer |
| 复用 `modules/knowledge/application/` | 笔记、知识、目标、题目和生命周期；AI 不另写一套规则 |
| 复用 `app.factory.js` / `postgres-app.factory.js` | 装配依赖；不引入一套未使用的 NestJS 启动框架 |

AI 基础不是单个巨大服务。按上下文构建、任务编排、动作执行、供应商适配拆分，保持可独立测试。

## 3. 提供商接入与配置

### 3.1 接入协议

首期交付一个经验证的兼容 OpenAI API 适配器。`baseUrl + apiKey + model` 并不足以证明兼容：Chat Completions、Responses、工具调用、流式事件和 JSON Schema 支持需分别探测。

建议首接兼容服务普遍提供的 Chat Completions 协议；若选定服务仅支持或更适合 Responses，则实现对应 adapter。业务模块仅依赖统一 gateway，不依赖某协议返回结构。不得因“兼容”二字静默切换 API 或模型。

gateway 最小职责：`generate`（文本/结构化）、`runWithTools` 所需的单轮消息转换、`capabilities`、`estimateUsage` 和 `cancel`。工具循环在 Knowra 应用层，适配器不能自己执行领域写入。未来 `embed`、图像输入、语音转写独立声明能力。

OpenAI 官方将工具调用用于连接外部能力，将结构化输出用于约束结果形态；函数请求仍需应用执行。Knowra 据此分离“模型请求”与“业务执行”。[官方工具调用文档](https://developers.openai.com/api/docs/guides/function-calling)

结构化输出不替代领域校验，并非所有模型或兼容服务支持相同 JSON Schema 子集。拒答、截断与格式失败必须有独立处理。[官方结构化输出文档](https://developers.openai.com/api/docs/guides/structured-outputs)

### 3.2 配置与凭据

配置分为非敏感配置和凭据引用：

- 非敏感：供应商 ID、协议、可信端点、模型 ID、能力声明、超时/预算、可用场景、配置版本。
- 敏感：API key，由服务器受保护环境或桌面系统凭据存储读取；任务只保存 credential reference。
- UI：显示已配置/不可用/验证时间，支持替换、撤销和最小连接测试；不回显完整密钥。
- 首次连接测试使用无业务内容的小请求，显示可能费用；真实资料请求另受范围授权约束。
- 端点由用户/管理员配置，不能由模型生成；对外提供的服务禁止任意端点代理，校验重定向，避免把凭据发往其他主机。本地模型端点使用独立显式模式。

P0 已选定 DeepSeek `deepseek-flash` 作为首接探测目标，用户已有 API Key 并同意发送明确选择的笔记片段，日预算 10 元人民币；执行细则见 [AI-00-01](p0/AI-00-01-接入决策与能力探测.md)。凭据尚未在 Knowra 配置，供应商能力也未经真实调用。密钥不进入前端包、LocalStorage、普通业务表、同步 payload、导出包或日志。备份和换机展示“需要重新配置凭据”。

### 3.3 模型选择与版本

按场景定义配置槽：`assistant`、`extraction`、`questionGeneration`、`grading`；首期允许全部指向同一模型，避免过早多模型路由。每次任务记录实际模型、提供商、参数、提示词版本、schema 和检索版本。

模型选择依据中文/公式/代码表现、引用忠实度、工具参数准确性、延迟、费用和服务可达性。具体价格、上下文窗口及可用性在 P0 选择时核实，不在架构里写死过时型号。

默认不自动跨供应商降级，因为这可能改变数据接收方。已授权的同供应商候选模型也需满足场景能力与评测要求，切换要记录。

## 4. 有界执行与持久任务

### 4.1 两种工作流

- 交互式助手：意图 → 检索/读取 → 回答或动作建议；设轮数、检索次数、输出和时间预算。写操作串行，独立只读查询可有限并发。
- 结构化任务：知识提炼、出题、批改采用固定步骤和 schema，避免让模型随意跳过审核节点。

长流程由父任务组织若干子任务。各阶段有明确产物和继续条件，不保持一个数据库事务等待用户或模型。失败后从已验证检查点继续。

### 4.2 持久化与执行器

先采用数据库任务记录 + 应用内 worker，进程启动恢复未完成记录；不引入 Redis 作为首期硬依赖。服务器存在多进程时必须有原子领取和过期租约，不能让两个 worker 重复提交。

- PostgreSQL：事务化领取与状态 CAS，网络调用在领取事务提交后执行。
- JSON：沿用受控单写服务/存储锁约束，不新增多个无协调 writer；持久化运行标识与租约。具体部署拓扑在 P1 准入核实。
- SQLite：活动资料集内原子领取/提交，不在 renderer 操作任务数据库。
- 过期租约不能让旧 worker 的迟到结果提交，提交时校验 `attemptId` / lease generation。
- 无法判断供应商是否收到请求时记录 `deliveryUncertain`。供应商不支持幂等时，重试可能再次收费；应用保证产物不重复，不承诺外部调用恰好一次。

任务与动作状态详见 [数据契约](03-数据工具与权限契约.md)。生成成功只表示有效结果已保存；场景若定义包含候选入库，则结果和候选同事务提交后才完成该任务。

### 4.3 流式事件

首期建议使用 HTTP 请求创建任务，SSE 传递进度/文本片段，断开后按游标恢复；部署不支持时退回带退避的状态轮询。浏览器重连不新建任务。普通响应保持 `{ data }` / `{ error }`，SSE 明确自己的版本化事件结构，不混用。

保存权威终态和有限事件日志；增量文本为预览，最终以经过校验的持久结果为准。文案允许显示“运行中”，不编造没有依据的百分比。

## 5. 上下文、来源与检索

### 5.1 上下文构建

权限检查 → 解析实际资料集/空间 → 读取授权对象 → 绑定版本 → 排除不可用和超范围内容 → 预算 → 构造清单 → 请求模型。

预算覆盖系统指令、对话历史、工具描述、来源、预计工具结果和输出预留。长会话摘要是派生上下文，不是新的用户授权；不能把摘要里一句“用户同意”当作 grant。输入超限时分批或请求缩小范围，分批结果明确覆盖范围。

资料内容、外部网页、附件文字、引用和模型输出均是不可信数据。工具名、grant、目标空间与允许的动作由服务端控制；在检索内容中看到命令不能据此执行。

### 5.2 检索演进

| 阶段 | 方法 | 进入下一阶段的依据 |
| --- | --- | --- |
| R0 / P1 | 现有标题+正文关键词检索，目录/标签过滤，受限结果集和版本片段 | 固定问题集出现同义表达召回不足或大文档开销问题 |
| R1 / P7 | 标题层级切片、关键词索引；固定 chunk 与版本/范围映射 | 基于基线比较召回、引用准确和延迟 |
| R2 / P7 | 关键词 + embedding 混合检索，按需重排 | 只有比 R0/R1 实测更好且费用可接受才上线 |

切片须保留标题路径、版本、正文哈希、UTF-16 区间及附件引用，避免切断公式、代码块和表格。过滤权限/生命周期发生在召回前及最终读取时，不只在 UI 隐藏结果。

索引变化由持久事件/outbox 驱动，失败可重建；删除或授权撤销后立即停止结果使用，后台再清理索引。索引 key 含资料集、空间、实体版本与模型/切片版本。知识库中的已确认内容和笔记原文可共同检索，但来源类型和审核状态分别显示。

默认不把全库上传到供应商托管文件库。若以后采用托管检索，需新增外发清单、删除回执、存储费用和保留说明。

## 6. 桌面与云端

| 场景 | 读取与提交 | 模型调用 | 约束 |
| --- | --- | --- | --- |
| Web | 当前服务器的 JSON 或 PostgreSQL | 服务器凭据调用 | 仅能看到服务端已持久内容 |
| 桌面联网 | 当前 SQLite 资料集及本地业务服务 | 桌面运行服务调用远程 API | 使用本机凭据；正式产物进入既有待同步队列 |
| 桌面断网 | 本地阅读与手动编辑正常 | 远程模型不可用 | 可保留请求草稿；恢复网络后再确认使用何版本，不默认补发 |
| 桌面本地模型（后续） | 同桌面 | 明确配置的本地端点 | 模型能力/资源占用分别验收，不能因为本地运行就默认授予全库 |

首期 AIJob、会话、租约和幂等 ledger 属于执行端，不作为普通业务实体双向同步。业务产物同步其必要来源信息，但不传播密钥、完整对话或另一个设备应执行的任务。

一个业务产物不能只依赖不可访问的本地 jobId：随产物保留独立来源摘要和不可变证据引用。当前同步 schema 不含新增 AI 元数据，P1/P3 必须做能力协商和版本升级，旧云端缺能力时保留本地待传并明确提示。

桌面训练目前只读下行。P4 可先在 Web 发布生成候选；桌面按钮应解释限制。P5 全端训练前必须补齐目标/题目/快照/作答的写入、关联同步、冲突恢复，不得简单放开路由白名单。

## 7. 外部 MCP

P2 起工具层保持与入口无关，P7 再提供 MCP adapter。先实现本机受控连接，远程开放另设认证与部署准入。MCP 提供工具发现、输入 schema 和结构化结果；协议本身不能代替 Knowra 的领域授权。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

- 本机 stdio/回环连接通过受保护配对配置绑定资料集和范围；禁止裸露回环 HTTP 即视为可信。
- 远程 HTTP 接入采用所锁定 MCP 版本的授权机制，并落实用户/客户端到 owner 与空间的映射、token audience、过期和撤销。现有 `KNOWRA_OWNER_ID` 是单 owner 边界，Nginx Basic Auth 也不是完整的外部客户端授权体系。[MCP Authorization 规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- 外部模型只能拿到已授权工具；确认 token 由受信 UI/用户流程产生，不把“确认”工具无条件交给模型自行调用。
- 首期不提供原始 SQL、任意文件/网络访问、批量永久删除或“设置审核为 confirmed”等通用入口。
- 工具失败保留稳定错误码；相同动作 idempotency key 查询同一结果，不能用重连当作再次执行依据。

引用的 MCP 2025-11-25 是本草案审阅的版本，不宣称是最新版本。P7 锁定 SDK/协议前再核实目标客户端支持情况。

## 8. 预算、可观测性与运行控制

初始工程限额建议（均为待评测调整的配置，不是已存在限制）：每会话同时运行 1 个任务、每运行最多 8 轮模型调用、12 次只读工具请求；单动作计划最多 20 个笔记变更。知识提炼仍遵守已有 v1 上限，其他场景独立设限。

基础调用建议 60 秒超时、结构化长任务 180 秒；网络/429/可恢复 5xx 最多额外重试 2 次，退避并遵守供应商限制；参数/授权错误不自动重试。多步骤总时长另设上限。实际数值在 P1 评测后冻结。

费用按任务预留、实际用量结算、失败/取消释放未用预留；未知用量记录 unknown，不写成 0。无可靠本地 tokenizer 时使用保守估计并尊重服务端上限。日预算和单任务金额须在真实调用前配置。

操作日志保存 ID、状态、耗时、用量、模型和错误码，默认不保存全文。指标包括成功率、重试率、引用校验失败、冲突拦截、成本及用户采纳率。后台健康探测不持续收费；管理员可关闭提供商、场景或全部 AI 写入。

## 9. 官方资料与项目决策的区别

外部文档用于核对协议，不决定 Knowra 的权限、候选审核、同步或产品范围。上文的单 worker、有界循环、默认限额、接入顺序及不自动跨供应商降级是本项目设计建议。官方资料核查日期为 2026-09-24，实施时锁定依赖版本后再验证。
