# AI-00-03：运行契约与迁移设计冻结

状态：P0 v1 契约与迁移设计已冻结，2026-09-26。**这不是已执行的数据库迁移或 AI 运行能力。** P1 的 repository、worker、迁移执行、真实存储和页面验收仍按任务表实施。

机器可读产物：[运行对象 schema](contracts/ai-v1.schema.json)、[模型工具调用 schema](contracts/tool-calls-v1.schema.json)、[SQLite v3→v4 DDL 草案](contracts/sqlite-v4-migration.sql)。本文件约束这三份产物的语义；JSON Schema 只能检查形状，不能代替权限、引用、状态转换或事务校验。

## 1. 执行边界与版本

| 记录 | 权威生成者 | 保存位置 | 同步/导出 |
| --- | --- | --- | --- |
| `ScopeSnapshot` | 服务端/桌面本地服务按用户选择和不可变版本构造 | 执行端保存不可变范围、排除和哈希，供 grant/manifest 共同引用 | 不进业务同步；默认导出仅安全元数据 |
| `ContextManifest` | 服务端/桌面本地服务按 grant 和不可变版本构造 | 执行端保存不可变 manifest 与哈希，供 job 引用；实际待发送片段单独限期保存 | 不进业务同步；默认导出仅安全元数据 |
| `AIGrant` | 受信用户请求或审核 UI | 执行端 | 不同步；备份恢复后旧 epoch 失效 |
| `AIJob`、`AIJobAttempt`、事件、用量 | 执行端 worker | 执行端 | 不同步，不由另一端重放请求 |
| `AIAction` | 应用服务依据已校验计划建立 | 与业务事务同一存储边界 | ledger 本身不同步；业务回执可回读 |
| `AIArtifactProvenance` | 业务提交事务 | 与正式产物同一权威存储 | 最小摘要随产物同步；不依赖远端存在原 job |

`contractVersion=1` 锁定字段、枚举、上限与状态语义。新增可选字段需要消费者显式升级；改变含义、删除字段或扩大发送范围必须升至 v2。当前知识提炼 `KNOWLEDGE_EXTRACTION_CONTRACT_VERSION=1` 保持独立，不因本契约自动开放提炼路由。

`ownerId`、`actorId`、`datasetId`、`datasetEpoch`、`spaceId`、`grantId`、`requestId`、`operationId`、`credentialRef`、`createdAt` 和哈希均由可信端填入；模型工具调用只允许 schema 中的 `tool` 与 `arguments`。任何模型输出中的 owner、授权、审核、目标 URL、数据库集合或真实操作回执一律丢弃并记为非法参数。所有 ID 在执行时重新解析，不把 schema 合法视作对象存在或有权访问。

## 2. 范围、授权与工具 v1

`ScopeSnapshot` 固定资料集 epoch、空间、允许读取的来源版本/范围、目录 ID 与排除项；`scopeHash` 对去掉哈希字段的 RFC 8785 JCS 规范化 JSON 的 UTF-8 字节计算 SHA-256。`ContextManifest` 再绑定本次实际发送的来源片段、排除/遗漏、接收方和 payload 哈希；job 的 `manifestHash` 对完整 manifest 的相同规范化字节计算 SHA-256，`payloadHash` 对实际发送的 UTF-8 字节计算 SHA-256。两者必须先于 job 持久化，job/grant 通过外键引用，运行时重读并核对 owner、epoch、空间及哈希。`sourceRef` 使用 UTF-16 左闭右开偏移；`quoteHash` 是所选原文的哈希，不能代替重新从 `NoteVersion` 逐字核对。manifest 的 `sources` 只包含本次发送的来源，必须是 snapshot 允许范围的子集；只阅读但不发送的上下文不放入 `sources`。`scopeKind=empty` 仅用于不引用既有笔记的新建指令，发送来源须为空。v1 `attachmentIds` 必须为空。目录在任务创建时固定展开；之后新增笔记不进入旧 job。知识对象范围需要 P3 的快照能力，schema 预留枚举不代表当前可用。

`AIGrant` 绑定 actor、入口、epoch、空间、不可变 `scopeSnapshotId + scopeHash`、允许工具与动作类别、目标上限、到期和撤销时刻；manifest 与 job 分别引用该快照及 manifest ID，运行时重新加载并比对哈希。普通只读请求只生成只读 grant；新建/追加只有用户明确的动作指令才可授权直接提交；改写和整理只允许生成计划，审核凭据由可信 UI 产生并绑定 `planHash` 与基线。grant、模型建议和工具参数都不能绕过现有只读/恢复/同步冲突保护。

工具 v1 的八个名称是 `notes_search`、`notes_read`、`folders_list`、`tags_list`、`notes_create`、`notes_append`、`notes_propose_patch`、`notes_propose_organize`。P1 只开放前两个；P2 在服务端 action ledger、CAS 和预览通过后逐个开放其余工具。`notes_create` 的 ID、`notes_append` 的版本基线与 `operationId` 均由服务端确定；模型提供的锚点/偏移必须与原文复核。`actions_approve`、正式确认、永久清理、任意网络/SQL 不在模型工具目录。

整理方案中的 `folderOperation=keep/root/move` 与 `tagsOperation=keep/replace` 明确区分“不改变”和“清空”；`move` 必须带目标 `folderId`，其余情况必须为 `null`。`keep` 时 `tagIds` 必须为空；`replace` 的空数组表示移除所有标签。这些条件由服务端作跨字段校验，不能仅靠 JSON Schema 的字段类型推断。

## 3. 任务、动作与来源不变量

1. Job 唯一键：`ownerId + datasetId + spaceId + jobKind + idempotencyKey`。同键同 `inputHash` 返回同 job；同键不同输入返回 409。`inputHash` 覆盖请求、实际选区快照、scope/grant 版本、模型配置、prompt/schema 和参数。
2. Job 仅允许 `pending→running`、`running→succeeded/failed`、`failed→retrying→running` 以及可取消态 `→cancelling→cancelled`。终态不可退回；显式重新生成用新幂等键。`phase` 不代表权威状态。
3. attempt 领取必须原子推进 `leaseGeneration`。生成调用在领取事务提交后发生。结果接纳时比较 attempt、lease、dataset epoch、grant、取消状态和唯一 `outputHash`；旧 attempt 的迟到结果不能覆盖先接纳结果。`deliveryUncertain=true` 时重试可能再次收费，不得把 usage 写成 0。
4. Action 唯一键：`ownerId + datasetId + operationId`；同 ID 不同 `planHash` 拒绝。状态从 `planned/awaitingApproval` 经 `authorized→applying→applied`，或走拒绝/取消/过期/冲突/失败；仅回执和实际业务事务均提交后显示 `applied`。网络丢失时先查询 operation 回执，不生成新 action 重试追加。
5. Action 提交事务内复核 grant、资料集 epoch、目标生命周期、`planHash`、目标版本/正文哈希与当前草稿保护，并同事务提交业务对象、必要版本/关联、provenance、action 回执和同步 outbox。PostgreSQL 事务内禁止文件/网络 IO。失败整体回滚。
6. Provenance 不含密钥、完整 prompt、完整模型输出或用户未选原文。同步目标可凭 `artifactId + sourceRefs + input/outputHash + provider/model/prompt/schema` 自独立解释来源；不能只指向本机 jobId。来源删除、裁剪、迁移需先检查正式产物引用。

以上转换和跨字段约束由 P1 应用服务实现并测试，**当前 JSON Schema 不执行它们**。特别是 `end > start`、`quoteHash` 对应的逐字原文、grant 未过期及单次事务均须运行时校验。

## 4. 存储与迁移实施设计

| 存储 | P1 落地方式 | 原子与恢复条件 |
| --- | --- | --- |
| JSON 服务器 | 在同一原子 `dataStore.runTransaction()` 边界增加执行端 scope/manifest 与 AI 集合；业务快照/同步导出显式过滤私有 scope、manifest、job、grant、attempt、事件、用量。正式 provenance 进入业务集合。 | 仅单写 API 进程；多 worker/多实例上线前改用跨进程领取。旧文件缺 AI 集合按空集合升级，不修改笔记。恢复后生成新 `datasetEpoch`，旧租约不得恢复写权。 |
| PostgreSQL 服务器 | P1 增量 migration 建 `ai_scope_snapshots/context_manifests/grants/jobs/attempts/actions/usage/events` 与计费账户+北京日的**权威预算**表；正式 provenance 与产物绑定。对唯一键、状态、租约建约束和索引。 | 领取、预算预留、业务提交、ledger/outbox 各用短事务和 CAS；网络调用在事务外。真实数据库迁移/并发/回滚验收因当前服务器内存条件暂缓，不把 DDL 设计写成已验证。 |
| SQLite 桌面 | 从 `PRAGMA user_version=3` 升到 4：先 `VACUUM INTO` 保护备份，再 `BEGIN IMMEDIATE` 执行 DDL、写入新 `metadata.aiRuntimeEpoch` UUID、设置版本并提交。AI 私有表与现有业务 `entities`/`sync_outbox` 共库。正式 provenance 作为显式版本化业务实体进入 `entities`。 | 迁移失败不启用 AI，原库与备份保留；旧 v1/v2 先沿现有路径到 v3。活动资料集恢复后刷新 epoch，旧 attempt/grant 只能只读诊断。实体同步协议与备份/救援导出须另行升级。 |

JSON 和 PostgreSQL 是服务器的两种驱动；SQLite 是桌面第三种存储，不能把某一驱动的测试当作另外两种通过。当前 `LOCAL_DATA_SCHEMA_VERSION=5`、SQLite `user_version=3`、同步协议 v1 均**没有**在本 P0 任务中修改。P1 应以显式迁移和版本协商升级，旧客户端遇到不理解的 provenance 保留待传，不丢字段。

**10 元/日是同一计费账户跨 Web 和 Mac 的总硬上限**，不能按设备、资料集或 owner 各给 10 元。预算权威以 `billingAccountRef + 北京日期` 为键，使用人民币微元整数（1 元 = 1,000,000 微元），单任务所有 attempt 合计最多预留 2,000,000 微元，原子检查“已花 + 已预留 + 新预留 ≤ 10,000,000”。Mac 可直接调用 DeepSeek，但先须取得服务器权威预留；若预算服务不可达，即使 DeepSeek 可达也拒绝付费生成。SQLite 仅记录本地用量/未知量，不作为总预算权威。当前预算服务未实现，因此所有生成入口继续关闭。

## 5. P1 实施顺序与验收移交

1. 基于此 schema 生成运行时校验器和 DTO，拒绝未知字段；增加 hash/状态/权限/引文的跨字段测试。
2. 实施 JSON、PostgreSQL、SQLite repository 和迁移；先在隔离库迁移、回滚与恢复，再接真实资料。对旧快照、未知未来版本和半迁移文件明确拒绝或保守恢复。
3. 完成权威预算和凭据引用、资料集 epoch、受控工具执行，再开启任何真实生成调用。
4. 分别验证三种存储的重启、并发领取、丢响应、取消/迟到结果、重复 action、来源删除、同步旧端及隐私导出；真实 PostgreSQL 暂缓项不得标为通过。

本任务已冻结**设计输入**；没有写业务库、启动 worker、开放工具或向 DeepSeek 发送资料。
