# 总体方案与决策记录

状态：v0.2；P0 的 AI-00-01/02 决策与基线已记录，功能尚未实施。2026-09-24。本文的“建议”“拟新增”均不表示已实现。

## 1. 产品目标

AI 是贯穿 Knowra 的横向助手，帮助用户完成以下闭环：

```text
记录、导入与阅读笔记
→ 形成可追溯的知识候选
→ 用户确认知识与可评测的学习目标
→ 生成、审核题目及组卷
→ 用户作答
→ 规则或 AI 批改，必要时复核
→ 形成有效学习证据
→ 更新掌握状态与安排复习
→ 回到原文、修订理解、再次训练
```

同时支持独立的笔记助手：用户可以只使用问答、摘要、整理和记录，不必先建立知识库或考试配置。

长期允许两类入口共用能力：Knowra 内置助手，以及通过 MCP 使用笔记与知识工具的外部 AI。接入模型只是基础之一；工具执行、版本、授权、来源和恢复必须由 Knowra 掌握。

## 3. 产品边界

### 3.1 必须保留的领域规则

- 笔记、知识点、学习目标、考试考点是不同对象。AI 摘要不能自动当作正式知识。
- AI 生成知识和目标进入候选，人工确认后才能进入正式出题范围；个人解释不得被重跑结果覆盖。
- 题目长期入库确认与一次练习采用分开。未经人工审题的临时 AI 题必须标识，仍需结构、答案和来源检查，并保存当次快照。
- 批改结果经采纳后形成学习证据，再由规则更新目标掌握状态。AI 不直接修改掌握度。
- 提示使用、参考答案曝光、自评与独立作答分别记录。学习报告不能把未测、失败或待复核当作能力低下。
- 来源、题目和用户答案采用稳定快照。历史成绩不随当前笔记或题库修改而漂移。
- 检索索引可重建，知识图谱是正式关系的投影，两者均不是新的正式数据真源。
- 模型调用在数据库事务之外；写入遵守领域服务、存储恢复和同步协议。

### 3.2 首个可用版本

首发范围为 P0–P2：基础接入、受控笔记助手与完整的读写反馈。

支持当前笔记/选区问答、跨笔记检索摘要、新建笔记、追加内容和有预览的局部改写；提供来源跳转、取消、操作记录和版本恢复。同步暂停时仍可使用本地笔记，但远程模型需要网络。

首发不依赖向量数据库、知识图谱、自动学习计划、后台巡查或多代理编排，也不要求所有模型同时接入。AI 故障不能阻断原有手动操作。

### 3.3 分阶段产品成果

| 成果 | 阶段 | 用户能实际完成 |
| --- | --- | --- |
| 笔记助手 | P0–P2 | 问自己的笔记，将讨论写成笔记并安全整理 |
| 知识整理助手 | P3 | 从所选资料提炼候选、核对来源、确认知识与目标 |
| 出题助手 | P4 | 根据已确认目标生成、审阅和保存题目 |
| 可用训练闭环 | P5–P6 | 生成试卷、作答、批改复核、查看有依据的掌握和复习建议 |
| 跨库与外部扩展 | P7 | 语义检索、关系建议、外部 MCP、多模态及按需自动化 |

P7 中 MCP 可以在 P2 后独立推进，关系建议依赖 P3，检索在有质量瓶颈时加入，不要求等待整个训练闭环完成。

## 5. 优先级与取舍

1. 先验证“读对范围、写对对象、失败可恢复”，再提高自主程度。
2. 笔记助手先提供日常价值，知识提炼复用现有契约；训练闭环先补正式领域模型，再挂 AI。
3. 首版使用单个有界工具循环及确定的工作流。复杂任务按阶段检查点继续，不通过无限循环或多个自由代理掩盖流程不清。
4. 不为接入 AI 推翻现有 `node:http`、V4、JSON/SQLite/PostgreSQL 架构；不因依赖中存在 BullMQ 就要求部署 Redis。
5. 生成结果结构正确、引用存在、语义可信是三项不同检查。后两者不能由一个“校验通过”标签混淆。

## 6. 规划风险

| 风险 | 对计划的影响 | 处理 |
| --- | --- | --- |
| 模型工具调用或结构化输出兼容性不足 | 不能承诺同一 API 地址即支持所有工作流 | 首接供应商做能力探测和契约测试，缺能力则禁用对应功能 |
| 已有正文草稿与 AI 写入竞争 | 覆盖或反复冲突 | 显式输入版本、提交时 CAS、草稿预览与合并 |
| 本地任务与云端重复执行 | 双份候选或题目 | 任务单端执行，业务产物幂等；不把同步事件当成再次调用模型的触发器 |
| 训练基础不足 | 出题演示看似完整但无法持久作答 | P5/P6 明列非 AI 前置任务，分开验收 |
| 来源与隐私副本增加 | 删除后残留任务输入、索引或供应商副本 | 产物来源可追踪，纳入清除范围；不宣称本地删除会撤回已发出的数据 |
| 质量或成本不稳定 | 功能能运行但不适合日常使用 | 固定评测集、运行预算、可关闭的能力开关与模型版本回退 |
