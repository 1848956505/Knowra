## 2. 核心记录 v1

集合名 `knowledgeArtifactProvenance`；每个 KnowledgeItem 至多一条，独占归该产物。记录 ID 为 `provenance-` 加 SHA-256(JSON.stringify(["knowledgeItem", artifactId]))。原记录不依赖 AIJob、私有任务或凭据外键。

共同字段严格为 `id/schemaVersion/state/artifactKind/artifactId/provenanceHash`，其中 `schemaVersion=1`、`artifactKind="knowledgeItem"`。`state` 为以下判别联合：

| state | 额外允许字段 | 含义 |
| --- | --- | --- |
| `recorded` | `executionMode/provider/modelId/promptVersion/resultSchemaVersion/origin/inputHash/outputHash/committedAt/sources` | 已保存的原生成事实 |
| `legacy-unavailable` | `reason="origin-record-unavailable"` | 旧数据确实缺少可校验来源元数据；不是生成记录 |

recorded 仅允许 `executionMode="mock"`、`provider="mock"`。旧 AIJob 的 provider=deepseek 是旧配置字段，不代表真实提供商。modelId、promptVersion 和 resultSchemaVersion 复制原合法 receipt，不强制旧 02A 记录等同 02B 固定 profile。

`origin` 严格为 `jobId/requestId/scopeId/spaceId/receiptHash`。其中 spaceId 是生成时空间，属于历史身份，不作为当前空间 FK；迁移笔记后不改写它。当前访问权限依据当前产物/Evidence/Note 的宿主边界判断。原 job/request/scope ID 仅作追溯标识，不是执行、授权或同步任务。

每条 `sources` 严格为：

```text
evidenceId / sourceId / noteId / originNoteVersionId / contentHash
start / end / quoteText / quoteHash
annotationRevisions: [{ annotationId, revision }]
```

sources 为 1–8 条，保持原引用顺序；evidenceId 对应原 candidateInput.evidence 同序项。quoteText 是该引用的精确原摘录，最多 8,000 UTF-16 单元，保留首尾空白；start/end 为绝对 UTF-16 左闭右开区间，不能切断代理对。现有 Evidence DTO 会 trim，故明确核对 `Evidence.quoteText === quoteText.trim()`，不反推丢失的空白位置。

标识符非空、无首尾空白/控制字符、最多 200 字符；SHA-256 为 64 位小写十六进制；revision 为正安全整数，start/end 为合法安全整数，时间为可解析 ISO 时间。同一候选内 evidenceId 及 (sourceId,start,end) 复合身份不重复；同 sourceId 可有不同摘录。每条来源的 annotationId 不重复，所有层级拒绝未知字段。完整记录 JSON UTF-8 上限 1 MiB，先查字节数再深入校验；超限整条拒绝，不截断。

不复制完整 receipt/request/result、request.sources.markdown、未引用片段、私有 task/grant/attempt/lease/manifest、对话、预算或凭据。诊断日志不打印 quoteText 或完整记录。

## 3. 哈希与版本 alias

`provenanceHash = SHA256("knowra:knowledge-artifact-provenance:v1\n" + canonicalJson(recordWithoutHash))`；前缀末尾为实际 LF（U+000A，以上以\n转义表示），不是反斜杠和字母 n。canonicalJson 递归按对象键排序，数组保留原顺序。该哈希证明记录一致性，不是密码学来源真实性证明。核心合同不能导入加载 AI schema/运行时的模块。

原 inputHash/outputHash/receiptHash、request、result、AnalysisScope 及其 hash 不变。当前知识正文、个人解释、审核/归档状态、来源派生健康和同步 revision 不进入来源摘要哈希。

复用稳定 Evidence 作为可校验 alias 桥：

1. 摘要保存 originNoteVersionId，不因同步改名。
2. 通过 evidenceId 解析当前 Evidence.noteVersionId；Evidence 必须属于同 artifactId 和 noteId。
3. 当前版本必须属于同 noteId，contentHash 相同，且 `content.slice(start,end) === quoteText`；Evidence 的摘录等于 trim 后原 quote。
4. 原版本 ID 与解析版本不同才返回 `aliasUsed=true`。不同 note 即使 hash 相同也不能合并；同 ID 不同 hash 拒绝。
5. 核心只读投影可返回 originalVersionId/resolvedVersionId/aliasUsed/sourceState，这些派生字段不写回摘要。

不新增通用 alias 表，不复活远端不存在或已墓碑化的原版本 ID。同步依赖沿摘要 → Evidence → 当前实际 NoteVersion 解析。

不可变 AnalysisScope 仍保存原 ID/inputHash。仅当原 ID 缺失时，核心关联验证以同 noteId、同实际 contentHash 且全部保存 segments/contextSegments 的 UTF-16 切片完全一致解析保留版本；原 ID 存在但身份不符直接拒绝。同步依赖和裁剪预览使用该已验证版本，不改 scope。需要重新执行提炼时原 ID 缺失仍明确停止，要求重新保存范围；不将历史 alias 自动变成新的执行授权。

## 4. 旧数据、回填与不可变性

旧 schema1–6 无摘要字段可增量迁移。合法 receipt 仅为仍存在的产物回填 recorded；保留用户当前标题、解释、确认、归档、sourceMode 和软删除状态。purge 产物、Evidence 或相关墓碑不能从 receipt 重建。空候选结果不产生摘要。

既有 sourceMode=ai 但没有合法可回填 receipt 的产物迁移成 legacy-unavailable；它不虚构 provider、版本、hash 或精确位置。坏/未知的新版摘要绝不能降级成 legacy 或清空。坏旧可选 receipt 保留并隔离，不使普通知识全面不可用。

新 Mock 接纳仅生成 recorded。schema7 中 AI 产物必须显式带已记录或旧来源缺失记录；不能用省略集合冒充旧资产。已有 recorded 的产物即使以后改 sourceMode 仍保留摘要。普通业务快照 import 不能把目标库同 ID 的 recorded 降级为 missing/legacy；同步下行同样保护已存事实。此要求不等同于现有整库 SQLite restore 已完成跨活动库比较：整库替换的来源/已知删除事实门禁归 05C，当前备份检查只验证被检查备份自身。

recorded 相同 ID 同 hash 幂等，异 hash 拒绝；禁止普通更新、降级或独立删除。legacy 可经严格 receipt 回填升级成 recorded；同步领域校验只允许合法的单向升级，不允许 recorded→legacy。两种记录均只能随合法产物 purge 同事务删除并保留既有删除事实：JSON/PG journal 墓碑，SQLite 原子 outbox 删除记录；本批不新增 SQLite 独立权威墓碑或整库恢复防复活。

## 5. 原子存储与保留

JSON：集合进入本地 schema；候选/Evidence/摘要/首 receipt/AI 终态/journal 同一 runTransaction，最终原子替换失败全部回滚。

SQLite：核心 entities 保存摘要，与候选/Evidence/首 receipt/AI 终态/sync_outbox 同一 BEGIN IMMEDIATE。回填只将 sync_base 中 value=null 且 server_revision 为正安全整数视作删除事实；旧 reset 的 null revision 仅表示缺席，非空非法 revision 拒绝加载。升级保护原库，不将本地业务 schema7 与 AI PRAGMA user_version=7 混为一谈。备份只读预检读取 metadata.localDataSchemaVersion，真实旧库缺失时按6验证兼容投影；未知/损坏标记及7中缺失/损坏摘要拒绝，不写回备份。

PostgreSQL：增量模型/迁移/repository/mapper；同一当前连接与核心同步锁事务。覆盖 sync provider、batch apply、JSON migration plan/db maps、snapshot exporter。原 receipt TEXT 不改为重排 JSONB。当前工厂外层隔离级别是 ReadCommitted，不宣称内层设置能将其提升。

核心读取、知识 purge、版本裁剪预览、附件引用预检覆盖摘要。archive/trash/restore/withdraw 只改变当前适用性，不改原事实。知识进入回收站仍允许在当前 owner 校验后读取原摘要；recorded 的来源投影为 unavailable，legacy-unavailable 仍如实显示缺失说明。只有产物真正不存在（或权限不符）才返回404，不以软删除隐藏历史来源。来源 Note 更新标 stale；软删除标不可用。现有 Note 受 Evidence/QuestionSource/AnalysisScope 引用的永久清理门禁保持，版本 canPruneNow 仍 false。

产物 purge 将摘要列为独占附属记录，与 item/Evidence 同事务清理。历史完整 receipt 独立保留，不据它自动恢复产物，也不把整个 request 所有临时内容永久钉住。附件扫描只加入摘要的必要 exact quoteText。

## 6. 同步 schema7 与统一协商

本批明确采用不向后同步兼容的整体升级策略：`LOCAL_DATA_SCHEMA_VERSION=7`，能力 `knowledge-provenance-v1`。保持离线阅读、编辑和未确认 outbox；不承诺旧端普通笔记仍能同步，不发版或打 tag。

所有实体数据入口要求 `entitySchemaVersion=7`，且 capabilities 包含 `atomic-entities-v2/knowledge-items-v1/asset-lifecycle-v1/knowledge-provenance-v1`。缺少、未知 schema 或不支持能力返回明确升级/不支持错误，不能静默去字段。

为减少两套解析，协议入参固定为：

- status 只读公布 schema、支持/必需 capabilities。
- bootstrap POST JSON 正文包含上述 schema/capabilities。
- batch 维持 protocolVersion=2，在 envelope 加 schema/capabilities。
- changes/snapshot GET query 使用 entitySchemaVersion=7 和逗号分隔 capabilities，规范化为无重复排序集合。
- /push protocolVersion=1 同样要求 schema7 和完整 capability 协商，无协商旧端明确拒绝，不能绕过 batch。仅允许已能完整收发 schema7 的新版客户端提交受限笔记操作；旧 notes-only 接收模式拒绝连接，不虚报完整来源能力。
- operation-receipt GET 在同一 schema7 协商与 epoch 下，按 deviceId/operationId/requestHash 只读查询升级前已冻结请求；没有回执且序号已被使用时保留未知提交并暂停，不盲发。
- blobs POST 也要求 schema7/capability，附件临时传输不放松门禁。
- snapshot-release 只释放已创建快照，不回传业务数据；device 只读序号不授予写权限。

| 客户端 / 服务端 | push | pull/bootstrap/snapshot |
| --- | --- | --- |
| 旧 / 旧 | 维持原行为 | 维持原行为 |
| 新 / 旧或缺能力 | 握手即暂停，完整原子组待传 | 不建立降级基线，不丢本地来源 |
| 旧或无协商 / 新 | 服务端拒绝，含 legacy /push | 服务端明确拒绝，不等下载后才失败 |
| 新 / 新 | 校验与接纳完整关联组后 ack | 整事务/固定快照通过后才推进 cursor |
| 未来未知 schema | 不 ack | 不应用，不清 pending |

journal 中 snapshot 绑定 `snapshotId/ownerId/datasetEpoch/entitySchemaVersion/capabilities/cursor/count`；每页返回并复核相同绑定。PG snapshotPage 的优化读取也必须遵循同样门禁，不能绕开 service 校验。旧无协商 snapshot 不续用，释放后重建。

产物/Evidence/摘要必须同一原子组，item 的反向依赖包含全部 Evidence 与摘要；sources 的版本依赖经 Evidence 解析。分组超限整体待处理，不先上传候选。失败不推进 cursor/device sequence、不删除未确认 outbox。

持久旧 operation/requestHash 不原地改内容并重用 operationId；先按既有回执和只读回读解决未知提交。未确认旧事务不能当作从未提交重编号盲发；旧冻结请求所在 epoch 已改变时先暂停，不能先 bootstrap 清除原封装。
