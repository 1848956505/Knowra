## 已批准范围

领域冻结稿定义学习目标为可观察、可训练和可评测的能力。沿用既有八个动作词和四个认知层级，以及服务端的含糊描述、动作/层级兼容性和父知识确认规则。人工保存与明确确认分开：保存只产生候选；确认后才成为可被训练资产使用的正式目标。修改已确认目标后保持既有目标与题目失效链路。

知识详情显示真实关联目标及其候选、已确认、归档和回收站状态；读取失败与没有目标分开。对已确认知识提供人工创建和逐项审阅入口；目标文字、动作和认知层级使用可复用表单，训练工作台复用同一表单，不再固定写入 `explain/understand`。目标与父知识必须来自用户实际审阅的版本，不能用提交前自动刷新代替重新审阅。

训练资产写权限保持原有能力边界。Web 连接且可写时开放操作；桌面本地、缓存只读和未连接状态不因知识可编辑而取得目标写权限。所有验证仅使用合成资料，不调用 provider。

## 审阅基线合同

新界面在创建候选时提交 `reviewBaseline: { knowledgeUpdatedAt }`；编辑及确认时提交 `reviewBaseline: { objectiveUpdatedAt, knowledgeUpdatedAt }`。带基线请求必须提交完整、合法的 UTC 毫秒时间（`Date.toISOString()` 格式）；缺失、空值、非法日期或非规范格式返回 `400 LEARNING_OBJECTIVE_BASELINE_INVALID`。服务端在写入事务中重读目标及父知识，可用记录的任一版本不同返回 `409 LEARNING_OBJECTIVE_UPDATE_CONFLICT`，不覆盖或确认现行资产；记录已不存在、归档或删除时保持既有 `404` 存在性语义。新界面保留人工草稿并提示重新核对。

已有未带基线的 API 调用继续兼容，不将其描述为已获得用户审阅版本保护。该小批不迁移全体训练资产的 revision，也不新增同步 schema 或资金权限。目标更新时间须单调递增；JSON/SQLite 的同步事务和 PostgreSQL 的行锁/CAS 分别保护校验与提交。题目失效应与目标变更处于同一业务事务，事务中不包含外部文件或网络 IO。

## 验收门禁

- 创建“能够计算一步更新”并选择 `calculate/apply`：保存候选时正式目标数量不变，明确确认后增加，刷新仍显示完整字段。
- 知识切换、迟到读取、读失败和只读能力不串目标、不冒充空列表、不开放写入。
- 空目标、含糊描述和不兼容组合不能确认；失败保留人工输入。
- 审阅后目标或父知识变化，旧基线编辑/确认拒绝且不改现行数据；正常变更继续使关联题目待复核。
