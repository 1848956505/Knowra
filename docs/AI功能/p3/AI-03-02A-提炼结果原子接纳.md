# AI-03-02A 提炼结果原子接纳

状态：2026-10-02，已有提炼任务的 Mock 接纳基础完成本地 JSON/SQLite 合成验收，PostgreSQL 场景已注册，等待真实隔离数据库 CI 核实。固定 head 独立审查和各次 CI 状态以关联 PR 为准。正式提炼仍未开放，AI-03-01、AI-03-02 的完整产品链路及整个 P3 均未完成。

## 本批次解决的问题

01A 只得到候选计划；宿主若逐个保存，再更新 AIJob，途中失败会留下部分候选，重试还可能覆盖用户已经编辑的结果。本批次提供受信宿主的 `knowledgeExtractionCommit.commit({ jobId, attemptId, scopeId, result })`，整批保存首次完整结果、全部候选、证据、精确 provenance、已接纳 attempt 和 succeeded 任务。HTTP/IPC 未注册此入口，没有模型调用或凭据读取。

输入仅接受标明 `provider: mock` 的完整 Gateway 响应。Mock 是执行模式，旧任务中的 provider/modelId 只是请求配置元数据；提交记录明确保存 `executionMode: mock`，不能把模拟验收记成真实 DeepSeek 已验收。真实 provider 接纳、核价、预算、发送前复核和执行调度须在后续 worker 连接中补齐。

## 保持冻结 v1 的方式

现有 AIJob v1 的 `jobKind` 已包含 `knowledgeExtraction`，但可选 `resultJson` 只接受问答 `{answer,citations}`。本批次继续使用其任务/授权/租约/CAS 元数据，提炼任务不写这个问答字段，也不改冻结 schema。成功任务保存 `acceptedAttemptId/outputHash`，完整提炼结果保存在独立核心提交记录 v1，业务资产和记录共用同一权威存储；不依赖 AI 私有表的外键或清理生命周期。

核心记录保存 owner、datasetId/epoch、space、job/attempt/scope/request ID、输入/输出哈希、模型/提示词/结果契约版本、提交时间、服务端原请求、完整已验证结果与候选计划。精确来源含旧 NoteVersion、正文哈希、绝对 UTF-16 偏移和原标注修订。记录采用严格白名单与整份 receiptHash，未知字段、损坏记录或未知扩展版本关闭此接纳入口，保留原记录及普通笔记操作。

提炼 v1 的 128 片段、120,000 UTF-16 输入、40 候选、每候选 1–8 个引文及 256,000 UTF-8 输出限制保留；Gateway 封装后限制也保留。现有 grant 的 create 权限和 maxTargets 上限 20 同时生效，因此本批次最多接纳 20 个且不超过本次实际授权数。超过授权整批拒绝，不截取前 20 个，不默认为所有通过结构校验的候选都有创建权限。

## 同事务复核与提交

1. 从宿主仓库读取任务；核实 owner、当前 dataset/epoch、jobKind 和契约版本。成功记录仅在同 attempt/scope/inputHash/outputHash 下复用；另一份模型正文返回冲突，绝不覆盖首次记录。
2. 首次接纳要求 running 任务、当前最高 leaseGeneration、sent attempt、未结束且未过期的租约；取消/结束/旧 attempt 的迟到结果拒绝。grant 必须来自 analysisScope、具有 create 权限、无工具、未撤销或过期，并与 manifest/范围边界完全一致。
3. 从服务端仓库加载保存的 AnalysisScope、所属空间及不可变版本；空间 owner 不匹配、快照删除、笔记删除或迁移均拒绝。重新生成请求，核对 requestId/inputHash、全部 SourceRef 和实际封装 payloadHash，不能采用客户端自报的范围或版本正文。
4. 整批通过 01A Gateway 终态与 v1 严格引文校验后，再交已有候选领域服务。首次提交遇到任何已存在的同 ID 候选也拒绝；证据冲突、墓碑和领域校验仍生效。当前正文变化沿用旧版本及 `stale` 证据，绝不换成当前版本或自动确认。
5. 保存全部候选/证据、独立核心提交记录、validated attempt、succeeded job；提交末尾再次复核有效期。任何失败全部回滚，调用方后续 worker 才负责失败状态与诊断调度，此入口不把失败伪装成完成。

相同已提交结果重试直接返回首次回执，不再次调用候选创建或修改服务。用户修订、归档或软删除的候选保持原状；回执中的初始计划是历史事实，不代表资产当前标题或状态。JSON 插入时严格验证并复制回执，读取时也复制，调用方修改返回对象不能污染内部记录或阻断后续普通编辑。

## 三种驱动与迁移

| 驱动 | 原子边界与增量存储 |
| --- | --- |
| JSON | 新顶层 `knowledgeExtractionCommits: {version:1,receipts:[]}`；缺省按空扩展加载，旧文件第一次事务原子写入。与业务集合、aiRuntime 和同步 journal 共用 `dataStore.runTransaction()`；磁盘替换失败恢复所有内存集合和记录。损坏扩展保留原文，不能当成空集合覆盖。 |
| SQLite | 新核心表 `knowledge_extraction_commits` 和独立 `metadata.knowledgeExtractionCommitsVersion=1`；不改 AI `user_version=7`。升级前 `VACUUM INTO` 并设 0600 保护备份，DDL 和版本标记同事务；未标记已有表、未知版本或损坏记录拒绝覆盖。记录、AI 表、entities 与 sync_outbox 同库同 `BEGIN IMMEDIATE`。 |
| PostgreSQL | 增量 migration `h_knowledge_extraction_commits` 增加 owner/dataset/job 唯一核心记录表，不修改 Prisma 业务模型或冻结 AI 表。`receipt_json TEXT` 保留完整 JSON 字段顺序，回读显式解析并严格校验；冻结提炼 v1 的 outputHash 依赖原序列，不能用 JSONB 重排或放宽哈希校验。接纳使用宿主短事务和既有核心 advisory 锁，锁住 epoch、job、grant；AI repository 绑定同一事务连接，候选/证据及同步 journal 随同提交。事务中没有提供商、文件或其他外部 IO。 |

普通业务快照/同步仍只带现有候选和证据；完整请求、模型原输出和精确 AI 元数据留在执行宿主提交扩展，未加入普通 entities 或公开响应。整库 JSON 文件/SQLite 备份会保留扩展，打开数据库时校验扩展。备份维护任务拥有 `backup.mjs`，本批次不修改其独立恢复流程；恢复预检的扩展 validator 接入、provenance 最小摘要同步、旧客户端版本协商和来源清理/裁剪保护仍属 AI-03-05，不能据本次原子保存宣称已完成。
