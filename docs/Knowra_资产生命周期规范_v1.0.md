## 0. 文档定位与评审结论

### 0.1 目标

本规范统一回答以下问题：一个资产何时应当归档、何时可以删除、何时能够永久清理；删除后如何处理来源、下游资产、历史记录、检索索引和设备副本；何种情况下允许恢复，以及如何防止已删除数据被旧设备重新写回。

核心决策为：

> **归档不代替删除，保留历史不等于永久保留全部内容。删除必须尊重用户意图，并在引用完整性、历史可解释性和同步一致性之间形成明确、可验收的边界。**

本文冻结产品语义、领域约束和验收要求，不规定完整接口路径、数据库表结构或具体同步算法，也不要求每一种对象都使用相同状态字段。

### 0.2 依据与证据边界

本规范参考现有《Knowra 知识与考卷系统领域冻结稿》、Phase2.0、Phase3.0 规划，以及项目开发规范。[D1][D2][D3][D4]

当前页面和 API 的能力描述以用户提供的 V4 代码审计摘录为依据；同步限制以用户粘贴的 `normalizeKnowledgeChange`、`validateKnowledgeBatch` 代码为依据。这些材料不是对最新仓库、生产数据库和所有客户端的完整复查。本文不据此断言所有引用关系、历史快照或清理机制已经实现。[U1][U2]

下文的新增状态、保留策略和清理流程均为本轮设计决策。对旧规则的调整在第 14 节列明，不将新建议伪装成现有实现。

### 0.3 对上一版讨论的修正

上一版“工作资产可删除、历史证据受保护、派生数据自动清理”的方向保留，但以下表述不得直接作为实现依据。

| 上一版不够严谨的表述 | 本规范采用的规则 |
| --- | --- |
| 有 `deletedAt` 字段，说明领域原本就完整支持删除 | 字段可能只是预留。是否支持删除，必须由状态转换、引用规则、持久化和同步协议共同确定。 |
| 历史证据不可普通删除，容易被理解为用户永远不能清除 | 不可篡改约束与保留期限分开。日常操作不得悄悄毁掉证据；用户仍可通过明确的历史清除或内容清除流程删除它。 |
| 取消重点后，关联 Evidence 一律失效 | 取消关注不等于否定证据。先判断历史版本和证据快照是否可独立复核；只有实际依赖受损时才降低证据健康状态。 |
| 有历史快照，就一定可以删原对象 | 快照必须足以独立展示、解释和使用，同时处理数据库硬引用、共享附件及仍在运行的任务。仅多存一个标题不够。 |
| 归档数据退出所有统计 | 默认工作范围可以排除归档资产；已经发生的考试、得分和学习历史不得因此被改写或无声消失。 |
| 回收站保留 30 天，之后全部删除 | 30 天只是恢复窗口的默认产品配置，不是无条件清理授权，更不是同步墓碑的保留期限。 |
| 来源消失或对象无人引用，就可认定为垃圾 | 必须区分独立资产、历史证据、真正的专属附属数据和派生缓存；“无下游引用”不意味着用户内容可以自动删除。 |
| 删除知识点时一起删来源和下游资产 | 只自动清理确属该对象且无其他用途的附属记录；笔记、其他知识点、学习目标、题目和训练历史不得被隐式连带删除。 |
| 永久删除就是执行一次数据库 DELETE | 产品还必须说明历史副本、文件、同步设备和备份的处置状态；数据库删除也不等于磁盘文件立即缩小。[E4] |

## 1. 通用语义

### 1.1 操作定义

| 操作 | 用户意图 | 内容与后续行为 |
| --- | --- | --- |
| 归档 `archive` | 暂不用于当前工作，但希望保留 | 保留资产；退出默认工作范围；允许查看历史和显式解除归档。 |
| 删除／移入回收站 `trash` | 不再需要，暂留恢复机会 | 保留恢复所需数据；从正常业务入口移除；不得接收新的正常业务绑定。 |
| 恢复 `restore` | 撤销回收站删除 | 在依赖仍可用、未进入不可逆清理时恢复；恢复不等于自动通过审核。 |
| 永久删除 `purge` | 不再允许通过普通恢复找回该对象 | 清理对象主体和明确纳入范围的附属数据；保留必要的最小删除事实；说明哪些历史副本仍保留。 |
| 移除来源／撤回 `retract` | 不再将某条来源用于当前知识确认 | 停止该证据关系的当前适用性，保留撤回记录；不等同于篡改摘录或删除原笔记。 |
| 历史记录清除 | 删除指定考试、作答或其他历史记录 | 经影响确认后清理所选历史包，并重新计算受影响的派生结果。 |
| 内容清除 | 还要清理系统内明确识别的相关内容副本 | 单独列出范围，处理历史快照、版本、附件和日志等；不得将仅删除主体冒充该操作。 |
| 垃圾回收 `GC` | 系统执行已获授权的安全清理 | 仅清理符合规则的派生数据、过期临时数据和专属无主记录，不擅自删除用户独立资产。 |

“永久删除”不是“此前所有地方出现过的相同文字都已消失”。该差异必须在确认界面和执行结果中明确呈现，详见第 10 节。

### 1.2 基本转换

```text
工作资产
  ├── 归档 ──解除归档──> 工作资产（重新校验）
  │     └── 移入回收站
  └── 移入回收站
          ├── 恢复 ──> 删除前的归档属性／工作属性（重新校验）
          └── 申请永久删除
                  ├── 引用或任务未处理：保持回收站状态，说明阻塞原因
                  └── 校验通过：进入不可逆清理
                            └── 主体清除，保留最小删除记录
```

归档不是删除的必经步骤。已归档对象也可以被删除。已永久清理对象不得通过普通恢复复活；用户明确重新创建时使用新的资产 ID。

### 1.3 状态维度不得混用

至少在语义上区分以下维度：

- **业务审核：** 例如 `candidate`、`confirmed`、`needsRevision`。
- **归档属性：** 是否退出默认工作范围。
- **删除属性：** 正常、回收站、不可逆清理中、已清除。
- **来源健康：** 例如 `valid`、`stale`、`invalid`、`insufficient`。
- **来源适用性：** 当前采用、已撤回或已被替代。
- **同步进度：** 本地已提交、待同步、权威端已确认、其他设备待处理。

这些是逻辑维度，不要求立即增加六组数据库字段。现有 `reviewStatus=archived` 可暂时兼容，但不能用它同时表示删除或证据失效；`retracted` 也不能未经领域迁移直接混入现有健康状态枚举。

删除状态优先于正常业务状态。例如，一个回收站中的 `confirmed` 知识点不能继续被用于新出题。来源恢复可达，也不能自动重新启用用户已经撤回的证据关系。

## 2. 资产分类与总矩阵

### 2.1 分类原则

分类按职责而不是按表名机械确定。同一对象可以既有“用户可管理”的一面，也有“被历史记录引用”的一面。

| 类别 | 典型对象 | 生命周期原则 |
| --- | --- | --- |
| 用户工作资产 | 笔记、标注、知识点、学习目标、题目、已保存分析范围 | 原则上允许删除；有引用时按规则处置，不永久剥夺删除能力。 |
| 来源与历史证据 | KnowledgeEvidence、NoteVersion、正式试卷快照、作答与批改、LearningEvidence | 留存期间不得随意覆盖；不随上游对象日常删除而消失；允许受控清除。 |
| 正式关系与配置 | KnowledgeRelation、ExamFocus、标签、考试配置 | 关系可以解除或删除，但不得误删两端资产；正式关系不是可任意重建的缓存。 |
| 容器与组织结构 | KnowledgeSpace、Folder、KnowledgeTopic、标签分组 | 区分删除容器与删除其中内容；非空操作必须明确迁移或批量删除范围。 |
| 可重建与临时数据 | 检索切片、向量索引、缓存、未保存 AI 预览 | 按依赖和保留策略自动清理；已被用户接纳的内容不再视为临时数据。 |
| 同步与运维元数据 | 删除墓碑、同步日志、清理任务、备份 | 有独立保留规则；既不能过早删除，也不能无限保留完整正文。 |

领域冻结稿将 RAG 索引定义为可重建派生数据，同时将知识关系列为正式数据；本规范延续该边界。[D1，§2.6—2.7]

### 2.2 资产操作矩阵

“受控”表示必须处理依赖、历史保留及同步条件，不表示当前实现已经支持。

| 资产 | 日常动作 | 恢复机制 | 永久清理方式 | 禁止的隐式影响 |
| --- | --- | --- | --- | --- |
| Note | 删除；归档可选 | 回收站 | 受控清理笔记及其专属内容 | 自动删除派生知识点、题目或训练历史 |
| ContentAnnotation／Annotation | 取消标注；归档可选 | 撤销与回收站 | 清理标注、无其他用途的修订记录 | 自动删除知识点或一概否定历史证据 |
| KnowledgeItem | 归档、删除 | 回收站 | 处置目标、关系和历史引用后清理 | 删除源笔记、其他知识点或历史作答 |
| KnowledgeEvidence | 移除来源、重新核验 | 显式重新采用并校验 | 来源历史清除、所属资产清理或安全 GC | 改写旧摘录、自动重启撤回来源 |
| NoteVersion | 查看、保留恢复点、清理无引用版本 | 清理前预览；删除后不普通恢复 | 引用保护下的版本裁剪或内容清除 | 删除唯一证据、当前版本或被占用版本 |
| 已保存 AnalysisScope | 删除 | 回收站 | 引用释放后清理 | 删除已独立保存的知识与题目 |
| 运行时 AnalysisScope | 取消、过期 | 通常不提供 | 任务结束后按临时数据策略清理 | 清理仍在使用的任务输入 |
| LearningObjective | 归档、删除 | 回收站 | 处理正式题目与学习历史引用后清理 | 自动删除题目或改写旧掌握记录 |
| ExamProfile | 归档、删除 | 回收站 | 处理 ExamFocus、蓝图和历史引用 | 隐式删除目标、考点、题目或试卷 |
| ExamFocus | 归档、删除 | 回收站 | 解除当前绑定并保护历史描述 | 删除其考试配置或学习目标 |
| Question | 归档、删除 | 回收站 | 历史快照独立且硬引用安全后清理 | 改变已发布试卷、答案、评分依据 |
| ExamBlueprint | 归档、删除 | 回收站 | 处理在用任务和历史配置引用 | 删除已生成试卷 |
| Exam | 归档、删除 | 回收站 | 处理 Attempt 与快照归属后清理 | 自动删除用户作答与批改 |
| Attempt 及所属 Response、GradeResult | 归档或删除整次记录 | 整次记录恢复并重新评估 | 清除明确选择的历史包 | 留下孤立答案、暗中保留掌握度贡献 |
| LearningEvidence | 撤回贡献、随历史处置 | 经校验恢复贡献 | 随对应历史清除或专门清除 | 继续参与已被撤回的掌握度估计 |
| MasteryState／派生复习安排 | 重算、暂停、重新生成 | 从有效证据重建 | 派生数据清理 | 当作唯一历史真源保留 |
| KnowledgeRelation | 解除关系、删除 | 撤销或随所属删除包恢复 | 清理关系本身 | 删除关系两端知识点 |
| KnowledgeSpace | 归档；删除需明确作用范围 | 容器与删除包恢复 | 迁移或清理选定内容后删除 | 因“删空间”而无提示抹去全部资产 |
| Folder／KnowledgeTopic | 删除容器、迁移或批量删除 | 按选择的删除包恢复 | 处置子容器和成员关系 | 将分类关系误当内容所有权 |
| 普通 Tag | 删除、合并 | 操作级撤销可选 | 删除标签及适用关系 | 删除被打标签的资产 |
| TagGroup | 删除空组、迁移标签或明确连同标签删除 | 撤销可选 | 清理分组／选定标签 | 删除笔记、知识点和题目 |
| 附件 | 解除引用、删除 | 随所属删除包 | 所有需要保留的引用释放后清理本体 | 删除其他资产或历史快照共用的文件 |
| Chunk／Embedding／KeywordIndex／Cache | 自动移出可用范围 | 按需重建 | 安全 GC | 删除对应的正式资产 |

内置标签和默认空间等系统对象可以限制“删除系统定义”，但不能因此让用户内容无法清空或迁移。系统外壳与用户数据必须分开处理。

## 3. 全局约束

### 3.1 默认业务范围与历史范围

归档对象默认退出日常工作列表、新的自动出题、默认知识图谱和默认 AI 检索；用户可主动进入归档范围查看。归档不代表内容错误，也不代表从已有历史记录中抹除。归档源笔记不等于删除源笔记，不应仅因归档就撤回已经成立的来源关系；新的默认检索范围与已有证据的可复核性分开判定。

回收站对象退出正常列表、一般检索、AI 上下文、新建引用和默认导出。回收站查看、恢复预览和维护诊断属于专门入口。

历史试卷和历史报告按当时的快照展示。知识点或题目被归档、删除，不得让既有得分和试卷内容悄悄变化。当前有效资产数量与历史学习统计必须分开计数。

旧索引尚未清理时，读取端也必须按权威生命周期状态过滤；不能只依靠异步清理最终完成后才隐藏已删除内容。

### 3.2 所有入口遵守相同规则

页面、API、本地应用服务、同步入口、导入、批处理及维护任务必须遵守同一生命周期约束。隐藏按钮不能替代领域校验。

服务端或承担权威职责的本地服务负责判定；客户端不得通过任意修改 `deletedAt`、`reviewStatus`、来源健康状态或版本号绕过校验。[D4]

### 3.3 不按审核状态推断删除安全

`candidate`、`draft` 或“从未进入试卷”不是无引用证明。草稿仍可能被另一个草稿、运行中任务、分析快照或用户操作记录引用。

另一方面，`confirmed` 也不是永久禁止删除的理由。引用可安全解除、快照可独立保留且用户明确授权时，正式资产可以清理。

### 3.4 不能自动删除用户独立资产

“长期未使用”“没有下游引用”“已归档”“来源已失效”都不能单独构成删除用户资产的授权。

自动清理只适用于用户已经删除并接受保留策略的对象、明确的临时数据、可重建派生数据，或能够证明没有独立保存意义的专属附属记录。

## 4. 引用与级联处理

### 4.1 必须区分五类关联

| 关联类型 | 示例 | 删除处置 |
| --- | --- | --- |
| 专属附属 | 标注修订、知识点专属辅助记录 | 若没有独立历史用途，可随主体进入清理范围。 |
| 独立业务引用 | 知识点与学习目标、题目与目标 | 不默认级联删除；需重新绑定、解除、转为不可用或另行明确删除。 |
| 历史引用 | 试卷引用当时题目和评分依据 | 以独立、完整的历史包保留；或用户明确选择清除历史包。 |
| 共享引用 | 多条来源共用 NoteVersion，多篇内容共用附件 | 只有所有保留用途解除后才能清理共享本体。 |
| 派生引用 | Embedding、检索切片、缓存 | 立即停止可用性；随后可靠清理或重建。 |

引用检查还必须覆盖运行中 AI 任务、待处理同步操作、恢复点以及保留策略锁定的记录。不能只统计页面能看到的几个关联数量。

### 4.2 允许的处置方式

永久删除前，对每项保留引用必须明确选择并落实以下方式之一：

1. **解除可选关系。** 关系本身可独立移除，且剩余对象仍满足领域约束。
2. **重新绑定。** 由用户确认语义正确的新对象；不得只为通过外键检查随意替换来源或目标。
3. **独立保留历史。** 确保历史数据不再要求原工作资产继续存在。
4. **显式组合删除。** 将相关对象逐项列入确认范围，整体校验，禁止隐藏扩展范围。
5. **暂时阻止。** 保持当前数据，返回具体依赖与可执行的处理路径，而不是永久只给出“有引用，不能删除”。

数据库层可以对已证明属于同一清理单元的专属记录使用级联能力，但不能让数据库级联替代业务决策。外键动作是否允许删除，仍需与领域规则一致。[E5]

### 4.3 历史快照的独立性

保留历史后删除原对象，至少需要满足：

- 保存历史展示和解释所需的题干、选项、答案／评分量规、分值、目标描述及版本信息；不要求保存与该历史无关的整篇原笔记。
- 历史界面、批改解释和必要复核不依赖已经删除的实时对象。
- 保留中的外键和非空约束已得到合法处置；不得制造悬空关系。
- 共用附件、公式资源及其他实际引用仍有明确归属与保留责任。
- 来源已删除的情况能明确展示；旧 ID 作为溯源信息保留时，不得继续被当作有效工作资产调用。

仅保存 `titleSnapshot` 或一段 `quoteText`，不能自动证明上述条件全部满足。历史快照和同步墓碑也不是同一种对象，不能互相冒充。

## 5. 笔记、标注与知识资产

### 5.1 重点标注：ContentAnnotation／Annotation

**“取消重点”的默认语义为移除这条标注，不是长期归档。** 操作立即撤去高亮，提供撤销，底层保留短期恢复机会。普通编辑界面不必再额外常驻一个“归档重点”按钮；确有保留历史标注的需求时，可放在次级管理入口。

取消重点不得修改笔记正文，不得自动删除由它产生的 KnowledgeItem，也不得自动删除 KnowledgeEvidence。[D1，§3.3；D2，§7.3]

证据处理分为两种情况：

- Evidence 已固定引用 NoteVersion，保存足够且可复核的摘录和定位信息：取消标注只影响“回到当前高亮”的能力，不自动否定证据。历史界面显示“原标注已移除”。
- Evidence 实际仍仅依赖该标注或其修订记录，删除后无法独立复核：暂停相关证据的当前使用，并按既有规则标记 `invalid` 或 `insufficient`；不得伪装为仍然有效。

用户明确认为原引用错误时，应执行“移除来源／撤回”，而不是靠取消重点推断用户否定了知识依据。

标注永久清理时可清理无其他用途的定位与修订记录。若 Evidence 仍依赖这些内容，应先将必要历史纳入独立证据包，或报告清理被阻止。恢复旧标注时必须重新核验正文位置；匹配失败则恢复为 `stale`，不能跳到看似相近但错误的文本。

### 5.2 笔记：Note

笔记沿用“移入回收站—恢复—受控永久删除”。进入回收站后，正文不进入普通阅读与默认 AI 检索；其标注在日常编辑入口不可用。为支持恢复，正文、版本和附件暂不物理清除。

父笔记回收站状态可以使附属标注暂时不可用，但不应无差别覆盖每个子对象原有的归档／删除状态。恢复笔记不应顺带复活此前已经单独删除的标注。

现有冻结稿明确规定：删除 Note 后，相关来源进入失效或来源不足状态。本规范保留该保守约束；历史版本仍被留存，不等于可以继续作为正常自动确认或出题的有效来源。[D1，§9；D2，§6.4—7.2]

笔记永久删除前必须处理被引用版本、共享附件、分析快照和在用任务。保留派生知识是默认方向，但不默认保留其“当前有充分来源”的结论。

需要保留历史时，应保留足以解释历史的最小证据包，并明确告诉用户哪些摘录或版本仍在。若当前实现只能靠保留原 Note／NoteVersion 主记录维持引用完整性，则继续阻止该部分物理清理，不得宣称原记录已彻底删除。

### 5.3 知识点：KnowledgeItem

知识点必须具备归档、回收站和受控永久删除三种能力。重复、错误、不需要的候选知识不应被强制永久归档。

删除知识点后：

- 来源笔记和原标注不删除。
- 它的当前知识图谱节点和相关边不进入默认图谱；边可暂时保留用于恢复。
- 依赖该知识点的学习目标停止接受新的正式使用；受影响题目不得在依赖不满足时继续参与新组卷。
- 不自动删除学习目标、题目、试卷或作答记录；已完成历史继续按快照显示。

永久清理时，专属 Evidence、关系记录和派生索引按归属处理；Evidence 若被历史引用，则先完成历史独立化或将相关历史纳入明确清理范围。任何共享来源正文和附件都不得仅因一个知识点被删而清除。

`LearningObjective.knowledgeItemId` 当前具有业务含义，不能为了删除 KnowledgeItem 而直接置空并留下仍被当作正式目标使用的记录。必须重新绑定、明确删除相关目标，或完成独立历史保存。[D1，§3.9]

恢复知识点只恢复资产存在性和原有归档属性，随后重新检查正文、来源与目标依赖。不能无条件从回收站直接返回可出题的 `confirmed` 状态。

### 5.4 知识来源：KnowledgeEvidence

Evidence 是带有历史摘录的来源关系，不是原笔记本体。保留期间，不得通过普通更新覆盖历史摘录、原始来源 ID 或版本 ID；纠正来源应创建新证据或新增明确的修订关系。[D2，§7.3]

“移除来源”应被定义为撤回该关系的当前适用性。来源技术上可达但用户已撤回，与来源已经无法复核，是两种不同情况。

撤回后必须重新评估知识点是否仍满足确认条件。若缺少必要依据，停止新的正式使用；不得自动改为 `sourceMode=manual` 来绕过确认。用户要改用人工声明时，必须显式完成该动作。

日常来源列表不必提供无保护的永久删除按钮，但必须有受控清除出口：

- 用户在来源历史管理中明确清除所选证据内容；
- 所属知识点永久删除，且该证据无其他保留用途；
- 真正的专属无主证据在完成完整引用检查后由 GC 清理；
- 用户执行范围明确的内容清除。

以上操作都不得自动删除对应原笔记，也不得悄悄删除其他知识点的来源。独立的历史保留理由必须具体、可见，不能笼统以“审计需要”无限期保留全部正文。

### 5.5 笔记版本：NoteVersion

NoteVersion 的不可变性指“保留期间不得覆盖其历史内容”，不等于“任何版本都不能删除”。[D2，§6.2]

第一版不要求在每条版本旁增加删除按钮，但应提供“清理无引用历史版本”的能力或维护入口。用户创建的保留点、当前必要版本、被来源／试卷／任务引用的版本，以及恢复必需的版本均受保护。

版本清理必须有预览，明确可清理和被保留的原因。未配置版本裁剪策略时不自动删除旧版本；不能将已有历史版本批量视为垃圾。

笔记永久删除不意味着所有版本必定能够立即清理。被引用版本必须先解除引用或纳入独立历史包；其内容仍保留时，应列入删除结果的“保留副本”。

版本生成频率与版本保留策略分开管理。应复用相同内容的版本，避免为了每一次重复保存制造额外副本；具体生成时机继续遵守版本模块的领域规则。[D2，§6.2]

### 5.6 分析范围：AnalysisScope

运行时 AnalysisScope 是一次任务输入，不默认变成长期资产；用户明确保存的分析范围才提供独立管理与删除能力。[D1，§3.4]

已保存范围采用回收站与受控清理。删除范围不删除已经独立保存的知识点、Evidence 或题目。

若任务审计、重试或正式资产仍依赖该范围快照，它就不是可立即清理的临时缓存。必须先保留必要任务／来源快照，或取消、结束相关任务并解除占用。仅凭其名称含“快照”或“临时”不能决定保留期限。

## 6. 训练资产与学习历史

本节规定未来训练工作域的目标行为，不表示 V4 占位页面已具备这些功能。[U1]

### 6.1 学习目标：LearningObjective

学习目标支持归档、删除和受控清理；草稿与正式目标都需要引用检查。

归档或删除目标后，不再接受新的正式出题与绑定，停止为其安排新的自动训练。已有题目不自动删除：如果移除该目标后仍有足够的有效目标，可重新校验后继续使用；如果不再满足题目约束，则标记为待处理或阻止新组卷。

永久删除目标前必须处理 QuestionObjective、ExamFocus、LearningEvidence 和当前 MasteryState 等关系。历史中应保留当时目标的身份与描述，或由用户明确清除相关历史；不能留下指向已不存在目标、仍被正常聚合的学习证据。

将目标重新绑定到其他知识点需要语义确认。目标含义实质变化时，不得把旧作答证据无条件算到新含义下；旧历史继续对应当时目标版本。

### 6.2 考试配置与考点：ExamProfile、ExamFocus

两者均支持归档、回收站和受控清理。

删除 ExamProfile 默认只表达删除该配置，不自动删除 ExamFocus、LearningObjective、Question 或 Exam。现有 Phase3.0 已明确禁止这种隐式连带删除。[D3，§5.2]

由于 ExamFocus 具有必需的 `examProfileId`，不能简单置空后继续作为正常考点存在。永久清理配置前，应将考点重新绑定到合适配置，或由用户明确选择分别删除相关考点；组合确认必须列出所选考点，不得隐藏在级联逻辑中。

删除 ExamFocus 仅解除考试语境中的侧重点，不删除通用学习目标。保留题目、蓝图或历史试卷中的当时配置描述；新组卷不得再使用已删除的配置或考点。

### 6.3 题目与蓝图：Question、ExamBlueprint

候选题、草稿题、正式题均允许进入回收站。垃圾候选无需永久归档，但仍不能绕过实际引用检查。

删除题库中的 Question 不得改变已发布试卷的题干、选项、答案、评分规则、分值及作答结果。这延续现有领域冻结稿对 `ExamQuestionSnapshot` 的要求。[D1，§3.15、§9]

只有历史快照已独立、相关硬引用已合法处理且在用任务已结束时，原题才可以被永久清理。快照机制尚未实现或不完整时，保留当前阻断，不得仅解除外键校验。

蓝图是组卷配置，不是试卷历史。删除蓝图不删除已生成 Exam；生成任务仍在使用蓝图时，应取消任务、等待结束，或确保任务已有独立输入快照。

### 6.4 正式试卷：Exam

归档试卷表示不再作为日常工作入口，已有历史继续可查。删除试卷默认移入回收站，不自动删除 Attempt、Response 或 GradeResult。

永久删除被 Attempt 引用的试卷时，必须先保证这些训练历史仍可独立展示题目、分值和评分依据，或者让用户明确选择同时清除有关训练记录。

没有完成历史独立化时，不能删除 Exam 后留下仍要求 `examId`、`questionSnapshotId` 存在的历史。历史快照有多个使用者时，不随任意一个入口删除而清除。

### 6.5 作答、批改与学习证据

用户必须能够清除自己的学习记录，不能将 Attempt、Response、GradeResult、LearningEvidence 永久锁定为只进不出。

默认删除单元为“一次训练记录”，包含该次 Attempt、所属答案与批改，以及对应学习证据的贡献处置。一般界面不提供随意删除一条底层 Response、却保留看似完整 Attempt 的操作。

正常纠正批改采用新结果或明确的更正记录，不覆盖历史而伪装为从未发生。删除整次历史则是另一条受控路径。

进入回收站时，该次训练对应的 LearningEvidence 暂停参与当前掌握度估计。永久清除时，清理对应证据或保留不含被清除正文的最小处置记录；不得继续让被删除记录影响当前 MasteryState。

掌握度和自动生成的复习安排必须从剩余有效学习证据重新评估。用户自行建立的学习计划不属于可直接丢弃的派生安排，不得随重算自动删除。不能简单减去一个分值，因为后续状态可能依赖证据顺序、时间和权重。重算尚未完成时显示“重新评估中”；没有有效证据时显示“证据不足／未评估”，不能沿用旧分数。[D1，§2.5、§3.18—3.20]

恢复训练记录时重新核验依赖并恢复适用的证据贡献，不重复累加；用户此前单独撤回或判为不适用的证据不得自动重新启用。

归档学习记录与删除学习记录不同：仅归档通常不撤销其已发生的学习贡献。历史报表是否包含回收站记录必须在报表口径中写明；已保存的历史报告若保留旧统计，应标示它是当时快照，而不是当前实时总数。

## 7. 容器、关系、标签与附件

### 7.1 知识空间：KnowledgeSpace

空间支持归档；删除空空间与删除非空空间分开处理。

非空空间至少提供两种明确路径：迁移资产后删除空容器，或把所选空间内容作为显式批量删除包移入回收站。确认范围包含可见内容、回收站内容、保留历史、附件与运行任务，不能只统计正常列表。

跨空间迁移必须保留 ID 语义与引用一致性，不能产生系统不支持的跨空间引用。当前不支持完整迁移时，明确禁用该选项，不做部分迁移后宣称成功。

归档／删除容器使其中资产在默认工作入口不可用，但不得批量覆盖其原有审核状态、独立归档状态和独立删除状态。恢复容器只恢复本次操作导致的可见性变化。

默认空间可以保留系统外壳，或在存在替代空间后允许删除。无论采用何种方式，都必须支持用户清空或迁移其自有内容。

### 7.2 文件夹与知识主题

Folder 与 KnowledgeTopic 默认属于组织结构，不等于内容所有权。

删除文件夹时，应明确选择“保留内容并移动到上级／指定位置”或“连同选定内容删除”。删除主题默认解除分类关系，不删除其中知识点。一个知识点属于多个主题时，更不得因删除一个主题而被清除。

### 7.3 标签和分组

删除普通标签，只删除标签定义及其成员关系，不删除任何被打标签的资产。合并标签时迁移关系并去重，删除事实仍需同步。

标签可以使用轻量撤销，而不必全部进入统一回收站；“界面直接删除”不代表同步系统可以不保留删除事件。撤销窗口内必须保留必要恢复材料；越过不可逆清理点后不再支持按原 ID 撤销，重新创建使用新 ID。

标签分组可保持现有“清空后删除”的保守模式；扩展时允许先迁移标签或明确连同所选标签删除。内置标签限制删除是保护系统定义，不是保护用户正文不被清除。[U1]

### 7.4 正式知识关系

KnowledgeRelation 是正式知识数据，不属于可随意丢弃的图谱缓存。[D1，§2.6—2.7、§3.8]

用户删除关系只删除边，不删除两端节点。知识点进入回收站时，相关边暂不显示，但可以保留用于恢复；永久清理该点时，可清理指向它的当前关系，同时保护其他节点与独立历史。

AI 尚未被用户采纳的关系建议可以按临时或候选数据策略丢弃；已确认或人工创建的关系必须按正式资产处理。

### 7.5 附件与共享文件

附件至少区分“从某个资产解除引用”和“删除文件本体”。主记录删除不证明文件无人使用。

文件本体只有在当前资产、回收站恢复包、保留版本、历史快照及任务均不再需要时才能物理清理。内容去重后的共享文件不得随其中一个引用者删除而清除。

附件清理失败不得恢复已经永久删除的业务对象。系统应保留可重试的清理任务，并停止正常访问该待清理内容；不能只在界面隐藏文件却保留无权限约束的直接下载入口。

## 8. 删除、恢复与清理流程

### 8.1 删除预检

删除预检必须检查权限和归属、对象当前状态、操作版本、活动引用、历史引用、共享资源、运行任务及同步能力。

预检结果至少区分：

- 可以立即进入回收站；
- 可以永久清理，且无额外历史保留；
- 可以清理主体，但将保留明确列出的历史副本；
- 需要用户先处理或确认的关联对象；
- 当前实现不支持安全处置，继续阻止并给出原因。

预览不是执行授权的永久凭证。用户确认后、实际写入前，必须重新检查状态和依赖；预览后新增引用时不得继续执行过期方案。

### 8.2 回收站提交

主体删除状态、必要的关系适用性变化和可恢复的删除事件应在同一可靠提交边界内保存。网络失败时不能只改页面状态而不持久化，也不能在本地提交成功但尚未同步时声称全端已删除。

一组关联删除应有可识别的删除包，使恢复能够区分“本次被删除的对象”和“此前已经被单独删除的对象”。

### 8.3 恢复

恢复要求对象仍有完整恢复材料，且没有越过不可逆清理点。

恢复到原空间、文件夹或目标失败时，应给出迁移位置选择，或明确阻止；不得伪造一个不存在的父级。恢复旧标注核对锚点，恢复知识核对来源，恢复题目核对目标与评分依据。

恢复归档资产后仍保持归档。解除归档是另一项动作，也需要重新检查正式使用资格。恢复不能通过直接改 `deletedAt=null` 来绕开这些规则。

### 8.4 永久清理

永久清理应有以下可观察阶段：

```text
等待确认／引用处置
→ 执行前复核
→ 提交不可逆删除事实，禁止正常恢复和新增引用
→ 清理主体及专属数据
→ 清理外部文件、索引、缓存和副本
→ 记录各清理目标的完成或待重试状态
```

提交不可逆删除事实与清理主体之间不能出现“主体已消失但系统没有任何删除记录”的窗口。具体事务或持久化任务实现可复用项目基础设施，不要求为此引入新架构。

数据库操作在本地事务／原子提交中组织；文件、对象存储或外部服务清理通过可靠任务重试，不放入长数据库事务。[D4]

对包含独立资产的组合删除，按确认范围整体检查最终引用状态；不依靠按数组顺序逐项删除碰巧成功。重复执行同一请求不得重复删错对象、重复恢复贡献或制造多份相互矛盾的结果。

### 8.5 运行中任务

AI 生成、组卷、批改、索引和导出任务需要检查输入资产是否仍可用。

资产删除后，任务应取消，或在合法快照与授权范围内结束；任务写回前再次检查生命周期。已经被永久清理的资产不得因迟到的 AI 响应、重试队列或索引重建而被重新创建。

## 9. 多端同步与删除墓碑

### 9.1 禁止无语义删除

同步中必须区分：该设备尚未加载对象、设备无权看到对象、对象被主动删除。同步范围内缺少一条记录，不能单独作为删除授权，也不能单独作为重新创建授权。

用户提供的同步代码拒绝知识对象 `value=null`，并拒绝 KnowledgeItem 的 `deletedAt` 变化。前者可以继续作为对不受控删除载荷的保护；后者应由明确的生命周期操作协议替代，而不是简单删除校验。[U2]

显式删除操作可以通过同步传递，但应携带操作类型、对象身份、预期版本和幂等标识，且由领域服务执行校验。受信任的服务端删除事件也需要能够被客户端应用；不能一面新增删除服务，一面仍被旧同步规则无条件拒绝。

### 9.2 权威顺序与冲突

采用云端中心协调的部署中，云端决定同步操作的权威顺序；本地版本与客户端时间不作为跨设备的最终裁决依据。纯本地模式由本地应用服务承担对应职责，后续接入同步时必须迁移删除事实。

最低冲突规则如下：

| 场景 | 处理规则 |
| --- | --- |
| 旧设备编辑已进入回收站的对象 | 不得顺带恢复；返回对象已删除，用户需先显式恢复。 |
| 旧设备上传已永久删除对象 | 拒绝旧身份重新创建，不以客户端更大的数字版本放行。 |
| 删除与编辑并发 | 检查预期版本；不满足时返回冲突。删除已被权威接受后，旧编辑不能恢复对象。 |
| 显式恢复后收到较早的删除操作 | 按权威因果／版本规则拒绝过期删除，不能用“删除永远优先”再次删掉。 |
| 重复删除请求 | 幂等返回已知结果；不扩大删除范围。 |
| 批次内同时删除主体与关系 | 校验完整操作意图和最终状态，保证引用一致性。 |
| 旧导出或备份被导入 | 不按原 ID 静默复活已清理对象；显式恢复旧数据时使用受控导入与新身份策略。 |

### 9.3 删除墓碑的内容

永久清理业务主体后，仍需保留同步能识别的最小删除事实，称为 Tombstone。它不是历史正文快照，也不是供用户恢复的回收站记录。

其逻辑信息通常包括对象类型、对象 ID、所属同步域、删除事件标识、权威删除版本／序号以及必要时间。不能在墓碑中长期保存标题、摘录、用户答案或完整原始对象。[E1]

来源曾经存在但已删除的历史展示，可以读取独立历史包；不能靠在墓碑里塞回全部正文来实现。删除空间或其他父容器时，不得顺带清除尚有同步责任的子资产墓碑；删除事实应能独立于已删除容器的主体记录继续存在。

### 9.4 墓碑保留与压缩

**回收站恢复窗口和墓碑保留周期完全独立。** 墓碑过早清除可能使离线设备错过删除通知；同步系统需要将保留策略与设备同步条件协调。[E1]

本规范的首版安全选择：保留最小墓碑，暂不按固定天数自动清除墓碑。后续只有在完整实现以下机制后才能压缩：

- 已纳入同步的有效副本及必要消费者，确认处理到安全的删除水位；
- 长期离线或被移除的设备不能拿过期状态直接写回，必须重新建立同步基线；
- 新设备、导入旧文件和恢复旧备份也不能绕过新的同步基线；
- 被压缩的删除信息仍由同步代次、失效游标、身份分配或其他机制保证不会造成旧资产复活；
- 墓碑清理不破坏尚未完成的文件／索引清理任务和必要历史说明。

安全水位不仅是“所有设备曾经在线”，而是“对应删除已经被处理，且旧副本以后不能无条件重新写入”。对删除历史的确认与检查点保护，是已有同步系统采用的设计思路；本文将其作为安全目标，不要求直接照搬其他数据库实现。[E2]

不必等所有设备上线后才能清理云端正文；只要删除事实被可靠保留，正文清理与离线通知可分开进行。但未上线设备的本地副本不能被宣称已经清除。

### 9.5 桌面端、网页版与导入

有同步能力的桌面端可以离线移入回收站并持久化待同步操作。首版跨设备永久删除应由权威端确认后推进；离线提交的永久删除请求显示“待确认／待同步”，而不是“已全端清除”。

设备首次接入、长时间离线回归以及恢复旧备份时，先处理删除边界再上传旧对象。过期客户端不能通过不理解新删除协议而绕过保护；必要时禁止其写入并提示升级或重建同步。

同步日志可以压缩，但不能在待同步期间提前抹去删除事实。内容清除时也不能为等待离线客户端而无限期保存日志中的旧正文；应转换成最小事件或要求旧客户端重新建立基线。

现有永久清除或数据库 purge 能否传播到其他副本取决于具体协议，不能想当然认为清除一个数据库就通知了所有设备。[E3]

## 10. 清除范围、留存与空间管理

### 10.1 对象永久删除与内容清除

普通永久删除默认清理所选对象主体及明确纳入范围的专属数据，但可能保留独立的历史证据或试卷快照。确认页面必须说明此事实。

内容清除用于用户希望进一步清理系统内可识别的相关副本。应盘点原正文、历史版本、来源摘录、试卷快照、任务输入输出、附件、同步日志、索引、缓存和可管理备份。

内容清除不是自动证明“所有改写、摘要、重新输入的同义文字都已找到”。无法可靠追踪的语义派生内容必须说明覆盖边界；不能自动删除其他独立资产，只因它可能表达相似知识。

保留历史与清除其中原文可能发生冲突。用户应在看到影响范围后选择保留快照、移除受影响的历史片段并明确标示，或清除整个历史包。不能静默改写历史使它看起来始终完整。

### 10.2 保留策略

以下为本规范的产品默认建议，不是当前系统已有配置，也不是统一适用于所有资产的强制期限。

| 数据 | 默认建议 | 清理约束 |
| --- | --- | --- |
| 新进入回收站的工作资产 | 恢复窗口建议为 30 天；自动到期清理须明确启用并告知 | 到期仍需引用、同步和任务校验；手动永久删除可以提前进行。 |
| 旧版本已有归档记录 | 保持现状，不自动转入回收站 | 不将旧 `archived` 批量解释为用户已同意删除。 |
| 正常归档资产 | 不按归档时长自动删除 | 除非用户另行明确设置适用范围与规则。 |
| 用户保留的训练历史 | 默认保留，允许用户主动删除 | 不以“历史证据”阻止用户清除。 |
| 无引用 NoteVersion | 首版默认仅提供清理预览；可配置裁剪策略 | 当前版本、保留点和被引用版本优先保护。 |
| 未保存且已结束任务的临时 AI 数据 | 建议采用短周期策略；示例默认 7 天 | 运行中、重试中或被正式资产使用的内容不适用。 |
| 可重建索引和缓存 | 不再适用时立即停止业务使用，随后清理 | 不必等待回收站窗口结束；恢复时可以重建。 |
| 共享附件 | 保留到所有应保留引用解除 | 不与某一个主体的期限简单绑定。 |
| 删除墓碑 | 首版不配置自动过期 | 未来按同步安全水位压缩，而非套用 30 天。 |
| 备份 | 单独配置并展示实际保留期限 | 不能在缺少配置或管理权限时宣称某日必定全部清除。 |

未启用自动清理时，应显示“保留至手动清理”，不能承诺 30 天后自动删除。已启用时，到期表示具备进入清理队列的时间条件，不保证清理在某一秒完成，也不越过引用阻塞。

回收站计时使用被权威服务接受的删除时间。设备本地时钟差异不能让内容提前永久清理。首次启用新保留策略不追溯清理旧数据，除非用户明确确认。

### 10.3 备份与离线副本

备份、离线设备和第三方服务各有边界。结果应区分“在线主体已清理”“索引或附件待重试”“离线设备待同步”“受保留策略管理的备份尚未到期”。

对无法立即按单条记录清除的备份，应限制日常访问、按已说明的周期轮换；恢复备份前必须重新应用删除事实，不能将已清理数据直接重新发布。

用户自行导出并保存在系统管理范围外的文件，不能承诺被远程删除。发送给第三方服务的内容也不能在没有真实能力与确认结果时宣称已清理。

本文的“永久删除”是应用与可管理存储范围内的对象清理，不是底层磁盘安全擦除认证。

### 10.4 空间观测与 GC

空间统计至少区分：正式正文、笔记历史版本、来源和试卷快照、附件、检索索引、临时任务数据、同步日志、备份。

没有测量前，不得认定向量、标注或知识点必然是最大占用来源。清理优先级由实际体积、增长速度、是否可重建和清理风险共同决定。

GC 应提供只读预览、小批量执行、引用复核、失败重试和结果记录。所谓“无主记录”必须确属没有保留用途的附属数据；不能因为某次查询失败就判为无主。

PostgreSQL 删除记录后，旧行版本的空间需要数据库维护机制回收利用，数据文件未必立即缩小。不要把每次业务删除与 `VACUUM FULL` 绑定；后者涉及强锁、重写与额外磁盘空间，应由独立运维策略决定。[E4]

## 11. 用户交互与结果表达

### 11.1 文案

界面应稳定使用“归档”“移入回收站”“恢复”“永久删除”“移除来源”等语义。不能把归档按钮命名为“永久删除”，也不能把保留历史摘录的来源撤回宣称为已清除内容。

“取消重点”可以保持现有简洁文案，但实际行为必须符合标注删除规则，并提供短期撤销或回收站恢复。

用户不需要理解 Evidence 表、外键或向量维度。确认信息优先展示真实资产和影响，不把全部实现对象逐项堆在弹窗里。

### 11.2 确认信息

低风险回收站删除可以立即执行并提供撤销。永久删除、批量删除、空间删除和历史清除必须明确展示：删除对象与数量、会保留的历史、会受影响的依赖、是否可恢复以及多端清理范围。

示例文案：

> 永久删除知识点“TCP 三次握手”？该知识点将无法恢复。2 条专属来源记录将清理；3 道题目的历史试卷快照仍保留。1 个学习目标尚需重新绑定，处理完成前不能永久删除。

以上数量是界面示例，必须由真实预检结果填充。

存在重要引用时，应提供“查看引用”“处理关联”或“返回回收站”的实际路径。不能用一个没有出口的错误提示永久替代删除能力。

### 11.3 结果与完成标准

结果至少区分：

| 结果状态 | 用户可理解的含义 |
| --- | --- |
| 已移入回收站 | 本端可靠保存了可恢复删除。 |
| 待同步／待权威确认 | 本地操作尚未获得跨设备权威确认。 |
| 清理被阻止 | 数据尚未被永久清除，存在明确依赖或权限问题。 |
| 主体已清理，附属清理中 | 主体不能恢复，文件或索引等仍待完成。 |
| 在线范围清理完成 | 所有明确纳入的在线目标已完成；仍单列离线设备和备份状态。 |
| 部分清理失败 | 列出失败范围并可重试，不声称全部成功。 |

“已收到请求”不是“已删除成功”。保留备份或历史快照时，不得展示“所有副本均已消失”。

## 12. 现有实现的改造约束

### 12.1 当前能力与目标能力分开

用户提供的 V4 审计表明，知识条目、重点标注、来源、学习目标和题目等对象多采用归档／恢复或来源停用；笔记、标签则已有不同程度的删除能力。该信息仅作为迁移起点，不作为本规范已落地的证据。[U1]

开发前应逐对象核对页面、API、领域服务、JSON／数据库存储、导入导出、同步和测试，形成能力表。不能仅在前端增加一个按钮。

### 12.2 同步校验改造

针对用户提供的代码，必须核对以下事项：[U2]

- 保留拒绝不受控 `value=null` 的能力，但为经过领域校验的明确删除事件建立合法传播路径。
- 将 `deletedAt` 的一律禁止变化，替换为对删除／恢复动作及预期版本的验证；不能改成任意载荷都可修改。
- 现有 Evidence 在校验中被 `continue` 跳过时，需要确认其他层确实禁止修改不可变来源内容。单凭注释或删除限制不能证明不可变性已实现。
- 删除来源、笔记、标注、知识点时，要重新检查受影响的知识与题目，不只检查此次载荷里直接更新的 KnowledgeItem。
- 确认门禁应基于规范化后的最终对象及其有效证据，而不是仅信任客户端提交的 `reviewStatus`。
- 批次创建、删除、恢复与证据调整必须验证最终状态；不得保留只支持“新增／更新但永远不支持删除”的隐藏假设。

本节为审查清单，不断言整个项目目前存在上述全部缺陷；DTO、实体、Repository 和其他同步层需要一并核对。

### 12.3 最小逻辑信息

实现应能表达删除时间、删除包、操作者或操作来源、预期版本、幂等标识、永久清理进度、引用阻塞原因及必要删除事实。

可复用既有字段和基础设施。不要为了生命周期统一，把所有小型关系、缓存和标签都强制变成同一个巨大状态机；也不要立即引入微服务、全量事件溯源或复杂分布式事务。

### 12.4 迁移安全

新增功能应以增量方式接入。已有 `archived` 保持原含义，不推断成用户曾经点击了删除；已有来源停用记录不能自动变成内容清除授权。

迁移前需要备份和只读预检，迁移后核验引用及各端兼容。旧客户端不能正确解释新删除状态时，限制其写入，避免其回传旧对象覆盖新规则。

历史数据缺少独立快照时，先标识受保护记录与阻塞原因；不能伪造快照，不能跳过校验，也不能用未知历史信息填补来源。

## 13. 验收标准

### 13.1 核心验收矩阵

下列用例是启用对应能力的最低要求。尚未开发的训练模块可随模块实现验收，但不得宣称已经覆盖。

| 编号 | 场景 | 必须结果 |
| --- | --- | --- |
| LC-01 | 正常知识点移入回收站 | 默认列表、图谱、新出题和默认检索不再使用；恢复入口仍存在。 |
| LC-02 | 已归档知识点被删除后恢复 | 保持原归档属性，不自动变为正式可用。 |
| LC-03 | 取消没有引用的重点标注 | 高亮移除、正文不变、可撤销或恢复。 |
| LC-04 | 取消具有独立版本证据的标注 | 不删知识点；显示原标注已移除，不无条件否定可复核证据。 |
| LC-05 | 删除 Evidence 唯一依赖的标注 | 来源降级并停止不满足条件的正式使用，不伪装有效。 |
| LC-06 | 用户移除某条来源 | 当前适用性撤回；后台健康重算不能将其自动重新采用。 |
| LC-07 | 删除来源笔记 | 保留知识点；依照现行规则处理来源失效／不足；正常检索不泄露回收站正文。 |
| LC-08 | 恢复笔记 | 不恢复此前被单独删除的标注；来源需重新核验。 |
| LC-09 | 恢复标注时正文已经变化 | 能重新定位则恢复，否则标为 stale，不跳错位置。 |
| LC-10 | 永久删除仍被引用的笔记版本 | 保留保护，列出具体依赖；不得破坏来源。 |
| LC-11 | 删除已保存分析范围 | 已独立保存的知识和题目仍存在；在用任务占用被正确处理。 |
| LC-12 | 删除知识点，仍有正式学习目标 | 无隐式级联；清理前重新绑定、独立历史化或显式处理相关目标。 |
| LC-13 | 删除候选题，但有其他草稿／任务引用 | 仍执行引用检查，不因 draft 状态直接硬删。 |
| LC-14 | 删除题库原题 | 历史试卷内容、答案、评分依据及附件不变。 |
| LC-15 | 删除目标后题目失去有效目标 | 不继续参与新组卷，不破坏历史试卷。 |
| LC-16 | 删除考试配置 | 不隐式删除 Focus、目标或题目；必需的配置引用得到合法处置。 |
| LC-17 | 删除一次训练记录 | 对应学习证据不再贡献当前掌握度，重算状态清晰。 |
| LC-18 | 恢复一次训练记录 | 证据贡献经校验恢复，不重复累计，不恢复已单独撤回贡献。 |
| LC-19 | 删除一个标签或知识关系 | 仅移除定义／关系，不删除对应正文或知识节点。 |
| LC-20 | 删除一个共享附件引用者 | 其他笔记与历史仍能访问文件；无保留引用后才清理本体。 |
| LC-21 | 非空空间删除与恢复 | 影响范围明确，恢复不复活此前独立删除的内容，不产生跨空间非法引用。 |
| LC-22 | 旧设备上传已经永久清除的对象 | 不按旧 ID 重新创建，不因客户端更大时间或版本放行。 |
| LC-23 | 回收站恢复后收到更早的删除请求 | 过期删除被拒绝，不再次删掉恢复后的对象。 |
| LC-24 | 长期离线设备错过墓碑保留窗口 | 被要求重建同步基线，不能直接推送旧状态。 |
| LC-25 | 导入含已删除原 ID 的旧文件 | 不静默复活；显式新建恢复使用合法的新身份或受控导入策略。 |
| LC-26 | 删除预览后有人新增引用 | 执行前复核发现变化，拒绝过期计划。 |
| LC-27 | 永久清理中断、进程崩溃或断网 | 删除事实可恢复、任务可重试，不产生部分正常可见的残留资产。 |
| LC-28 | 文件或索引清理失败 | 主体不复活；正常访问被阻止；结果明确为部分未完成。 |
| LC-29 | 删除请求被重复提交 | 返回幂等结果，不扩大删除范围。 |
| LC-30 | 清理期间出现新的绑定或 AI 回写 | 拒绝新增引用与旧内容写回。 |
| LC-31 | 自动回收站清理到期但仍有保护引用 | 保持受保护数据，展示阻塞；不越权清除。 |
| LC-32 | 首次启用新保留策略 | 不追溯删除旧归档或未经确认的旧数据。 |
| LC-33 | 执行内容清除但备份或设备离线 | 报告实际剩余范围，不宣称全副本已清除。 |
| LC-34 | 从旧备份恢复环境 | 对外提供数据和允许写入前重新应用删除事实／建立新基线。 |
| LC-35 | JSON 与 PostgreSQL 两条持久化路径 | 对同一操作得到一致的领域结果，失败不留下悬空引用。 |
| LC-36 | 非授权用户／客户端伪造生命周期字段 | 权威入口拒绝，不依靠按钮是否显示来保护数据。 |

### 13.2 上线门槛

任何对象开启永久删除前，必须同时满足：

1. 删除范围、引用关系和历史保留方式已经明确。
2. 所有支持的写入入口均执行生命周期校验。
3. 回收站、恢复、永久清理、同步和失败重试完成该对象的闭环测试。
4. 查询、检索、统计与导出不再把删除对象当作正常资产。
5. 备份恢复、旧客户端和旧导入不会无条件复活被清除对象。
6. UI 能准确表达保留副本、阻塞和部分完成状态。

只完成数据库 DELETE、API 返回成功或按钮接入，均不构成生命周期完成。

## 14. 与旧规则的关系

### 14.1 保留的领域不变量

继续遵守：标注不等于知识点；删除标注不自动删除知识点；知识来源保留期间不可任意覆盖；删除 Note 后处理来源失效／不足；正式试卷保存稳定快照；删除题目不改变历史试卷；掌握状态从学习证据形成；外部 I/O 不进入数据库长事务。[D1][D2][D4]

### 14.2 需要显式更新的规则

| 旧规则或旧表述 | 更新方式 |
| --- | --- |
| Phase2.0 知识条目仅归档／恢复，不做物理删除 | 以本文规定的回收站和受控永久清理扩展；改造完成前保持旧保护。 |
| 标注“取消重点”落地为归档 | 新操作按删除语义执行；既有归档数据不自动迁移为删除。 |
| 来源停用和来源技术失效共用含糊状态 | 在语义上区分适用性与健康；需要迁移时建立兼容映射。 |
| 所有知识同步删除均被拒绝 | 继续拒绝无语义载荷；增加经过领域校验的显式生命周期操作和权威事件传播。 |
| 有历史快照即可忽略源对象引用 | 补充快照完整性、外键处置、共享附件与在用任务检查。 |
| 删除 Profile 顺带删除 Focus | 继续禁止隐式级联；组合操作必须分别明确纳入相关资产并整体校验。 |
| NoteVersion 只能随整篇笔记清理 | 新增受引用保护的版本清理能力；不强制逐版本按钮。 |
| 历史资产永远不可删除 | 增加范围明确的历史记录清除和内容清除流程。 |

字段预留、旧阶段规划和新生命周期规则必须统一记录，不能让开发代理任选一个互相冲突的版本。

历史阶段文档可保留原阶段决策作为记录，在相应章节增加“后续由本规范扩展”的说明；不要重写成这些能力早已存在。领域冻结稿、开发规范、工程变更日志和实际代码契约应随实施同步更新。

## 15. 建议实施顺序

### 第一步：冻结语义和基础保护

确认归档／删除／来源撤回语义，建立实际引用清单，区分来源健康与适用性，明确删除事件和最低墓碑策略；补充领域测试。

本步骤不急于开放永久删除按钮，也不需要为尚未实现的训练历史搭建完整清理平台。

### 第二步：闭环当前常用资产

优先完成 Note、Annotation、KnowledgeItem、已保存 AnalysisScope 的回收站、恢复与同步闭环；保留来源和版本的引用保护。已有标签删除也要纳入删除事件传播与回归测试。

### 第三步：受控永久清理与空间管理

为已经完成生命周期闭环的对象增加清理预检、最小墓碑、附属文件与索引清理、版本清理预览和结果报告。

只对实际能安全处理的情况开放永久清理。有引用但尚未完成历史独立化的对象，继续给出可解释的阻断，不通过跳过校验来追求按钮齐全。

### 第四步：随训练模块实现历史清除

在 LearningObjective、Question、Exam、Attempt 等工作域落地时，一并实现快照独立性、历史包清除、LearningEvidence 贡献撤回与 MasteryState 重算。训练模块不能先把新实体一律做成永久只归档，再无限期推迟生命周期设计。

### 第五步：按真实数据规模优化

在已有空间统计和可靠同步基线后，再增加可配置的到期清理、版本裁剪与墓碑压缩。对个人项目，简单、可解释且可验证的方案优先于提前建设复杂通用平台。

## 16. 规范摘要

> 用户工作资产原则上可以删除；归档只表达保留而暂不用。历史证据在留存期间不得篡改，但应有受控清除出口。删除先处理当前可用性，再处理引用与历史，最后完成主体、附属内容及副本清理。任何清理均不得隐式毁掉独立资产，不得用历史保留掩盖实际残留，也不得让旧设备或旧备份静默复活已清理对象。

本规范的实施目标不是“每个列表都增加一个删除按钮”，而是让用户对自己数据的保留、恢复和清除拥有可理解、可执行且结果可信的控制。
