# Knowra 全项目工程质量审查方案

日期：2026-09-05。本文保存本次对话制定的完整审查方案，后续执行以阶段报告记录进度；本方案本身不代表已经完成代码审查。

最终需要回答四个问题：项目是否遵守现行规范、现有功能是否可靠、代码是否便于继续开发，以及部署和数据维护是否可控。

## 一、审查依据

主要依据为：

- [AGENTS.md](../../AGENTS.md)：当前命令、架构边界和数据约束。
- [开发规范](../开发规范.md)：分层、文件职责、前后端开发、跨平台及版本维护要求。
- [项目结构导航](../项目结构导航.md)：目录职责与代码定位约定。
- [V4 运行时与目录架构](../前端重构/V4/02-V4运行时与目录架构.md)：适用于当前阶段的前端架构约束。
- [领域冻结稿](<../知识库与试题模块/Knowra 知识与考卷系统领域冻结稿.md>)及各模块当前实施文档：业务对象、关系、状态流转与数据保护要求。

正式审查开始时，先建立“规范条款—适用模块—验证方式”清单，区分：

| 文档内容 | 审查处理 |
| --- | --- |
| 当前有效的强制约束 | 检查是否满足，偏离时给出证据 |
| 建议性约定 | 结合实际维护成本判断，允许合理例外 |
| 未来规划、尚未进入实施的功能 | 不直接认定为当前缺陷 |
| 历史设计、归档材料 | 用于理解背景，不自动作为验收标准 |
| 文档相互冲突或含义不清 | 单列“规范待澄清”，不擅自认定代码违规 |

例如，普通业务文件超过 250 行应触发职责复查；是否需要拆分，要看是否混杂职责，不能只凭行数判定。

## 二、审查范围与深度

整个仓库都纳入清点，但根据实际用途采用不同审查深度。

| 范围 | 审查重点 |
| --- | --- |
| `apps/web-v4` | 当前前端的组件、页面、状态、编辑器、样式、服务及开发和生产入口 |
| `apps/api` | HTTP、业务服务、持久化、文件操作、错误处理和应用装配 |
| `packages/*` | 共享契约、公共逻辑、依赖方向、跨端一致性 |
| `apps/web` | 遗留代码职责、回归价值、退役边界，以及是否影响当前运行和构建 |
| `prisma` | Schema、迁移、数据库约束、索引、兼容性 |
| `scripts`、`deploy`、`.github` | 开发工具、部署模板、CI、备份迁移和维护脚本 |
| 根配置与依赖清单 | workspace、构建、类型检查、环境变量、版本及依赖管理 |
| `docs` | 规范一致性、结构导航准确性、当前与历史内容的区分 |
| `storage` 及其他运行产物 | 管理边界、误提交风险、读写与恢复机制；使用隔离数据验证 |

依赖目录、生成文件、构建产物、截图等记录来源和用途，不逐行当作手写业务代码审查。归档 Demo 检查隔离和误引用风险。

所有自有源码模块都应有覆盖记录；关键写入、安全入口和跨层流程逐项深入检查。低风险重复内容可以采用规则扫描与代表性人工核验，但报告必须说明实际覆盖深度。

## 三、审查目标

| 目标 | 核心问题 | 主要验证方式 |
| --- | --- | --- |
| 1. 规范符合性 | 是否符合现行开发规范、架构边界、命名、样式和配置管理约定？ | 逐条对照规范、静态检查、人工阅读 |
| 2. 功能与业务正确性 | 当前已实现功能是否符合规则？边界输入、状态切换和前后端契约是否正确？ | 需求映射、调用链追踪、接口与页面验证 |
| 3. 健壮性 | 请求失败、重复操作、并发更新、缓存损坏、进程重启时是否可控？ | 异常场景测试、竞态复现、失败注入 |
| 4. 数据完整性与可恢复性 | 是否可能丢数据、留下部分成功、破坏引用？备份能否实际恢复？ | 事务审查、双驱动对照、恢复演练 |
| 5. 安全与隐私 | 输入、文件、内容渲染、访问边界和敏感信息是否受保护？ | 安全入口追踪、负面用例、依赖检查 |
| 6. 架构与可扩展性 | 增加一个功能是否需要修改大量无关模块？抽象是否合理？ | 依赖分析、代表性变更推演 |
| 7. 目录与可维护性 | 文件是否容易定位？职责是否清楚？是否存在重复实现和失效代码？ | 目录清点、引用分析、职责审查 |
| 8. 性能与资源使用 | 数据量增加后是否明显变慢？是否存在重复请求、全量扫描或资源泄漏？ | 代码分析、分档数据测试、运行测量 |
| 9. 测试有效性 | 测试是否真正执行、能否发现真实错误、是否覆盖关键失败路径？ | runner 核验、断言审查、关键场景验证 |
| 10. 交互可靠性与可访问性 | 加载、空态、错误、焦点、键盘操作、长内容和缩放是否可用？ | 浏览器状态验证、截图与键盘操作 |
| 11. 构建、部署与运维 | 能否重复构建、正确配置、定位故障、执行升级与回退？ | 隔离构建、配置检查、部署流程核验 |

功能正确性、数据完整性、安全性和测试有效性是补充重点：它们决定系统是否可信，也能防止审查过度集中在文件长短和目录外观上。

可扩展性按项目当前用途和明确的后续方向评估，不默认要求引入微服务、分布式锁或复杂设计模式。

## 四、Knowra 必查项目

以下是后续要验证的清单，不代表目前已发现问题。

### 1. 前端分层与状态

- V4 是否保持与 V3 的导入隔离。
- `react-aria-components` 是否经过项目 UI 包装层。
- `web-core` 是否保持框架、DOM、CSS 无关。
- 页面、业务动作、状态与数据访问职责是否清楚。
- 请求乱序、切换文稿、重复保存时，是否可能显示或覆盖错误的数据。
- 加载恢复期间的写入保护、失败回滚和编辑器状态同步是否有效。

### 2. 后端协议与业务边界

- 路由、应用服务、repository 是否各司其职。
- 请求校验、DTO、状态码和错误封装是否一致。
- 单 owner 边界是否由服务端控制。
- 当前部署保护是否符合单用户阶段约束；不能把 owner 字段当作身份认证。
- 正式资产的确认、失效、引用与删除规则是否在所有入口一致执行。

### 3. 持久化与文件可靠性

- JSON 原子替换、引用校验、事务失败后的恢复。
- PostgreSQL 事务、约束、条件更新及迁移兼容性。
- 两种驱动的业务结果、错误码和失败恢复是否一致。
- 附件路径、符号链接、上传中断、元数据与文件不一致等情况。
- 导入、导出、永久删除、迁移与普通写入并发时的行为。
- 数据备份与附件备份能否恢复为可启动、可读取的完整状态。

### 4. 工程与部署

- 端口发现、同源 `/api/*` 代理和环境配置。
- 开发及生产入口是否一致遵循当前 V4 边界。
- 跨平台路径、脚本和依赖安装是否可重复。
- CI 是否覆盖必要检查，是否存在失败被忽略的情况。
- 日志能否帮助定位故障，是否泄露正文、凭据等敏感信息。

## 五、执行顺序与阶段产出

分六个阶段推进，每阶段留下可独立查看的结果。

| 阶段 | 工作内容 | 阶段产出 |
| --- | --- | --- |
| 1. 确定基线 | 记录分支、提交、未提交改动、环境和文档适用范围 | 审查基线、规范清单、覆盖计划 |
| 2. 全仓结构与静态检查 | 清点模块、运行入口、依赖关系、职责分层、配置和重复实现 | 模块地图、规范符合性矩阵、候选问题 |
| 3. 分模块深入阅读 | 检查前端、后端、共享包、存储、脚本及测试实现 | 有定位和影响说明的问题记录 |
| 4. 跨层流程验证 | 从用户操作追踪到接口、持久化、返回及页面状态 | 关键业务流程验证记录 |
| 5. 专项验证 | 运行测试与构建，验证并发、恢复、安全、性能和兼容性 | 可复跑证据、测试结果、未验证项 |
| 6. 复核与汇总 | 排除误报、合并同源问题、确定优先级与整改顺序 | 总报告、问题清单、整改路线图 |

跨层验证至少覆盖：

- 创建与编辑 → 自动保存 → 重载或重启后读取。
- 查询、搜索、筛选、排序、分页及目录导航。
- 上传 → 引用 → 下载 → 删除。
- 软删除 → 恢复 → 永久删除。
- 导出 → 导入 → 数据与附件一致性。
- 当前已实现的知识、目标、题目及来源状态联动。
- 弱网、断网、接口失败、旧版本更新和重复提交。

每条关键流程至少验证正常路径、边界输入、失败路径，以及适用的并发和恢复路径。

## 六、测试与测量计划

现有检查入口作为基础：

```bash
npm run check:web:v4
npm run build:web
npm run test:api
npm run test:web-core
npm run test:web:legacy
npm run test:web
npm run test:scripts
npm run test:e2e -w @study-accelerator/web-v4
npm run prisma:validate
```

执行前核对各命令包含的检查，避免重复运行。API 测试通过项目 runner 执行，并记录实际执行数、跳过数和失败数。

补充验证：

- 双驱动验证：使用隔离 JSON 数据和隔离 PostgreSQL，执行相同关键场景；数据库迁移只在隔离环境演练。
- 浏览器验证：覆盖主要页面状态、键盘操作、长内容和缩放；平台未实际运行时，明确标注仅做静态检查。
- 性能验证：先记录环境和数据规模，再按日常、增长和压力三档数据测量耗时、内存、请求数及查询行为。
- 依赖验证：检查运行、开发和构建依赖；扫描结果结合版本、可达路径和实际影响复核。
- 失败恢复验证：模拟写入失败、附件缺失、损坏快照、冲突更新和中断后重启。

性能阈值若已有要求就按要求执行；若没有，先提出带环境与数据规模的验收基线。不能仅凭主观感觉判定“性能差”。

正式审查以检查和隔离验证为主，修复另行安排。测试数据、生成产物和复现脚本与真实运行数据分开管理。

## 七、目录结构评价标准

- 容易定位：从业务功能能否找到主要实现和测试入口。
- 职责集中：同一业务的主要规则是否集中，是否散落在多个无关目录。
- 依赖清楚：上层是否通过明确接口使用下层，是否存在循环引用和跨层访问。
- 复用适当：共享目录是否承载真正公共能力，`utils`、`common` 等是否成为杂物区。
- 维护可控：修改一个功能涉及多少模块，文档导航是否能帮助定位，遗留代码是否有明确用途。

只有在发现实际问题后，才提出拆分、合并或迁移建议。每个目录调整建议都应说明收益、影响范围和迁移成本。

## 八、问题记录与优先级

每个问题统一记录：

> 编号、问题类别、优先级、证据状态、文件与行号、规范依据或质量理由、触发条件、预期与实际行为、影响范围、修复建议、验证方式。

证据状态：

- 已证实：有明确代码证据或可重复的运行结果。
- 待验证风险：存在合理风险，但缺少必要环境或复现证据。
- 改进建议：当前可工作，但维护成本或扩展成本偏高。

| 级别 | 判断标准 | 处理建议 |
| --- | --- | --- |
| P0 紧急 | 严重数据破坏、重大安全暴露或核心服务不可用 | 优先阻断相关操作或发布并处理 |
| P1 高 | 关键流程错误、数据覆盖或恢复机制失效，影响明显 | 下一轮修复优先完成 |
| P2 中 | 特定场景失效、明显维护负担、性能或测试缺口 | 纳入近期整改 |
| P3 低 | 轻微一致性、命名、文档或局部简化问题 | 按模块维护节奏处理 |

严重程度根据影响和触发条件确定。规范偏离、代码较长或依赖扫描告警，不自动等于高优先级缺陷。

## 九、最终交付与完成标准

正式审查完成后交付：

1. 审查总报告：整体判断、主要风险、有效保护机制和判断限制。
2. 规范与模块覆盖矩阵：每项是否已检查、采用什么方法、有何证据。
3. 可定位的问题清单：按优先级排序，同一根因合并记录。
4. 验证证据：测试、构建、复现步骤、关键页面状态和测量结果。
5. 整改路线图：建议先修什么、哪些可合并处理、每项如何验收。

审查完成的标准：所有范围有明确覆盖状态，关键流程有证据，每个问题可定位且经过复核，环境缺失和未验证风险被明确列出。审查结束可以仍有待修复问题；“检查完成”和“质量达标”分别给出结论。

执行时优先排查可能损害数据和核心功能的问题，再处理架构、目录与维护成本，最后安排一般规范和文档整理。
