## 4. 结构评价

### 已确认的合理边界

- API 真正入口为 `main.js → app.factory.js / postgres-app.factory.js → node:http server`，不是 NestJS。实际 API 源码外部包导入仅见 PostgreSQL 分支动态加载 Prisma。
- HTTP 响应与路由分发、应用服务、repository 已有物理分层；JSON/PostgreSQL 在工厂处选择，当前未发现 domain→application/HTTP/repository 或模块 repository→application/HTTP 的字面量反向导入。
- V4 由 `main.tsx → Providers/Router/App → AppRoutes` 进入页面，单一 Zustand Store 组合四个 slice，React Aria 集中于 UI 包装层。
- web-core 实际承载 `api` 和 `workspace`；`packages/shared` 当前只有占位 README 和清单，不把空包视作功能缺失。
- V3 不进入当前 dev/build/PM2 入口；其回归仍参与 `npm test`。旧 Milkdown 打包脚本仍存在，使用字符串路径指向 V3，但没有接入当前启动清单，不能直接判为可删除死代码。
- JSON/迁移/快照基础设施有 3 条对应用层纯规则的引用（正式资产校验、正文策略）。这属于为导入/迁移复用领域门禁的已识别依赖，不是“全仓不存在向上引用”；后续可评估规则下沉，当前不把它与业务服务直接依赖持久化混为一谈。

### 维护成本较高的区域

- `NoteEditorView.tsx` 集中滚动恢复、附件与标注异步编排、文件动作和页面组合；`workspaceSlice.ts` 集中加载恢复、缓存、笔记、标签、附件和批量操作。二者值得按职责提取协作者，保留单 Store 和页面契约。
- `icons.tsx`、迁移转换、Schema/关系校验、映射和装配文件较长有合理背景。ComponentShowcase 属于展台，不能与普通业务组件同级按行数惩罚。
- V3 仍占较大文件规模。先补“保留理由/活跃测试依赖/可退役入口”表，再决定删除，不能仅按运行时不可达作清理。
- 结构导航中 V4 编辑器描述仍含“附件/标注后续迁移”，与实际接线不一致；历史目录并不都在 `已归档` 下，读者需要按阶段解释。

详细入口和依赖关系见[模块地图](05-模块地图与依赖关系.md)。
