## 3. 合并、排除与证据变化

- **合并**：S3-01 与 S4-03 → R-01。两者都在一个业务操作尚未完整成功时提交了子变更，修复需明确业务事务边界。目录子树可导致库无法启动，合并优先级取 P1；批量导入本身的“隐藏部分成功”样本仍保留 P2 影响描述，不能以修了其中一个场景关闭整项。
- **不合并**：R-01 与 R-05 都影响 JSON 恢复，但前者是进程存活期间业务提交边界，后者是文件替换中断后启动恢复；必须分开验收。R-03 与 R-11 共用 parseBody，但分别是字节保真与超限响应，修复可同批、问题仍分别关闭。
- **关联但不合并**：R-04/R-06/R-08/R-09/R-10 涉及标签模型演进，遗漏位置与触发链路不同，不把它们缩成一个无法独立验收的“标签问题”。R-14 的测试陈旧与 R-15 的文档陈旧也有不同验证入口。
- **证据升级**：S3-01/02/03/04/08 已有阶段四真实 HTTP/浏览器复现；S2-06 已有阶段五规模测量，最终保留 R-17“容量风险”，没有既定 SLO 可据以判定超标。R-04 保留实际函数契约证据，不伪称真实 PG 通过或失败。
- **不计产品缺陷**：阶段四响应形状、初始化时机、定位器等审查脚本错误；阶段五性能脚本地址/取数时点错误；完整 E2E 表格首次失败但单独复跑与两个真实页面样本通过的情况。表格稳定性仍列 V5-05 待观察，没有删除首次失败证据。
- **没有撤销已证实问题**：本轮源码未变，复核未发现足以撤销其根因的证据。结构扫描零循环/零越界、单元测试成功，也不能否定隔离失败场景。
