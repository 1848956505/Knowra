## S2-01：自定义 API 端口未同步 Web 代理默认目标

- 定位：`deploy/ecosystem.config.cjs:13`、`:24`；`apps/web-v4/server.mjs:20`。
- 触发：使用模板提供的 `KNOWRA_API_PORT` 改变 API 监听端口，未同时手动设置 `API_ORIGIN`。
- 预期：未显式指定远端 API_ORIGIN 时，Web 代理默认目标与同一模板中的 API 端口一致。
- 实际：API 的 PORT 使用 KNOWRA_API_PORT，Web 的 API_ORIGIN 仍默认 `http://127.0.0.1:3001`。server.mjs 优先采用非空 API_ORIGIN，因而不会从运行端口登记纠正。
- 证据：使用人工 env 求值已读的配置，默认端口一致；仅设置 KNOWRA_API_PORT=43123 后 API 为 43123、Web 目标仍为 3001；两者显式同步后恢复一致。见[配置推演](证据/阶段2/配置推演.json)。没有启动服务或读取真实环境凭据。
- 影响：在该自定义配置下，代理可能失败或访问 3001 上其他服务；本次没有证明当前默认生产部署发生故障。
- 建议：在模板中统一派生 API 端口与默认 API_ORIGIN，继续保留显式 API_ORIGIN 覆盖。不要把默认值全改成另一个硬编码端口。
- 验证：默认、自定义端口、显式 origin 三组配置断言，加隔离 Web→API 请求；同时检查 Nginx 自定义 Web 端口是否需要显式调整。

- 定位：`.github/workflows/ci.yml:52`、`:61`；`apps/web-v4/package.json:15`、`:19`；根 `package.json:14`、`:30`。

## S2-06：索引逐批拉全的容量与延迟风险

- 定位：`apps/web-v4/src/features/notes/useNotesIndexData.ts:6`、`:45`～`:58`；`NotesIndexView.tsx:121` 附近。
- 触发：在线 API 模式、非 root/unfiled 的普通查询，匹配笔记数量增长，且服务端每批返回 30 条并持续 hasNext。
- 结构证据：loadResults 串行 await queryNotes，累积所有 items，直到无下一页后才 setRemotePage；列表页大小并不限制这段请求总量。recent 单独限 6，不受该全量路径影响。
- 规模推演：若匹配 3,000 条且每批恰为 30，完整汇总需约 100 次请求；这是代码条件推演，不是实际测量。当前仍可能显示本地缓存回退，并非页面必然一直空白。
- 风险：切换筛选/查询可能放大请求量和结果就绪延迟，图标视图还渲染全部结果；尚未确定日常数据量是否造成明显影响。
- 当前状态：待验证风险，不认定已超过性能阈值，也不把为避免跨页漏项的设计目的当作错误。
- 建议：第五阶段用明确数据规模测量首屏、完整结果、请求数和内存；若超标，再设计文件夹/文稿统一分页契约或增量加载，保留结果完整性与计数语义。
- 验证：30/300/3,000 条数据，日常/弱网，列表/图标，连续输入/切换筛选；同时确认请求取消、排序、空页和引用计数不回归。
