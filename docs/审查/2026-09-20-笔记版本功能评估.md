# 笔记版本功能评估

## 结论

保留底层版本快照，但当前“版本”面板需要改进。它有防误改与来源追溯价值，现有界面仅支持查看旧正文，缺少差异对比、另存和恢复，因此用户可感知收益不足。本次仅评估，不删除版本、不调整保存频率。

## 当前实际行为

- 编辑停止约 700ms 后触发自动保存；正文改变会调用 `noteVersionService.ensureForNote`，存储完整 Markdown，不是增量差异。
- 同篇笔记按内容哈希去重。相同正文重复保存不会新增版本；标题、目录等元数据修改也不创建正文版本。不断修改正文会持续产生新快照。
- 标注的来源版本、原始范围快照、知识证据及试题来源依赖这些不可变记录。直接按数量或时间删除版本可能破坏引用，不能把它当作纯界面历史随意清空。
- 目前没有针对单篇笔记的自动历史淘汰策略。列表接口返回全部版本且含正文，面板又请求所选版本详情，长文和大量版本会增加内存及传输成本。
- 面板按创建时间排列，将第一条标为“最新版本”；同分钟的修改显示相同时间，不利于识别。恢复到曾经出现过的相同正文会复用旧内容版本，因此“创建时间最新”不一定等于“当前正文”。

代码入口：`apps/api/src/modules/knowledge/application/note-service.js`、`note-version-service.js`、`infrastructure/note-version-repository.js`、`apps/web-v4/src/features/editor/EditorInspector.tsx`。

## 本机占用样本

2026-09-20 只读查询桌面 SQLite：

| 内容 | 数量 | 字节数 |
| --- | ---: | ---: |
| 当前笔记实体 | 28 | 821,539 |
| 正文版本实体 | 609 | 4,803,875 |
| 其中历史 Markdown 正文 | — | 4,407,807 |
| 标注修订 | 7 | 6,257 |

版本实体约 4.6 MiB，其中正文约 4.2 MiB。SQLite 主文件约 32.9 MiB；其中还包括同步队列、索引等，不能全部归因于版本。统计不含 WAL、附件、备份，也不是云端空间审计。

例：100 KiB 的长文保留 1,000 份不同全文快照，正文部分约占 97.7 MiB；同步记录和备份可能进一步增加总体存储。

## 建议的优化顺序

1. **先提高可用性和列表性能**：改为“历史记录”；明确标记当前正文对应版本，时间精确到秒；增加与当前版本对比、复制或另存为新笔记。列表分页且仅返回摘要，正文按需读取。
2. **保持及时保存，合并面板展示**：按编辑会话或时间段归组，默认展示每组最后一次快照；被正式来源引用的版本单独保留。展示合并本身不会释放磁盘空间，但不会牺牲编辑安全。
3. **再实施真正的空间治理**：区分用户可见检查点与领域来源快照，评估压缩或内容寻址存储。清理必须检查标注、originSnapshot、证据、分析范围、试题及同步未确认记录的引用闭包，支持预览和备份；不得靠降低正文自动保存频率节省空间。

优先做第 1 项，而不是移除底层版本系统。当前样本的版本空间不大，但长期大量编辑长文确实需要治理。
