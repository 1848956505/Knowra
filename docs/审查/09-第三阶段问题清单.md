## S3-01：失败写入未被完整回滚

**定位**：[file-data-store.js](../../apps/api/src/infrastructure/file-data-store.js) 第 39～44 行（非事务 flush），[folder-repository.js](../../apps/api/src/modules/knowledge/infrastructure/folder-repository.js) 第 9～24 行（先改数组再 persist），[folder-service.js](../../apps/api/src/modules/knowledge/application/folder-service.js) 第 164～171 行，[index.js](../../apps/api/src/modules/knowledge/index.js) 第 331～336 行（目录清理未包事务）。依据 N-20/22、Q-02/03。

**触发与影响**：目录创建后落盘失败，HTTP handler 抛出 `STORAGE_WRITE_FAILED`，但数组中已存在新目录；后续任一成功 flush 会把这条失败操作写入磁盘。删除含子目录的父目录时，先持久化父目录删除，再删除子目录；第二次落盘失败会在磁盘留下引用不存在父目录的子目录，重启被引用校验拒绝，影响整个 JSON 库加载。普通收藏/关联及部分实体保存也采用直接 repository 写入，应按同根因核查，不能只修目录样例。

**证据**：[本地定向复现](证据/阶段3/本地定向复现.json) S3-01a/b。使用实际 factory、handler、仓储和原子写入函数；仅在第 N 次写入注入错误，随后用实际数据加载器重启。区别于进程崩溃推演，本次已复现正常错误返回后的不一致。

**建议与验收**：将一个业务变更的所有内存修改及持久化放入统一事务；子树清理一次提交。对每个写入阶段注入失败，断言调用失败后内存、磁盘与重启结果均为原状态；成功时也校验引用。现有文件级原子替换应保留。

## S3-02：编辑器卸载丢失冲突草稿

**定位**：[useNoteAutosave.ts](../../apps/web-v4/src/features/editor/useNoteAutosave.ts) 第 57～66、216～235 行，[AppRoutes.tsx](../../apps/web-v4/src/app/AppRoutes.tsx) 第 60～64 行，[App.tsx](../../apps/web-v4/src/app/App.tsx) 第 82 行开始的主页导航及资料导航。依据 N-12/24、Q-02/03。

**触发与影响**：输入正文，自动保存返回 409，再点主页/资料入口离开编辑页。草稿与冲突只存在 hook 的 refs；卸载清理在有冲突时不保存，路由直接换成其他组件，未设全局离开保护，也未把草稿移交到跨页面存储。重新打开笔记只取得服务端正文，未保存文本无法从应用中找回。`beforeunload` 不能拦截应用内部路由切换，而且随 hook 卸载移除。

**证据**：[frontend-probes.test.ts](证据/阶段3/frontend-probes.test.ts) 在真实 hook 上复现编辑、409、卸载、重挂载；草稿从 `unsaved review draft` 退回 `server`，没有再次保存。App 路由源码证明存在卸载入口。未在真实浏览器点击，第四阶段须补完整页面证据。已有 hook 测试保留组件实例的断言不足以覆盖这条路径。

**建议与验收**：建立跨路由的草稿恢复机制，并在离开前提供保存/导出/明确放弃；统一覆盖主页、侧栏、搜索、浏览器历史和 hash。验收断网、409、卸载中保存失败、重新进入后草稿仍可恢复，且不无条件覆盖服务端版本。

## S3-03：导航覆盖缓存时遗漏 tagGroups

**定位**：[navigationSlice.ts](../../apps/web-v4/src/store/slices/navigationSlice.ts) 第 12～26 行，[loading.ts](../../packages/web-core/src/workspace/loading.ts) 第 3～10 行，[TagManagerView.tsx](../../apps/web-v4/src/features/tags/TagManagerView.tsx) 分组生成 sections。依据 N-17/24、Q-01/03。

**触发与影响**：在线加载分组后选择笔记、目录、开关目录或调整标签页。`commitNavigation` 新建快照时传入 tags 却未传 tagGroups，快照工厂默认写成空数组。当前内存仍有分组；刷新后若 API 不可用，缓存恢复没有分组，按分组生成的标签管理与选择列表不完整。服务器分组未被删除。

**证据**：[前端定向复现](证据/阶段3/前端定向复现.txt)：导航后内存分组为 1，持久缓存为 0。

**建议与验收**：统一 workspace 快照序列化入口，保留所有服务端字段，只更新导航信息。覆盖在线加载 → 导航 → 离线重载，标签及分组完整且保持只读。

## S3-04：恢复绕过同级名称约束

**定位**：[note-service.js](../../apps/api/src/modules/knowledge/application/note-service.js) 第 191～201 行；[postgres-async/note-service.js](../../apps/api/src/modules/knowledge/application/postgres-async/note-service.js) `saveDeletedState` 第 128 行起及第 172 行。依据 Q-01、N-28，以及创建/更新已实施的 `SIBLING_NAME_CONFLICT` 规则。

**触发与影响**：删除笔记 A，同一目录创建同名笔记 B，再恢复 A。恢复只改 deleted，没有复用同级文件/目录名称检查，形成两个有效同名对象；用户难以区分，后续普通编辑也可能被已有重名检查阻止。恢复与新建/重命名规则不一致。

**证据**：[本地定向复现](证据/阶段3/本地定向复现.json) 产生两条 `Same` 有效笔记。PG 分支同样没有恢复前校验，尚未实库复现。

**建议与验收**：明确重名恢复策略，至少返回可操作的冲突或让用户选择新名称，并在恢复事务中执行。覆盖同名文件、同名目录及重复恢复，双驱动一致。

## S3-05：重复 ID 的“新建分组”实际覆盖旧记录

**定位**：[tag-group-service.js](../../apps/api/src/modules/knowledge/application/tag-group-service.js) 第 18～22 行，[dto/tag-group.dto.js](../../apps/api/src/modules/knowledge/application/dto/tag-group.dto.js) 第 15 行，[postgres-async/tag-group-service.js](../../apps/api/src/modules/knowledge/application/postgres-async/tag-group-service.js) 第 9 行，[postgres/tag-group-repository.js](../../apps/api/src/modules/knowledge/infrastructure/postgres/tag-group-repository.js) 第 8 行 upsert。依据 Q-01/03、N-28。

**触发与影响**：POST 新建分组携带已有 ID 和不同名字。只检查名称可用，未检查 ID；save/upsert 覆盖已有组。已有标签仍引用这个 ID，却可通过“新建”把 multiple 改成 single，绕过 update 对有标签分组的模式变更保护。UI 通常自动生成 ID，主要影响 API 客户端、重试及导入集成。

**证据**：[本地定向复现](证据/阶段3/本地定向复现.json) 对已有标签的组重复创建后名称和选择模式被替换，记录仍只有一条。PG 实库未运行，但其 upsert 的 update 明确包含 name/selectionMode。

**建议与验收**：新建采用 create-only 契约并拒绝重复 ID；更新走独立规则。覆盖同空间、不同空间、系统组与模式切换，拒绝后原记录及引用不变。

## S3-06：备份/迁移未覆盖标签分组模型

**定位**：[postgres-snapshot-service.js](../../apps/api/src/infrastructure/postgres-snapshot-service.js) 第 50～95 行，[migration/json-to-postgres.js](../../apps/api/src/infrastructure/migration/json-to-postgres.js) 第 97 行 plan、第 236 行起替换删除及第 264 行 tags 写入、第 293 行空库检查；[local-data-relations.js](../../apps/api/src/infrastructure/local-data-relations.js) 第 119～129 行；[schema.prisma](../../prisma/schema.prisma) Tag.groupId / TagGroup。依据 N-17/22/28、Q-03/05。

**触发与影响**：PostgreSQL 中存在引用自定义分组的标签，导出快照没有 `data.tagGroups`，导入校验报 unknown group。JSON→PostgreSQL 计划保留 tag.groupId，却未生成/写入分组；目标数据库为空且有外键时无法正常落入标签。即使只建了空分组，其元数据也未进入迁移计划。删除/空目标检查的模型清单同样未纳入 tagGroup，说明是全链模型扩展遗漏。

**证据**：[PostgreSQL契约复现.json](证据/阶段3/PostgreSQL契约复现.json)：实际导出函数配 stub 仓储产生不能通过实际导入校验的快照；完整输入的迁移预检 `canApply=true`，但 plan.tagGroups 缺失而 tag.groupId 保留。外键失败结论来自 schema/迁移实现，未伪称实库执行过。

**建议与验收**：快照、转换、计数/校验和、空目标检查、写入/删除顺序全部包含分组。真实隔离 PostgreSQL 中覆盖 JSON→PG→导出→清库导入→再次导出，比较全部集合、分组模式及引用；有分组无标签的情况也必须保留。

## S3-07：写操作分类依赖名字前缀，漏掉 merge/reorder

**定位**：[maintenance-gate.js](../../apps/api/src/infrastructure/maintenance-gate.js) 第 87 行，[postgres-advisory-lock.js](../../apps/api/src/infrastructure/postgres-advisory-lock.js) 第 40～42 行；[postgres-async-module.js](../../apps/api/src/modules/knowledge/postgres-async-module.js) `mergeTags`；[postgres-async/tag-service.js](../../apps/api/src/modules/knowledge/application/postgres-async/tag-service.js) `reorderTags`。依据 N-22/28、Q-02。

**已证实部分**：两个 handler 是写操作，但正则不含 merge/reorder，因此本地 gate 按普通 operation 执行，数据库包装采用共享 advisory lock。合并和排序能相互并发。共享锁仍阻挡正常排他写和迁移；不能说所有互斥都失效。

**未证实部分**：并发合并/排序是否在实库形成部分更新或引用异常尚未验证，故整体保留为 P2 待验证风险。证据中的 false 仅证明分类遗漏，不证明某个竞态结果。

**建议与验收**：用显式操作元数据代替两份独立正则，枚举所有 mutating handler。双进程执行交叉合并、排序与导入，检查结果与失败原子性；同时核验多步合并本身的事务边界。

## S3-08：按 Buffer 独立转字符串破坏 UTF-8

**定位**：[http/request.js](../../apps/api/src/http/request.js) 第 15～22 行。所有 JSON 路由共享 parseBody。依据 N-17、Q-01/03。

**触发与影响**：网络流某个分块恰好切在中文/emoji 的 UTF-8 字节中间。`data += chunk` 每块单独隐式解码，不保留未完成字节；产生 `�` 后 JSON 仍然有效，正文进入 service 时已经被修改。影响正文、标题、导入等中文字段；服务端 hash/version 无法恢复请求原文。

**证据**：[请求分块复现.json](证据/阶段3/请求分块复现.json) 将“中”的首字节与余字节放在相邻两个 Buffer，实际 parseBody 成功返回被改写的字段。属于确定性的流解析缺陷；没有测量真实网络中触发频率。

**建议与验收**：累计 Buffer 后一次解码，或使用保留跨块状态的 UTF-8 decoder；保留字节级大小限制。对中英文、emoji、组合字符的每个字节切点做分块回环，输出必须与原请求一致，再补真实 HTTP 保存及重读。
