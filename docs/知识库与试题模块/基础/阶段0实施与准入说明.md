# 知识与试题模块：阶段 0 实施与准入说明

> 状态：已完成
> 日期：2026-07-27
> 对应版本：2.6.1（阶段 0 收口版本）
> 当前仓库版本：2.8.0（阶段 1.0 基础设施已在此基线上继续演进）
> 当前领域基准：[Knowra 知识与考卷系统领域冻结稿](Knowra%20知识与考卷系统领域冻结稿.md)

> 本文现在同时承担两项职责：记录阶段 0 的准入设计，以及记录阶段 0 已经落地的安全基线。阶段 0 不负责定义正式知识点、学习目标、试题或试卷领域；这些对象必须以领域冻结稿为准。

## 1. 阶段目标

阶段 0 不新增 `KnowledgeItem`、`KnowledgeEvidence`、`LearningObjective`、`ExamFocus`、`Question`、`Paper`、AI 或 RAG 业务功能。它只负责在进入新领域开发前修复会放大数据风险的基础问题，并建立可验证的开发准入线。

本阶段的完成标准是：

1. 文档冻结稿与历史文档归档已单独固化；
2. 新阶段从最新 `origin/main` 创建独立分支；
3. 当前单用户数据边界明确；
4. JSON、附件和实体引用不再接受静默覆盖或结构性损坏；
5. 前端保存失败、缓存降级和异步竞态不会继续执行破坏性操作；
6. 自动化测试通过，文档、版本号和结构导航同步。

## 2. 访问与用户边界决策

本阶段不实现应用内登录系统。

正式登录并不只是增加一个登录表单，还必须同时处理会话生命周期、安全 Cookie、CSRF、密码存储、暴力尝试限制、退出和恢复流程。只实现其中一部分会制造虚假的安全感，因此它不属于“简单顺手补上”的任务。

当前项目为单人使用，采用以下边界：

- API 由服务器固定 `ownerId`，读取顺序为 `createAppContext.ownerId`、`KNOWRA_OWNER_ID`、默认值 `demo`；
- 创建和查询知识空间时忽略客户端提交的 `userId`，客户端不能切换数据所有者；
- 领域服务仍保留多用户表达能力，后续正式登录可以替换 HTTP 边界，不需要重写领域对象；
- 公网访问保护继续以 Nginx HTTP Basic Authentication 为生产基线，`/api/health` 可匿名；
- 生产站点当前按用户此前要求临时关闭 Basic Auth。本阶段不擅自修改服务器；下一次公开部署前应把恢复 Basic Auth 作为发布门禁。

## 3. 后端完成项

### 3.1 实体与 HTTP 契约

- Note、Folder、Tag 默认 ID 使用 UUID 熵；
- 客户端重复 ID 返回 `409`，不再通过 repository upsert 覆盖原记录；
- 持久化应用上下文默认启用严格引用校验；
- space、folder、tag、note 的不存在、冲突和字段错误统一映射为 `404`、`409`、`422`；
- 动态路由改为精确匹配，避免相似路径误命中；
- 未知异常统一返回 `500 INTERNAL_SERVER_ERROR`，不向客户端泄漏内部错误信息；
- 附件上传必须引用存在且未删除的笔记；
- SVG、HTML、XML、JavaScript 等主动内容不得以内联可执行类型返回，二进制响应增加 `nosniff` 和 sandbox 约束。

### 3.2 本地 JSON 与附件

- 本地 JSON 使用“同目录唯一临时文件 → `fsync` → 原子替换”写入；
- 新增 `schemaVersion: 1`，快照版本保持 `v1-local-json`；
- 旧无版本数据仍可加载：缺失的 note space 可在唯一空间或所属目录下推断；旧数据中失效的 note space/folder 引用只在无版本迁移路径中修复；
- 版本化数据和导入快照严格校验 space、folder、tag、note、annotation、attachment 的跨引用、同空间约束和目录环；
- 导入先完整校验，再切换附件目录和提交 JSON；同步异常会恢复旧内存、旧 JSON 和旧附件目录；
- 附件上传、删除和重命名在元数据写盘失败时执行补偿回滚，避免孤儿文件、悬空记录或文件路径与 JSON 不一致；
- 本地事务只包围内存集合与 JSON 提交，附件文件清理在提交后执行；
- 永久删除笔记或清空回收站时，同步移除当前阶段的标注记录、附件元数据，并在提交后清理附件文件。

### 3.3 已知存储边界

本地 JSON 仍是单进程、最后写入者获胜，不具备跨进程文件锁。若进程恰好在附件目录切换完成、JSON 提交之前被强制终止，仍需要事务日志才能自动恢复。进入多人、并发任务、试卷历史和 AI Job 阶段前，应迁移 PostgreSQL，并为文件操作增加 outbox 或可恢复任务。

### 3.4 阶段 0 实际改动清单

阶段 0 已按“先保护现有稳定笔记功能，再进入新领域开发”的原则落地。实际改动分为以下四组：

#### 数据、边界与 API

- 通过 `KNOWRA_OWNER_ID` 和应用上下文固定单用户所有者，HTTP 层不再接受客户端通过 `userId` 切换数据边界。
- Note、Folder、Tag 等实体默认使用 UUID 熵；客户端重复 ID 不再触发静默 upsert，而是返回冲突错误。
- 补齐实体字段、跨空间引用、目录环和回收站状态校验；动态路由改为精确匹配，异常统一收敛到现有 API error envelope。
- 保留 `ContentAnnotation` 作为重要内容标注的临时基础能力，但没有把它升级为正式 `KnowledgeItem`，也没有恢复旧 `KnowledgePoint` 业务链路。

主要落点包括：`apps/api/src/config/env.schema.js`、`apps/api/src/app.factory.js`、`apps/api/src/server.js`、`apps/api/src/http/`、`apps/api/src/modules/knowledge/domain/`、`apps/api/src/modules/knowledge/application/` 和 `apps/api/src/modules/knowledge/http/`。

#### JSON、快照与附件一致性

- 新增 `schemaVersion: 1` 和本地快照版本标识，兼容读取旧的无版本 JSON，并只在明确的兼容迁移路径中修复可推断字段。
- JSON 写入改为同目录临时文件、`fsync`、原子替换；导入改为先全量校验，再提交 JSON 和附件目录，并在异常时恢复旧状态。
- 附件上传、删除、重命名和笔记删除增加元数据与文件的补偿处理，避免阶段 0 新操作制造孤儿文件或悬空记录。
- 附件文件始终作为独立文件保存，正文只保留引用；主动内容类型不以内联可执行方式返回，并增加 `nosniff` 与 sandbox 约束。

主要落点包括：`apps/api/src/infrastructure/atomic-json-file.js`、`local-data-schema.js`、`local-data-relations.js`、`attachment-directory-swap.js`、`local-attachment-store.js`、`local-attachment-upload.js`、`local-attachment-deletion.js`、`local-attachment-snapshot-store.js` 和 `local-attachment-snapshot-validator.js`。

#### 前端保存与异步竞态

- `persistDraft()` 改为返回明确结果，并将保存请求串行化，避免慢请求覆盖较新的草稿。
- 切换笔记、目录、标签页，返回索引，新建、复制和导入前统一检查保存结果；保存失败时保留当前编辑上下文。
- 缓存和加载状态只读化；笔记详情、标注和附件等异步请求增加序列号及当前笔记校验，旧请求不能覆盖新选择。
- 创建标注前必须先保存正文，标注列表的文本和属性统一转义。

主要落点包括：`apps/web/src/controllers/editor/draft-controller.js`、`apps/web/src/app/app-state-actions.js`、`apps/web/src/lib/workspace-loading.js`、`apps/web/src/lib/workspace-cache.js`、`apps/web/src/controllers/annotation-controller.js` 和 `apps/web/src/controllers/sidebar/`。

#### 文档、版本与验证

- 已将旧 KnowledgePoint 链路退役，将阶段 0 规划、领域冻结稿、项目结构导航和变更日志作为当前交接基线。
- 阶段 0 收口版本为 `2.6.1`；后续 Phase1.0 的 PostgreSQL 与附件可靠性改动在 `2.7.0`、`2.8.0` 继续演进，不能把这些后续改动倒推为阶段 0 的领域功能。
- 阶段 0 门禁已执行 API、Web、部署脚本、编辑器 bundle、JSON 兼容和 `git diff --check` 检查；正式知识实体、AI、RAG 和试卷功能仍未在本阶段引入。

## 4. 前端完成项

- `persistDraft()` 返回明确的成功、失败、是否变更和原因；
- 保存请求串行执行，较新的草稿不会被较早的慢请求反向覆盖；
- 切换笔记、切换目录、返回索引、关闭当前标签、新建、复制和导入前统一检查保存结果；
- 保存失败时保留当前笔记、目录、标签页和编辑上下文；
- `cache` 与 `loading` 模式只读，禁止把后端缓存误当成本地可写数据；`local` 仅作为显式演示模式；
- 笔记详情和右侧附加数据都有请求序列与当前笔记校验，旧请求不能覆盖新选择；
- 创建正文标注前先保存当前草稿，保存失败不创建标注；
- 标注列表的持久化文本和属性统一转义，避免注入 HTML。

## 5. 验证与准入

阶段 0 收口时执行：

- API 全量测试（包含真实 `createServer` HTTP 契约）；
- Web 全量测试；
- 部署脚本测试；
- Milkdown 生产 bundle 构建；
- `git diff --check`；
- 当前 `storage/data/knowledge-base.json` 只读加载兼容检查。

不执行浏览器视觉检查和截图；视觉验收由用户在本地项目中完成。

## 6. 与领域冻结稿的对齐

阶段 0 的实现边界与冻结稿保持一致：

1. `Note` 是原始资料载体，不等于 `KnowledgeItem`。
2. `ContentAnnotation` 只表示“正文哪里重要”，不能直接当作正式知识单元、学习目标或考点。
3. 冻结稿使用 `KnowledgeItem`、`KnowledgeEvidence`、`LearningObjective`、`ExamFocus`、`Question`、`Paper` 等职责分离的对象；旧方案中的 `AssessmentPoint` 不作为新实现命名。
4. 阶段 0 的笔记删除清理标注，是正式知识实体尚未启用时的临时数据清理策略。进入正式知识链路后，删除 Note 应使来源证据失效或变为来源不足，不能自动删除正式知识对象。
5. 阶段 0 不定义掌握度公式、图谱独立存储、RAG 索引或 AI 事务边界；这些内容以后仍需遵守冻结稿中的来源、证据、幂等和可审查规则。

## 7. 下一阶段准入规则

满足以下条件后，可以从阶段 0 的安全基线进入 Phase1.0 工程阶段；领域实体仍须在 Phase1.0 完成后按冻结稿另行准入：

1. 本文档列出的自动化门禁保持通过；
2. 新领域实体按冻结稿命名，不复活旧 `KnowledgePoint` 语义；
3. 先建立数据库迁移和 repository 边界，再引入试卷历史、异步 AI 和 RAG；
4. 外部 AI、对象存储和网络 IO 不进入数据库事务；
5. 删除 Note 后，未来的 KnowledgeEvidence 必须转为失效或来源不足，不能沿用当前“尚无正式知识实体时清理 Annotation”的临时策略；
6. 对公网发布前恢复 Nginx Basic Auth，或者先完成经过安全审查的正式登录系统。
