## 0. 先认错：复用“没有触发”的原因是我的脚本 bug

我在 [A/B 实验结果](./2026-10-15_提炼提示词AB实验结果.md) 2.5 节写“复用一次都没有触发，因为各节内容重叠很少”。**这个解释是错的。**

GPT-6 在复核 1.1 节指出了真实原因：我的脚本只在候选“没有任何问题”时，才把它的标题加入下一篇的已有标题列表；而那一轮所有候选的引文偏移都不对，所以列表始终为空，复用能力根本没有被测到。GPT-6 已经修复脚本，并补充了内容重叠的样本。复核文档的其余结论我都同意。

## 2. 我对结果的解读

### 2.1 “类别 5/7”是评分标准的问题，不是模型的问题

N05“矩阵加法把两个相同形状的矩阵在对应位置上的元素相加”、N06“逐元素乘法对同形状数组按对应位置相乘……”，模型都判为 **definition**，预期答案是 fact。这两句本身就是定义，模型的判断更合理。按语义看，类别应该是 7/7。建议修正 `scenario.mjs` 中这两条的 expected。

### 2.2 两个干扰项的通过，不能说明模型会区分易混概念

系统提示词里写着：

> 矩阵（数学对象）、矩阵乘法（运算）、矩阵加法（运算）、逐元素乘法（另一种运算）彼此不同；不要为了减少节点把不同概念硬合并。

这句话把负对照的答案直接告诉了模型。再加上 N05、N06 的笔记标题就是概念名本身，这两个负对照几乎没有难度。**本轮的 7/7 可以证明流程和契约跑得通，不能证明易混概念的区分能力。**

### 2.3 新发现：概念的“语境说明”吸收了条目内容

N01 新建概念时，模型给的 sense 是：

> 两个矩阵之间按行与列对应元素相乘再求和的运算，**要求左矩阵列数等于右矩阵行数**

后半句正是 K_SYN_1 的内容。这就是 GPT-6 第二轮第 4 节担心的“同一语义主张有两份真源”，只是发生在概念说明和条目之间，而不是关系和命题之间：以后如果 K_SYN_1 被修订或标记为错误，sense 里那半句不会跟着变。

建议在契约中约束 sense：只写“它是什么、属于哪个语境”，用于和同名概念区分，不写性质、条件或方法。验收时检查 sense 是否包含已有条目的陈述。

### 2.4 每篇笔记只有一条知识，比真实情况简单很多

提示词要求“把每篇笔记中唯一的一项主要知识……”。真实笔记一节有十几条，模型需要同时决定多个条目分别属于哪些概念，难度不在一个量级。

### 2.5 全量概念目录的做法无法扩展，融合依赖检索

每次请求都附上全部已有概念和全部已有条目。从 result.json 看，输入 token 随条目数稳定增长（N01 583 → N07 956，每多一个条目约增加 60 token）。知识库到几百条时，这条路走不通，只能先检索出少量候选概念和条目，再让模型从中选择。

这意味着 [检索索引备忘](./2026-10-15_图谱渲染复用与检索索引备忘.md) 里的检索模块，和 Concept 融合并不独立：**融合的召回质量以检索为前提**。检索漏掉了正确的已有概念，模型就只能新建重复概念。我修正之前备忘里“两者分开立项、互不相关”的隐含假设：可以分开实施，但融合实验需要尽早模拟“只给 top-k 候选”的情况。

## 3. 建议的第二轮场景

在现有实验框架上增加以下内容，每一项对应上面的一个缺口：

| 改动 | 检验 |
| --- | --- |
| 删除提示词中列举具体概念的那句话；干扰项笔记改为不直接写概念名的标题和表述 | 2.2：没有提示时能否区分易混概念 |
| 加入“梯度（数学）”与 `x.grad`（PyTorch 属性）一组同名异义 | 同名不同义时是否误合并 |
| 加入一篇包含 3～5 条知识的笔记，契约改为允许返回多条 | 2.4：多条知识的归属 |
| 概念目录中加入 20～30 个无关概念作为噪声，并模拟只给 top-k 候选（正确概念有时不在候选中） | 2.5：规模与检索缺失时的行为 |
| 检查 sense 是否包含条目陈述 | 2.3 |
| 修正 N05、N06 的预期类别 | 2.1 |
| 同一设置重复运行 3 次 | 稳定性 |

“正确概念不在 top-k 候选中”这一项最关键：此时正确行为应该是提议新概念并标为“可能与已有概念重复”，而不是硬挂到一个错误的候选上。前者可以由用户合并，后者会悄悄污染已有概念。

## 4. 结论

首轮实验第一次用真实模型验证了“Concept ID 与 KnowledgeItem ID 分离”的基本流程：新建、挂靠、复用条目、追加来源都能按预期工作，契约和内存模拟也站得住。这是对 Concept 桥接方案（方案 B）的正面证据。

但本轮在易混概念区分上没有提供证据（见 2.2），也没有覆盖真实规模（见 2.4、2.5）。在第二轮补上这些场景之前，不建议据此决定 Concept 的 schema。
