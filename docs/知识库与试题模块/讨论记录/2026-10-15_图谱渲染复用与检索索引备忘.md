# 图谱渲染复用决定与 AI 检索索引备忘

> **性质：** 用户已确认的方向性决定（第 1 节）+ 待立项的备忘（第 3 节）。不是实施任务，也不更新冻结稿。  
> **日期：** 2026-10-15  
> **记录：** Claude，依据当日与用户的讨论

## 1. 已确认：图谱的渲染与布局复用开源库

当前的 [概念图原型](../../../apps/web-v4/src/features/knowledge/graph/ConceptGraphView.tsx) 用手写坐标和 SVG 实现，只适合十几个节点的演示。接入真实数据后，自动布局、缩放平移和大图性能都改用成熟的开源库，不自己写。

**具体选哪个库暂不决定。** 候选与比较维度：

| 候选 | 备注 |
| --- | --- |
| Cytoscape.js | 老牌图论与可视化库，布局算法多，生态成熟 |
| AntV G6 | 中文文档完善，交互和动画能力强 |
| Sigma.js（配合 graphology） | 基于 WebGL，节点多时性能好 |
| React Flow | 与 React 集成最自然，更偏向流程图和节点编辑 |

选型时至少比较以下几点：

- 能否实现已验证的交互：点击概念后展开方块、相邻概念半清晰、其余淡出，以及连线中点承载关系条目；
- 节点规模到几百时的性能；
- 键盘可访问性，是否能与现有 `components/ui` 包装层共存；
- 是否违反 V4 边界规则（`scripts/check-v4-boundaries.mjs`）；
- 体积与维护活跃度。

现有原型中的数据结构和聚合规则（`conceptGraphData.ts`、`conceptGraphModel.ts`）与渲染无关，换库时保留。

## 2. 已确认：不复用 GraphRAG 一类系统作为知识库主体

GitHub 上常见的 LLM 建图项目（如 Microsoft GraphRAG、LightRAG、Neo4j LLM Graph Builder、LangChain `LLMGraphTransformer`）面向**检索增强**：

- 全自动抽取实体与关系，没有用户确认环节；
- 图是可以重建的检索索引，不是权威数据；
- 节点不区分概念、命题和方法，也没有掌握度和精确到原句的来源。

这与知境的定位相反：知境的知识网由用户确认、可以溯源、承载学习状态，正是冻结稿 2.6 节所说的“正式知识”，而这类图属于“可重建的派生数据”。此外，这些项目多为 Python 实现，接入需要额外维护一个服务。

可以借鉴的是思路，例如实体去重、同名合并的做法，可用于别名与同名异义的处理。

## 3. 备忘：供 AI 使用的检索索引（另立模块，暂不展开）

随着笔记和知识点增多，AI 不能每次逐篇读取笔记库或知识库，需要一套索引。这属于冻结稿中的 **Retrieval Module**，与知识模型讨论分开进行。

已有基础，供立项时参考：

- `apps/api/src/modules/ai/retrieval.js` 已有授权检索入口：关键词检索作为基线，并预留了 `candidateSource` 接口供索引接入；索引异常、陈旧或无结果时自动回退到关键词检索。
- 已有文档：`docs/AI功能/p1/AI-01-R06-授权检索接口与关键词基线.md`、`docs/AI功能/p2/授权关键词检索覆盖验收.md`。
- 冻结稿 2.6 节：索引是可以重建的派生数据，不能成为知识的唯一真源。

立项时需要回答的问题：

1. 索引对象：只索引笔记，还是同时索引知识点、学习目标；
2. 检索方式：关键词、向量，还是二者混合；embedding 用哪个模型、放在本地还是云端；
3. 隐私与授权：如何与现有的 AI 可读范围、授权清单衔接；
4. 更新时机：笔记或知识点修改后，索引如何增量更新；
5. 能否复用开源 RAG 项目：这里的数据可以重建，复用风险比知识库主体低得多，值得认真评估。
