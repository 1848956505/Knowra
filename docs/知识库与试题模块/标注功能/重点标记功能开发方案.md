## 2. 本次范围和最终用户行为

### 2.1 基础标记必须交付

- 连续文字选区、一个或多个相邻内容块、标题章节范围三种标记。
- 一次操作创建默认重点；可编辑类型、备注和可选重要程度；取消与恢复不破坏正文。
- 统一重点清单，类型／章节／处理状态筛选，多选、原文定位、范围预览和关联知识查看。
- 标题动态覆盖、整块随内容编辑变化、范围重叠去重、单次排除和标题持久局部排除。
- 笔记编辑后的可靠重定位、边界变更提示、版本摘录保留、内容待检查及重新选择来源。
- 分析范围预览与不可变范围快照；无标注时可选择选区、章节、整篇、多篇，文件夹／标签先展开实际笔记清单。
- 标记、证据和下游影响在 local-json／PostgreSQL 中保持一致，迁移保留旧数据。

### 2.2 与 AI／知识模块的交接边界

基础包必须实现真实可用的“提炼知识”范围确认面板、范围快照及关联查询。AI 不可用时，面板明确显示“提炼服务暂不可用”，允许继续管理标记；不能显示生成成功或用假候选填充处理状态。

后续提炼包接收本文定义的快照，完成实际任务、候选写入、候选确认及关联回传。联调时必须验证三种标记共用一个入口且无标注也能提炼。仅有范围预览时，交付记录必须写“基础标记完成，AI 提炼接入未完成”，FR-M01／M04／M06／M08 涉及真实提炼的端到端验收仍未完成。

本次不实现完整知识图谱、组卷、掌握算法、考试优先级推断或模型供应商选择；只修正标记引发的来源影响，不借此重建整个知识系统。

### 3.1 与旧方案冲突时的明确决策

1. **取消重点不是否定来源。** 旧代码“归档标注 → Evidence invalid”不能直接沿用。若笔记／版本摘录仍可用且内容未变，仅移除阅读重点，不自动撤销已确认知识，也不因此统一禁用题目。
2. **重新定位不是改写历史。** 不按现状文档建议把所有历史 Evidence 的版本、摘录、标题路径直接同步成新值。新增当前定位或证据修订，原分析依据始终保留。
3. **整篇哈希变化不等于每项知识内容变化。** 原哈希可用于并发校验，但变化影响应按标记有效覆盖和引用内容计算。
4. **三种范围都是首期基础标记。** 不沿用旧 Phase2.0 “章节只预留接口”的范围限制。
5. **标注不是唯一来源。** 不能强制先创建标注才能分析整篇或创建知识。

## 4. 产品规则与页面操作

### 4.1 创建与展示

- 用户文案统一为“标为重点”，原“标记为重要内容”入口接入同一命令。默认 `kind=important`，重要程度未设置，不要求弹窗输入标题。
- 选区：菜单打开时捕获选区，焦点移入菜单后仍使用该选区；空选区禁用。跨段连续文字仍是一个选区标记，不自动升级成内容块。
- 块：块操作菜单提供“将此块设为重点”；相邻块选择工具支持多块。部分文本选择时可明确选择“标记选区”或“标记所在块”，不得静默扩大范围。
- 标题：标题旁和大纲项提供“将本节设为重点”，图标表示已标记；预览展示起止标题、包含块数、排除内容和当前版本。
- 样式：选区用轻量底色；块用边线／图标；章节用标题标识及预览。不修改 Markdown 语法、不借用代码围栏、不把正文复制到另一篇笔记。摘录是版本证据，不是另一份可编辑正文。
- 重叠处显示可展开的标记列表；点击不能任意选中其中一个。取消一个标记只移除该标记装饰，剩余标记继续生效。

### 4.2 块与标题的范围定义

- 首版块单位：段落、列表项及其子树、整个引用块、整个代码块、整个块公式、整个表格。列表整体可视为连续列表项集合；表格单元格内的文字支持选区，整块菜单标记整表。
- 多块须在规范化文档顺序中相邻；祖先与子孙不能重复计入同一块集合。混合层级选择先预览提升到的公共连续块边界，再由用户确认。
- 内容块后续编辑仍属于该块。拆分时保留原范围内的后继块映射；合并含未标记邻块、跨章节移动或无法判定继承关系时提示范围变化，确认前不扩大可分析范围。
- 章节从标题节点开始，到下一处层级小于等于该标题的节点之前结束。代码围栏内的 `#` 不视作标题，支持编辑器实际支持的标题语法。
- 本节正常新增正文自动纳入，不逐次弹确认；改标题层级、移动标题、章节拆合或删除结束边界导致覆盖成员变化时进入范围待确认，展示旧／新预览。确认前不能以扩大后的范围启动分析。
- 标题文字重命名但身份和边界稳定时只更新显示路径；标题被删除不把下一标题当替代，更不退化成整篇。

### 4.3 类型、备注和重要程度

| 字段 | 可选值 | 规则 |
| --- | --- | --- |
| kind | `important` 重点、`question` 疑问、`supplement` 补充、`pitfall` 易错、`temporary` 临时笔记 | 兼容现有 important；默认只填类型 |
| importance | `null` 未设置、`normal` 普通、`important` 重要、`core` 核心 | 与 kind 独立；null 不显示成“重要” |
| comment | 可选备注 | 纯文本安全呈现，可清空；不是来源正文 |

备注和疑问作为用户意图传给提炼服务，不作为原文事实。易错不写入掌握证据，核心不等于考试高频。首版建议备注限制 2,000 字符、批量选择上限 100 条；这些是本方案工程默认值，可配置且超限明确提示，不截断保存。

### 4.4 重点清单

复用笔记右侧检查器，避免新增一级导航。显示摘要、范围类型、章节路径、备注、类型、可选重要程度、定位状态、处理状态及关联数量。支持按类型／章节／处理状态组合筛选；无标题项归“未分章节”，归档项默认隐藏并可单独查看。

操作包括定位、预览、编辑、取消重点、恢复、重新选择来源、查看关联知识、多选提炼。批量取消使用项目确认弹窗，说明正文和已有知识保留；单条取消提供撤销入口。空清单提示可以直接分析当前选区或整篇；加载失败、只读缓存、保存中、定位失效分别显示，不能当作空数据。

处理状态不由用户手动切换：

- 无候选或知识关联：未提炼。
- 存在有效候选关联：已有候选。
- 存在已确认知识关联：已关联知识。
- 当前有效覆盖相对分析快照有变化：额外显示“内容变更待检查”。

“已有候选”与“已关联知识”允许同时出现并显示数量；内容变化为独立提醒。候选被忽略后无其他关联可回到未提炼，但保留历史处理记录供提炼服务去重。AI 任务进行中／失败是任务状态，不覆盖上述状态。仅存在源笔记相同的 Evidence，不能推断它来自该标注。

## 5. 数据契约与持久化设计

### 5.1 增量扩展 ContentAnnotation

保留原 ID、noteId、spaceId、createdAt 和现有 NoteVersion。新增字段由两驱动统一校验：

| 字段 | 拟定含义 |
| --- | --- |
| `schemaVersion` | 新格式为 2；旧记录为 1，不混用坐标 |
| `scopeType` | `selection / blocks / section` |
| `kind / importance / comment` | 阅读关注元数据 |
| `lifecycleStatus` | `active / archived`，表示标记是否启用 |
| `anchorStatus` | `resolved / needsReview / missing`，分别为可靠定位／歧义或边界待确认／无可用位置 |
| `anchorReason` | 如 `ambiguousMatch / boundaryChanged / sourceDeleted / legacyUnverified` |
| `revision` | 标注乐观锁整数；所有修改自增 |
| `anchor` | 当前版本中的权威定位描述，含格式版本、版本 ID、范围、上下文及结构指纹 |
| `originSnapshot` | 创建时版本、范围、摘录和内容摘要；不可随正文编辑覆盖 |
| `resolvedContentHash` | 当前有效覆盖内容摘要，用于比较分析来源变化 |
| `boundaryFingerprint` | 章节起止身份、层级及成员摘要；不只保存标题文字 |

旧 `status` 仅由新字段投影：archived 优先，其余 resolved → active，非 resolved → stale。禁止旧、新状态各自维护。现有 quoteText、headingPath、fromPosition 等旧字段保留兼容读；新客户端以 schemaVersion 与 anchor 为准，旧坐标不重新解释成新坐标。

### 5.2 排除、修订和范围快照

新增下列逻辑记录，实体命名可沿项目约定微调，但语义必须保留：

- `AnnotationExclusion`：id、parentAnnotationId、版本化 anchor、状态和修订号。仅允许挂到 section 标记；删除父标记时随父标记隐藏，恢复后重新校验。
- `AnnotationRevision`：annotationId、revision、操作类型、旧／新定位与范围摘要、时间、原因。保存重定位和边界确认依据，不要求逐键保存全部正文副本。
- `AnalysisScopeSnapshot`：不可变的笔记版本集合、选择项、有效片段、独立上下文、排除项、未纳入项、关联标注修订、摘要及创建时间。它是提炼任务输入；不是 KnowledgeItem，也不是任务已启动的证明。
- Evidence 扩展当前定位／内容检查原因和修订引用，或增加独立来源修订记录。原 noteVersionId、quoteText、headingPath 表示当时依据，不能批量改成最新正文。

local-json 增加集合与引用校验，保留一次原子快照提交。PostgreSQL 增量 migration 加字段／表、外键、索引；范围 JSON 在应用层做完整 schema 校验。索引至少覆盖 `(noteId, lifecycleStatus)`、`(parentAnnotationId)`、`(annotationId, revision)`；幂等仍使用现有 `(noteId, idempotencyKey)` 唯一约束。

扩展永久删除预检：NoteVersion 被分析任务／候选／正式证据引用时保留保护，不因新表未纳入检查而级联丢失历史。未启动任务且无下游引用的范围草稿快照可显式清理；已有任务引用的快照不可作为普通缓存清理。清空回收站仍先整批预检，新增排除和修订记录纳入同一删除事务。整库导入导出与迁移继续使用已有维护互斥协议。

### 5.3 定位状态与知识健康独立

| 事件 | 标记结果 | 证据／知识结果 |
| --- | --- | --- |
| 取消重点 | archived；保存原定位 | 正文和历史摘录存在时不因取消本身设 invalid |
| 恢复重点 | 对当前版本重新解析后 resolved 或 needsReview/missing | 按来源实际状态重算；不批量把证据设 valid |
| 可靠位置前移，内容未变 | 更新当前 anchor | 保留历史依据，不标实质变化 |
| 排版变化导致位置不明 | needsReview，显示旧摘录 | 提示定位确认；确认内容一致后解除对应阻断 |
| 公式／论点或有效范围内容变化 | 当前定位可 resolved | 关联内容待检查，旧知识不自动改写 |
| 笔记删除／唯一来源不可用 | missing，显示来源删除 | 来源不足；保留知识及历史依据 |
| 多来源之一失效 | 显示该来源异常 | 重算剩余依据，不统一停用整项知识 |
| 人工选中新来源 | 新增 anchor 修订 | 内容不同则仍需知识复核；不能靠重新定位解除实质冲突 |

算法只判断精确内容相等、结构等价或发生变化，不声称自动证明“语义仍正确”。无法证明仅格式变化时要求用户比较后确认。疑问、临时笔记等类型变化不会产生学习表现证据。

## 6. 定位与范围解析的实施方案

### 6.1 先建立可验证坐标，不在旧位置上打补丁

当前 `fromPosition/toPosition` 是 ProseMirror 结构坐标，正文却是 Markdown。**禁止用 `rawMarkdown.slice(fromPosition, toPosition)` 校验旧标注，也禁止只检查正文中包含 quoteText。**

新格式采用以下实现方向：

1. 建立无 DOM、无 React 的 Markdown 来源投影模块，输出结构树、文本／原子节点、原文 offset 和结构路径。建议放入独立 `packages/content-anchor` 工作区，以 Node 可运行的 ESM 实现及类型声明供 API／V4 共同消费；`web-core` 仅保留 DTO，不直接依赖编辑器。
2. 统一 Markdown 方言、换行和 offset 规则：版本正文按实际保存的字符串计算 SHA-256；位置采用该字符串的 UTF-16 半开区间 `[start,end)`，不做隐式 trim。显示摘录可裁剪，校验文本不得裁剪。CRLF 转换须发生在保存前并纳入版本，不能只在校验一侧转换。
3. V4 适配层把编辑器选区／块／标题映射到“已保存的版本正文”来源投影。富文本标记分隔符可能使一个连续可见选区对应多个 source segment；允许多个 segment 表示一个连续逻辑选区，但不能借此提交不连续用户选区。
4. 服务端从自己的 NoteVersion 原文重建投影，校验连续性、越界、节点类型、quote 的规范投影、结构身份、版本与空间。摘录、标题路径、指纹由服务端计算，客户端值只能用于一致性断言。
5. 代码、公式和表格保留原始语法片段和块类型，不能压扁成普通字符串后丢失含义。图片／附件作为原子对象列明是否可读；基础包不具备识别能力时写入未纳入项。

先做“保存→解析→选区映射→重载”的小型验证，再确定解析器依赖。必须覆盖加粗跨节点、链接、转义、中文、emoji、列表嵌套、代码、公式、表格和标题；全部可验证后才扩展 UI。若现有 Milkdown 自定义语法无法映射，补其适配规则，不能退回首个文本匹配。解析器升级须显式升级 projectionVersion 并验证旧版本读取。

### 6.2 编辑后的跟随规则

- 同一编辑会话使用 transaction mapping 跟踪范围和节点；这只是前端即时装饰，不是服务端已经保存的事实。
- 保存时提交基础版本及受影响的 anchor 映射建议；服务端从旧／新投影验证差异并写入新版本，不能直接信任客户端映射。
- 选区边界采用不向外吸附的策略：范围内部插入跟随并标内容变化；起点之前／终点之后插入不纳入。选区被完整删除则 missing，不吸附附近文本。
- 块／标题的逻辑身份保存在版本定位侧表或修订映射中，不写入用户 Markdown。可靠的前后结构映射可继承身份；复制产生新身份，剪切移动能可靠追踪才继承。
- 重载／外部导入时先验证版本和精确范围，再用摘录、前后文、标题路径、相邻结构联合生成候选。只有可证明唯一且一致的候选才自动解析；重复标题、重复公式、多候选一律 needsReview，供用户选择。
- 不能可靠判断块拆合、标题边界或排除位置时保留旧摘录并暂停该项分析；不要悄悄忽略失效排除，从而扩大范围。

### 6.3 分析去重与排除优先级

范围解析由服务端作为权威，预览与任务启动复用同一 resolver：

1. 确认 noteId、NoteVersion、标记 revision 和本次实际笔记集合；跨笔记分别计算，不能把不同笔记的相同文字合并丢失来源。
2. 解析显式选区、块、章节／整篇范围；标题范围递归覆盖至规定结束边界。
3. 对每个被选标题先减去其持久局部排除。父标题的排除不能被子标题继承范围重新加入；另一标题重叠继承也不能绕过排除。
4. 若用户显式选择的选区或块与持久排除重叠，展示“此内容已被排除，是否仅本次重新纳入”。默认保持排除；用户确认后写入本次 override。直接分析被排除的选区同样适用。
5. 合并剩余覆盖为有序不重复片段，最后减去本次排除。本次排除优先于此前 override；再次改变选择须重新预览。
6. 保留片段到全部贡献 annotationId 的多对多映射、各自备注／类型；去重正文不删除标注。元数据冲突原样保留，不让一个“重点”覆盖另一条“疑问”。
7. 需要的上下文放入独立 `contextSegments`；明确排除的内容默认也不能作为上下文读取。上下文不足时提示扩大，不能越过排除偷读。
8. 固定快照；后续新增段落、文件夹新加笔记不改变已有快照。开始分析时若预览版本已变化，返回冲突要求刷新；分析启动后变化则在结果标注“基于开始时版本”。

示例：标题 S 覆盖 A、B、C，持久排除 B；另有块标记覆盖 B、C。选择两条标记时默认覆盖 A、C，并提示 B 冲突；明确本次纳入 B 后覆盖 A、B、C，正文各一次，保留 S 和块标记两个来源关联。若再单次排除 C，最终为 A、B。

## 7. API 与后端工作包

下列新接口为拟定契约；沿用 `/api/knowledge`、成功 `{ data }`、失败 `{ error: { code, message } }`。所有读写均通过现有 owner／space 校验链，不接受客户端 owner 覆盖；标记、排除、知识、版本之间必须属于同一可访问空间。

| 接口 | 操作与约束 |
| --- | --- |
| 现有 `POST /annotations` | 接受新 schemaVersion、scopeType、anchor、kind、comment、importance、noteContentHash、idempotencyKey；服务端绑定版本 |
| 现有 `GET /annotations`、`GET /annotations/:id` | 保留旧数组契约；增加可选类型／章节／处理状态过滤，返回新状态和关联摘要；分页另设显式版本，不静默改变 data 形状 |
| 新增 `PATCH /annotations/:id` | 修改类型、备注、重要程度；携带 expectedRevision，不允许借元数据接口替换来源 |
| 现有 `DELETE /annotations/:id`、`POST /annotations/:id/restore` | 取消／恢复；按 revision 校验；恢复重算当前来源 |
| 现有 `PATCH /annotations/:id/anchor` | 显式重定位，包含 expectedRevision 和新版本；生成修订，不覆盖历史 Evidence |
| 新增 `POST /annotations/:id/confirm-range` | 确认服务端给出的边界变化；绑定预览版本／修订，过期不能确认 |
| 新增 `GET /annotations/:id/preview` | 当前覆盖与排除、旧／新边界、定位问题；只读，不偷偷修复数据 |
| 新增 `POST /annotations/:id/exclusions`、`DELETE /annotations/:id/exclusions/:exclusionId` | 持久局部排除；校验父标题、范围和 revision；新建返回服务端权威锚点 |
| 新增 `GET /annotations/:id/knowledge-links` | 返回真实候选／已确认知识及 Evidence 来源状态，供清单计数和详情回链 |
| 新增 `POST /analysis-scopes/preview` | 只解析预览；返回 note/version 集合、范围片段、上下文、排除冲突和未纳入项，不调 AI |
| 新增 `POST /analysis-scopes` | 按相同输入加预览版本和幂等键保存不可变快照，返回 snapshotId；本身不启动 AI |
| 新增 `GET /analysis-scopes/:id` | 读取范围快照；权限按快照所属空间，来源当前不可用时保留历史说明 |

建议错误码：`ANNOTATION_RANGE_INVALID`、`ANNOTATION_QUOTE_MISMATCH`、`ANNOTATION_CONTENT_CONFLICT`、`ANNOTATION_REVISION_CONFLICT`、`ANNOTATION_ANCHOR_UNRESOLVED`、`ANNOTATION_EXCLUSION_CONFLICT`、`ANALYSIS_SCOPE_EMPTY`。输入不合法为 400，不存在为 404，版本／范围冲突为 409。沿用现有空间拒绝语义，不能泄露其他空间摘要。

### 7.1 创建与并发控制

- 保存正文成功后获取权威版本／哈希，再提交该版本的范围。保存途中继续输入时重新映射到保存版本或取消本次创建并提示重选，不把新位置配给旧哈希。
- 一次用户操作生成一个幂等键，网络重试复用；服务端保存 requestHash。同键同参数返回原结果，同键不同参数报冲突。
- 区分技术重试与业务重复：同范围同类型的重复创建返回已有项或明确重复；同一范围不同类型允许分别存在，范围重叠合法。归档后再次标记提供恢复原项或明确新建，不能被旧唯一判断永久阻断。
- Note 保存与标注创建／更新遵循一致锁顺序。PostgreSQL 在事务中锁定／条件更新对应 Note 版本及标注 revision，防止“检查后正文被其他请求更新”竞态；JSON 在事务内做同样检查。

### 7.2 写入和来源传播必须原子化

用应用层 `annotation-change-coordinator`（拟新增）协调：读取当前版本 → 校验 → 更新标注／排除／修订 → 计算 Evidence 当前状态 → 重算受影响 KnowledgeItem／QuestionSource 门禁 → 提交。具体领域计算仍各归原服务。

PostgreSQL 复用模块 runTransaction，并给所有参与者注入同一事务 repository；禁止回调闭包继续使用事务外 repository。local-json 通过 `dataStore.runTransaction()` 一次提交，保留引用校验和回滚。纯解析可先在事务外计算，但事务内须复核版本；AI、网络、附件 IO 不在数据库事务内。

批量取消以整批原子提交为默认；若超出批量上限明确拒绝。返回最新 revision、状态和关联摘要，前端提交后更新清单与装饰，再按正文版本刷新受影响查询。

取消标记不改写历史试卷。来源实质变化只作用于当前可用性及受影响知识／目标；涉及下游未实现状态时返回结构化影响结果并记录联调缺口，不能假称已暂停正式出卷。

## 8. V4 实施结构与状态同步

建议沿现有目录按职责拆分，以下为拟新增职责，不要求把所有内容塞进 NoteEditorView：

- `annotationCommands`：统一创建、取消、恢复、元数据修改和错误处理。
- `annotationAnchorAdapter`：ProseMirror 与版本来源投影互转；不承担 API 写入。
- `annotationDecorations`：选区、块和标题装饰、重叠标记命中及焦点。
- `useAnnotationController`：按 noteId／版本／revision 管理加载与变更，替换分散的本地数组更新。
- `AnnotationList`、`AnnotationDetails`、`AnnotationScopePreview`：清单、详情、边界／排除确认，复用 `components/ui/`。
- `AnalysisScopeDialog`：统一范围确认及 AI 可用性，接收三种标注或无标注选择。

状态同步要求：

1. 草稿编辑时装饰通过 transaction mapping 更新并标为未保存；保存失败不展示持久化成功。
2. 保存成功后刷新本笔记标注、范围预览、关联状态；缓存 key 含当前内容版本。清单与正文不得一个显示已定位、另一个待确认。
3. 切换笔记取消旧请求或使用序列号；旧 mutation 响应不写进新笔记。检查器关闭时仍维护正文装饰，重新打开显示最新状态。
4. API 失败时保留草稿和用户备注；冲突提供刷新后重试，不能自动用旧 anchor 覆盖服务器。
5. 标记操作不污染 Markdown 撤销栈。取消后的“撤销”执行恢复 API；正文 Ctrl/Cmd+Z 撤销编辑后重新映射标记，两类历史不混淆。
6. 只读、缓存恢复、保存中、笔记已删除时禁止标记写入；阅读和旧摘录查看继续可用。
7. 可用键盘进入菜单、清单和预览，状态不只靠颜色；关闭弹窗焦点回到原入口。长备注、窄窗口、长表格不挤破独立滚动区域。

## 9. 迁移、兼容和回退

### 9.1 旧数据迁移

1. 备份 JSON／数据库和 schema 版本；使用副本 dry-run，输出总数、可确认数、需人工确认数、非法引用和失败原因，不修改真实 storage 验证。
2. 旧记录映射为 scopeType=selection、kind=important、importance=null、comment 为空；archived 生命周期保留。
3. 旧位置标明 `legacy-prosemirror`。仅当能通过旧版本解析器重建并验证时转换；否则保留 legacy anchor、原摘录和版本，标 needsReview，不能在 Markdown 中查首个同文回填。
4. originSnapshot 使用可靠绑定的原 NoteVersion；没有历史版本的记录保留原始摘录与“历史版本缺失”原因，不能把当前版本伪装成创建版本。
5. 旧 Evidence 的 invalid/stale 缺少原因时不自动改 valid；生成复核清单。能证明只是取消标记且来源未变的才按新规则恢复对应来源健康，记录修订。
6. JSON schema、加载器、导入导出、snapshot validator、PostgreSQL migration、JSON→PG 迁移脚本同步支持新集合和字段。迁移必须可重跑，不重复生成 ID 或修订。

### 9.2 发布与回退规则

先部署可读新旧格式的兼容后端，再开新 UI。旧客户端只能修改可兼容的旧选区；遇到新 blocks／section 写操作明确要求升级，不能降格成 selection 覆盖。

功能开关关闭后仍保留新数据和只读查看。应用回退只能到支持 schema v2 读取的版本；不能以删除新增字段／表作为在线回滚。彻底回到旧 schema 需恢复对应备份，并明确备份之后的写入处理方式。部署和生产切换是后续实施动作，本方案不执行。

推荐每阶段一个可审查提交，提交说明用中文 Conventional Commits；不自动发版或打 tag。结构性实施变更记入 `docs/工程变更日志.md`，新目录边界更新项目结构导航。此次仅新增开发方案，无需伪造工程功能交付记录。

### 11.2 自动化验证分层

- 纯函数：坐标投影、范围边界、区间并差、排除优先级、重叠来源映射、重复文本候选、状态派生。断言用户范围含义，不只断言内部对象结构。
- API runner：双驱动契约、伪造 quote、跨空间引用、并发版本冲突、备注／类型编辑、恢复与重新定位的不同路径、关系查询、不可变快照。
- 事务集成：在标注保存后、Evidence 更新后、下游状态更新前分别注入异常，重启后核对全部回滚。PG 必须使用隔离测试库、真实事务和并发请求；mock repository 测试不能替代。
- 迁移：旧数据缺版本、重复文本、归档标记、无原因 invalid、局部排除失效、新数据导入导出、重复迁移不新增记录。
- V4：菜单丢焦点、保存期间继续输入、清单刷新、请求乱序、重叠点击、状态无障碍和窄屏；E2E 对真实 API 验证保存／重载。
