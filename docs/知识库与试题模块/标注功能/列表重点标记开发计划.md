# 列表重点标记开发计划

> 日期：2026-09-30  
> 状态：已按 L0–L5 实施；实际验证、运行限制和人工待验项见[列表重点标记验收记录](列表重点标记验收记录.md)。
> 目标：为有序、无序列表添加独立列表标记，覆盖当前列表项及其全部子项，沿用章节标记的结构跟随、范围确认和来源保护原则。  
> 工作量：初步估计 5–8 人日；包含局部排除、持久化和同步回归，实际耗时取决于结构映射及保存问题排查结果。

## 1. 需求与交付边界

### 1.1 已确认的产品决定

- 新标记属于独立的“列表项”范围，保存为 `scopeType: 'list'`，不属于选区或内容块。
- 标记根是用户操作的当前列表项，范围包含自身的全部正文、续接段落、嵌套内容和所有子列表项；不包含相邻同级项。
- 有序、无序列表共用同一范围类型。混合嵌套同样适用，不能用数字编号或项目符号判断身份。
- 正常内容编辑与新增子项自动跟随；不能可靠判断的身份或范围变化进入待确认。
- 保留标注 ID、备注、重要程度、知识关联和原始来源快照；历史 Evidence、NoteVersion 与分析范围快照不随正文改写。

需求来源是用户对[现有问题第一点](../../../现有问题.md)的后续修订，优先于该文件仍写着“属于选区标记”的旧描述。执行本计划不自动修改问题清单。

### 1.2 本计划采用的默认范围

- 首版包含列表标记的局部排除和恢复排除，复用章节的范围预览与确认流程。这是为落实“规则沿用章节标记”选定的默认范围。
- 任务列表暂不提供新列表标记入口；已存在的选区、块标记照常使用。未来任务列表支持单独扩展。
- 保留现有“标记此块为重点”和手动选区入口，不将历史列表上的块标记或选区标记自动转换。
- 不新增整份列表标记、跨列表集合标记或跨笔记移动继承，不接入新的 AI 调用。
- 图片、附件和表格沿用现有正文投影能力；附件二进制不进入标注摘录。本计划不承担问题清单第二点的功能完善。
- 第三点“保存失败”作为关联回归检查：复现后记录具体失败阶段，仅修复会阻断本功能或造成来源不一致的问题，不能提前宣称已定位或已修复。

### 1.3 范围示例

```text
1. 卷积层                 ← 标记此列表项
   卷积层的说明            ✓ 包含
   - 卷积核                ✓ 包含
   - 步幅                  ✓ 包含
     - 步幅示例            ✓ 包含
2. 池化层                 × 不包含
```

范围以 Markdown AST 中该 `listItem` 的完整子树为准，不能简单扫描到下一个编号或换行。子项内的引用、代码、表格及标题仍属于子树，标题不截断列表标记。

## 2. 产品行为与状态规则

| 操作或状态 | 确定行为 |
| --- | --- |
| 修改自身正文、行内格式或在项末追加文字 | 根身份稳定时保持 `resolved`，重新计算完整子树 |
| 在范围内新建子项或续接段落 | 自动纳入；无需逐次确认 |
| 删除部分正文或子项，根项仍存在 | 自动缩小范围；被删除的独立子标记按自己的生命周期处理 |
| 在前后添加同级项、按 Enter 创建下一个同级项 | 新同级项不纳入；当前标记保持 |
| 改变有序起始编号，或在有序与无序之间切换 | 可验证为同一项及子树时保留；不因编号、符号或路径下标变化换绑 |
| 调整根项缩进或取消缩进 | 若父子关系改变，进入 `needsReview`，提供新范围候选 |
| 将原范围外已有项缩进为当前项的子项 | 覆盖成员扩大，进入范围待确认；与直接新建子项区别处理 |
| 将原子项移出范围或重新归属 | 因结构调整改变覆盖成员时待确认；明确删除子项仍自动缩小 |
| 拆分、合并列表项 | 根身份与原成员归属可证明且不吸收其他项时跟随；否则待确认，不自动降为选区 |
| 同笔记剪切、粘贴整个子树 | 使用现有一次性移动凭据；身份可靠且层级、成员关系保持时自动跟随；否则待确认 |
| 复制列表项或粘贴到另一笔记 | 副本获得新结构身份，不继承原标记；原标记不换绑 |
| 删除根项 | `missing`，保留历史、备注和关联，不标记下一项；重新输入相同文字不自动复活 |
| 去掉列表格式，变成普通段落 | `needsReview`，显示“列表结构已变化”；无合法列表候选时禁用范围确认，允许重新定位到列表项或取消重点 |
| 清空文字但编辑器仍保留空列表项 | 已有标记保留为空结构标记；同项重新输入跟随。空项不允许新建标记或发起分析 |
| 根项成为空项且 Markdown 序列化删除了该结构 | 按实际结构消失处理，不合成占位项；若不能确定身份则待确认 |
| 原始版本缺失、映射不合法、重复内容无法区分 | 待确认，不按第一处相同文字猜测绑定，不阻断普通正文保存 |
| 待确认期间继续编辑 | 待确认保持；候选按当前版本刷新，不能通过一次普通保存自动消除待确认 |
| 撤销、重做、历史恢复 | 基于已有事务和版本记录恢复原身份、范围与状态；不能仅凭文本相同恢复 |
| 取消与恢复重点 | 使用现有标注生命周期；恢复时重算结构，不直接强制设为可定位；取消不删除关联知识 |

父项与子项可以分别标记，列表标记也可与章节、块、选区重叠。沿用重叠标记清单、独立取消和分析片段去重；取消父标记不取消子标记。

局部排除只影响所属列表标记的有效分析范围，不改变原文或独立子标记。排除项必须位于当前可定位的子树内；排除范围移动、删除或无法跟随后进入原有冲突流程，修复前不得默默纳入分析。范围确认后再次检查排除项的包含关系。

## 3. 技术方案与契约

### 3.1 当前代码基线

| 子系统 | 已有能力 | 本次必须补齐 |
| --- | --- | --- |
| V4 编辑器 | 选区工具、块悬浮菜单、章节标记、事务映射 | 明确识别当前 `list_item`，新增列表入口和实时子树装饰 |
| `packages/content-anchor` | Markdown AST 投影含 `listItem`、块身份侧数据、动态章节跟随 | 列表层级投影、列表锚点和结构身份跟随；避免通用文本重定位破坏子树边界 |
| 标注应用服务 | JSON/SQLite 共用服务、PostgreSQL 异步服务、版本校验和修订 | 四种范围一致校验、结构重算、列表恢复/重定位/确认及排除 |
| 范围确认 | 已有 `preview`、`confirm-range` 与过期候选检查 | 列表候选和新旧子树预览，无需新增确认路由 |
| 持久化/导入 | `scopeType` 是字符串，锚点是 JSON | 扩展白名单与引用规则；当前局部排除校验只接受章节 |
| 桌面同步 | 关联实体组、来源校验与版本别名回写 | 传输列表锚点和排除；升级格式门槛，防止旧应用按普通选区处理 |

不要依据历史验收中的通过数判断新范围已经可用。执行前重新检查工作区，保留现有同步、省电等未提交改动，提交时只纳入本功能文件。

### 3.2 共享类型与锚点

- 扩展统一 `AnnotationScopeType` 为 `'selection' | 'blocks' | 'section' | 'list'`；同步更新 web-core、编辑器命令/回调、DTO 和全部范围白名单。新增代码使用共享类型，逐步替换受影响位置的重复联合类型。
- 继续使用 `ContentAnnotation` 和 `schemaVersion: 2`。`kind`、`importance`、生命周期、定位状态含义不变；“列表”是范围类型，不是新的标注内容类型。
- `MarkdownProjection` 增加 `listItems`，每项提供 `path`、`parentListPath`、`parentItemPath`、`depth`、`ordered`、`sourceStart`、`sourceEnd`。利用 AST 父链生成，不将 ProseMirror 路径直接当作 Markdown AST 路径。
- `ContentAnchor` 增加可选 `list` 元数据：`itemPath`、`parentItemPath`、`depth`、`ordered`、`memberFingerprint`。`structurePath` 指向根列表项，`sourceStart/sourceEnd` 覆盖完整根子树，`segments/quoteText` 使用现有可见正文投影生成。
- 结构跟踪扩展 `tracking.rootId`、`tracking.ancestorItemIds`，复用已有 `memberIds/structureRevision`。ID 来自服务端 `Note.annotationStructure` 中的 `listItem` 节点；父链和成员指纹只表达结构身份与归属，不把正文文字变化当成范围变化。
- 客户端只提交当前范围的一致性断言；创建、确认和保存后的最终列表元数据、身份及范围由服务端生成。DTO 的 `scopeType` 与 `anchor.scopeType` 必须一致。
- 保留 `MARKDOWN_PROJECTION_VERSION` 的现有文字投影规则；只增加列表结构信息，不改变旧范围的可见文字和偏移语义。

### 3.3 范围生成、解析与动态跟随

在 content-anchor 内按职责增加列表投影/锚点模块，避免将所有规则堆进已有入口或动态跟随文件。

1. 增加 `anchorForListItem(projection, itemPath)`：验证根为普通有序/无序列表项，生成完整子树锚点；空可见正文拒绝创建。
2. 增加 `followListAnchor(markdown, anchor)`：供预览和恢复使用；严格核对完整子树和列表结构，不能把任意相似文字当成列表标记。
3. 增加 `followListAnchorChanges(before, after, anchor, edits, structures)`：`structures` 提供前后结构侧数据。基于根 ID、父链、成员归属与经过验证的逐步编辑，执行第 2 节规则。
4. `prepareAnnotationChange` 保留旧结构并提供新结构；`reconcileAnnotationSource` 对 `list` 分派至列表跟随函数，其余三种范围保持现有行为。
5. `updateStructure` 补足列表项末尾插入、编号/列表类型转换和可验证移动时的身份继承。不得因范围末尾插入的 association 规则丢失根 ID；不得让同一旧 ID 被多个新项继承。
6. 允许明确的新内容生成新成员 ID 并自动纳入；已有外部成员被结构调整吸收时生成待确认候选。纯路径下标变化不要求确认。
7. 列表标记不能走普通 `relocateAnchor` 的任意摘录匹配兜底。没有可靠身份时只产生合法列表候选；多候选不自动选第一个。
8. 已有空列表项沿用空锚点跟踪，但必须验证根结构存在。扩展解析、持久化及同步的空锚点准入，不把任意空范围视为合法。

前端事务映射负责当前文档即时反馈；服务端使用正文哈希约束的编辑日志和结构身份做最终裁决。序列化末尾换行与内部编辑分别映射。两端在正常增删与结构变化时应得到一致范围；不确定时不展示扩大后的正常高亮。

### 3.4 API、事务与来源保护

- 复用现有创建标注、更新锚点、取消/恢复、范围预览、`POST /api/knowledge/annotations/:id/confirm-range`、排除和分析范围接口；不新增列表专用 CRUD。
- 服务端拒绝伪造子树、跨同级项范围、范围类型不一致、过期正文、非法版本或非列表根。沿用现有错误封装及范围/冲突错误码。
- `assertCurrentNote`、`authoritativeAnchor` 和 PostgreSQL 对等实现都核对列表结构，写入完整版本引用与服务端生成的身份，不信任提交的 `rootId/memberIds`。
- `reconciledAnnotationFields` 的边界指纹支持 `list.memberFingerprint`；修订记录保存新旧列表锚点，原始快照保持不变。
- 待确认使用已有 `pending`、`candidateHash`、`expectedRevision` 与 `noteContentHash`。合法当前子树候选才能确认；过期确认返回 409 并刷新预览。
- 将章节专属的局部排除准入扩展为 `section/list`，同时修改范围解析、JSON 引用验证、导入校验及 PostgreSQL 服务；父项待确认时拒绝新增排除。
- 普通正文保存、结构侧数据、标注修订、排除及关联来源健康更新沿用当前应用协调器事务提交。合法旧来源失效记为待确认/删除，不让定位错误使正文保存失败；存储错误和真实事务失败仍按原逻辑回滚并保留草稿。
- 范围候选尚未确认或空子树不能发起分析。原有已确认知识按来源内容健康规则要求复核，不能自动删除或改写历史依据。

### 3.5 UI 与保存时序

- 在当前列表项的悬浮重点菜单增加“标记此列表项为重点”，菜单说明“包含本项及全部子项”；点击子项以最近的 `list_item` 为根。
- 不用当前 DOM `closest('p,...,li')` 返回的段落直接决定列表范围；从目标对应的编辑器位置向祖先查找列表项，并核对节点归属。任务列表不显示新入口。
- 菜单开启时捕获根项与文档基线，焦点进入菜单后保持。文档变化时通过事务映射更新目标；失效时明确提示重新选择，不能借当前光标标记另一项。
- 复用 `EditorAnnotationActions`、项目 Menu/Button/Dialog 和现有 tokens。快捷入口与根项第一行对齐，滚动、换行、窄屏和嵌套缩进后仍可操作。
- 根项提供重点状态提示；正文沿用现有标注装饰，覆盖子树内可见内容，不覆盖列表外空白或相邻项。重叠区域仍可查看全部标注。
- 检查器新增“列表项”范围分类、计数和标签；详情展示根项摘要、子项数量、当前范围、排除和定位状态。
- 待确认详情复用新旧范围预览与确认控件，无合法候选时禁用确认并提示重新定位；重新定位仍要求完整列表项子树，不降为选区。
- 创建沿用“读取当前正文 → 保存 → 基于同一正文生成标注请求”。保存期间若用户继续编辑，已捕获范围与正文必须对应同一批次；发生版本冲突时保留编辑内容并提示重试。
- pending 期间阻止重复触发，同一创建请求重试复用幂等键；失败不提前显示“已标为重点”，不产生重复清单项。

### 3.6 存储、同步与兼容

- PostgreSQL 已使用字符串范围和 JSON 锚点，本计划不增加表或列，不预设 DDL migration。JSON/SQLite 的保存、恢复、备份、导入及来源验证都必须识别 `list`。
- 本地逻辑数据格式 `LOCAL_DATA_SCHEMA_VERSION` 从当前 5 升至 6，新读取器接受 1–6；旧标注保持原类型，不执行批量范围转换。快照容器版本及 SQLite 物理表版本不因这次纯 JSON 字段扩展机械升级。
- 同步握手 `entitySchemaVersion` 从 5 升至 6，保持现有 protocolVersion。新版客户端要求实体格式 6；旧客户端按现有精确版本门槛拒绝同步，避免旧跟随算法处理列表范围。
- 服务端先升级格式准入与跟随能力，再更新桌面客户端和 Web；同步世代、游标、待发送队列和资料集身份保持原值，不借升级清空冲突或重置资料库。
- 联动更新所有写死版本 5 的同步校验与测试；错误提示明确“同步格式已升级，请更新应用”，不得报告本地保存失败。
- 同步关联组完整携带根标注、原始版本、修订、排除和知识依据，源版本 ID 别名回写包含列表嵌套锚点和 pending。
- 导入/恢复旧数据时按现有升级路径读取；新列表数据不得被旧读取器静默降为选区。已有列表数据的库不支持直接降级运行，恢复旧版本应用需使用升级前独立备份，不删除 SQLite/WAL/SHM。

## 4. 分阶段执行任务

| 阶段 | 工作与主要入口 | 阶段完成条件 |
| --- | --- | --- |
| L0 基线与失败复现 | 阅读现有标注需求、领域冻结稿与本计划；检查当前工作区；隔离数据复现章节保存失败及当前列表操作 | 记录真实错误响应、保存/创建阶段和运行环境；无法复现则保留未验证结论，不作为臆测修复依据 |
| L1 投影与范围契约 | `packages/content-anchor/src`、web-core workspace types；列表投影、锚点生成、解析、结构身份与动态跟随 | 普通/嵌套/混合列表范围准确；新增子项与外部成员归入区别正确；三种旧范围回归通过 |
| L2 服务与持久化 | knowledge application 下的标注、范围、来源协调及 PostgreSQL 对等服务；local-data-schema/relations 与导入校验 | 四种范围、确认、排除和历史保护一致；JSON/SQLite 重启与真实 PG 事务检查通过 |
| L3 V4 交互 | editor 的菜单、范围生成、事务映射、NoteEditorView、检查器及共享 UI | 子项命中准确；正确创建 `list`；状态、列表过滤、确认/重新定位/排除完整可用；保存并发无误标 |
| L4 同步与恢复 | API sync 与 desktop-runtime 的实体组、版本门槛、导入恢复、草稿与备份；保留已有同步改动 | 新格式同步往返不丢范围/排除/依据；旧版本同步拒绝可解释；失败不丢队列；备份恢复可继续跟随 |
| L5 页面验收与交付 | V4/桌面 E2E、隔离 PG、原生 Mac 打包验收，更新相关领域说明、项目结构导航及工程变更日志 | 验收矩阵逐项有证据；明确自动化、页面、打包和生产迁移/发布的不同结论 |

按 L0 → L1 → L2 → L3 → L4 → L5 执行。每阶段修复已发现问题并完成对应检查后继续，不用先跑完整测试掩盖局部失败。普通职责模块超过仓库建议长度时按职责拆分。

实施时新增独立列表标注验收记录，与本计划互链；记录运行命令、驱动、版本、隔离数据及未验证项。计划文档本身不改变运行代码，不代表允许发布、迁移生产资料或发版。

### 5.1 必须覆盖的场景
