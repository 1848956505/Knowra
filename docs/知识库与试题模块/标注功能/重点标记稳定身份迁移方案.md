# 重点标记稳定身份迁移方案

> 日期：2026-10-11
> 状态：S0 已完成（第 8 节）；S1 已完成（第 9 节）；S2 拆为 S2a（服务端影子比对，已完成，第 10 节）与 S2b；S2b 再拆为 S2b-1（块身份持久化，第 11 节）与 S2b-2（重点绑定持久化）。
> 目标：让重点标记拥有随文档移动的稳定身份。编辑器保存时直接提交最终位置，服务端只校验；推断式跟随只保留给编辑器以外的正文改写。
> 前提：产品行为以[重点标记功能开发方案](重点标记功能开发方案.md)、[列表重点标记开发计划](列表重点标记开发计划.md)和[快捷操作与范围修复](重点标记快捷操作与范围修复.md)为准。本方案只替换定位机制，不改变用户可见规则。

## 1. 现状与问题

### 1.1 当前链路

| 环节 | 入口 | 做法 |
| --- | --- | --- |
| 创建 | V4 `editorAnnotations.ts` `getAnnotationSelection` | ProseMirror 选区 → Markdown 投影偏移 → `ContentAnchor` |
| 实时显示 | 同文件插件 state `ranges` | `transaction.mapping` 逐事务推算，`Decoration` 叠加 |
| 剪切／粘贴 | 同文件 `handleDOMEvents` | `application/x-knowra-move` 剪贴板类型，加闭包变量 `cut`、`moving` |
| 撤销／重做 | 同文件 `snapshots` | 最近事务快照逐个做 `doc.eq` 比对 |
| 保存 | `annotationEditJournal.ts` → `AnnotationMapping` | 文本 diff 拆成 `SourceEdit`，夹带 `history`、`moveKind` 等意图 |
| 结构身份 | `content-anchor/dynamic.js` `updateStructure` | 服务端按编辑日志或 diff 为 Markdown 块继承 `block-<hash>` ID，存入 `Note.annotationStructure` |
| 服务端跟随 | `reconcile-annotation-source.js` → `followAnchorChanges`、`followListAnchorChanges` | 每条重点按日志重放编辑，得出 `resolved`、`needsReview` 或 `missing` |
| 兜底 | `resolve-stored-annotation.js` → `relocateAnchor` 等 | 结构路径 → 投影偏移 → 唯一摘录匹配 |

### 1.2 根因

1. 同一结果算了两遍。前端在 ProseMirror 坐标里推算，后端在 Markdown 源码偏移里重放，两边序列化稍有差异就是 `mappingMismatch`。
2. 移动、撤销这些意图靠旁路信息传递，换一个入口（拖拽、跨标签页、外部粘贴）就丢失。
3. 重点没有身份，只是"某个版本里的一段区间"，所以每次编辑都要重新推断它是否还是原来那段。

### 1.3 已有可复用的基础

- `Note.annotationStructure` 已经是旁路身份表：按 Markdown 块记 `id`、`path`、`type`，并且已经进入同步字段（`sync/journal.js` `NOTE_FIELDS`）。
- 列表重点已经用 `tracking.memberIds` 记录覆盖的块 ID，"成员变化进入待确认"实际上已经在按 ID 判断。
- V4 代码块由 ProseMirror 直接编辑（`editorCodeBlock.ts` 只做外层节点视图），里面的 mark 和装饰都能正常渲染。

本方案就是把这套已有的身份表从"服务端推断"改为"编辑器持有、服务端校验"。

## 2. 目标设计

### 2.1 两层身份

| 范围类型 | 绑定对象 | 范围怎么得出 |
| --- | --- | --- |
| `section` | 标题块的 `blockId` | 读取时按标题级别现算到下一个同级或更高级标题，规则不变 |
| `list` | 列表项块的 `blockId` | 读取时取该列表项的完整子树，规则不变 |
| `blocks` | 首、尾块的 `blockId` | 首尾之间的同级连续块 |
| `selection`（普通正文） | 编辑器内带 `annotationId` 的 mark | mark 覆盖的文字；保存时换算成"块 ID + 块内偏移" |
| `selection`（代码块内） | 同上，代码块的 schema 只放开这一种 mark | 同上 |
| 行内公式等原子节点 | 节点作为整体被 mark 覆盖 | 不支持只选原子节点的一部分，与现在一致 |

章节和列表是会随结构增长的动态范围，用 mark 表达不了，所以绑在根块 ID 上、读取时现算。选区是固定的一段文字，用 mark 最自然。

### 2.2 编辑器侧

**块 ID**
- 给所有块节点（段落、标题、列表项、引用、代码块、表格、公式块、分割线、图片块）加 `blockId` 属性。`toDOM` 输出 `data-block-id`，`parseDOM` 读回，这样剪贴板 HTML 里也带着 ID。
- 新增 `appendTransaction` 插件 `editorBlockIdentity`，在每批事务结束后统一去重（S0 验证后由"粘贴钩子判断"改为"事务后判断"，见第 8 节）：
  - 节点没有 ID 时分配新 ID（`crypto.randomUUID()` 截短）。
  - 出现重复 ID 时，**落在本批事务插入范围之外**的那个保留，插入范围内的换新 ID。
    - 拆分段落或列表项：前半在插入范围之外 → 前半保留原身份，与列表方案里"根身份可证明时跟随"一致。
    - 复制粘贴：原文在插入范围外 → 原文保留，副本换新，对应"复制获得新身份"。
    - 剪切后粘贴、拖拽移动：事务结束时已无重复 → 保留，对应"移动保留身份"。
  - 粘贴或拖放事务（`uiEvent` 为 `paste`／`drop`）插入的重点 mark，如果同一个 `annotationId` 在插入范围外仍有片段（说明是复制），从插入内容上剥离。
  - 从其他笔记粘贴：不属于本笔记的 `annotationId` mark 一律剥离。块 ID 是随机值，带过来不冲突，按上面的规则处理即可。

  这套规则替代现有的 `x-knowra-move` 剪贴板类型、`cut`／`moving` 闭包变量和 `moveId` 日志。

**重点 mark**
- 新增 mark `knowraAnnotation`，属性 `{ id }`，设置 `excludes: ''` 让多个重点可以重叠，`inclusive: false` 让在边界处输入不会扩大重点。
- mark 只用来追踪位置，不负责显示。颜色、重要程度、聚焦态仍由现在的 `Decoration` 层绘制，装饰范围改为扫描文档里的 mark 得出。`createDecorations` 的视觉输出不变。
- Markdown 序列化前先从文档副本上剥离这个 mark，再交给 Milkdown 序列化器。S0 证实只把 mark 的 `toMarkdown` 写成空操作不够：mark 会把文本拆成多个节点，Milkdown 的代码块只输出第一个文本节点，行内代码会被切成两段，29 篇里有 18 篇因此出错。剥离后 29 篇全部与原文一致，最长笔记（30 万字符）序列化含剥离约 10ms。
- 前置修复：Milkdown 自带的 `hardbreakClearMarkPlugin` 在任何 mark 覆盖软换行时会把它重置成硬换行。这是现有产品就有的 bug（加粗跨行再取消，保存后会多出 `\`），已单独立任务修复。重点 mark 依赖这个修复。
- 代码块：schema 放开 `knowraAnnotation`。mark 设置了 `inclusive: false`，所以在代码末尾新增的行不会自动纳入。[快捷操作与范围修复](重点标记快捷操作与范围修复.md)规定"完整覆盖代码内容的选区，在同一代码块内增行时继承颜色"，因此由 `editorBlockIdentity` 处理：事务前某个重点覆盖了整个代码块的内容，事务后就把它扩展到整个代码块。
- 已取消但可恢复、或已归档的重点，mark 继续留在文档里，只是不绘制。这样恢复时位置仍然准确，满足"归档期间正常编辑后恢复，不用文字相似复活"的规则。只有永久清理时才移除 mark。
- 撤销、重做由 ProseMirror 历史自动带回 mark 和块属性，`snapshots` 比对逻辑删除。"删除后重新输入同样文字不复活"天然成立，因为新输入的文字不带 mark。

**加载与绑定**
- 打开笔记时，按 `annotationStructure` 把 ID 写回块属性，再按每条重点的 `binding` 加 mark。这一步用一次 `addToHistory: false` 的 meta 事务完成，并且不能触发自动保存。现在的 `onDocumentChange` 用 `doc.eq` 判断是否变化，需要排除这类 meta 事务。
- 写回 ID 需要把 ProseMirror 块序列和 Markdown 块序列对齐，用 2.4 节的共享纯函数完成。前提是保存的 `contentHash` 与当前正文一致；不一致说明正文被外部改过，先走 2.5 节的外部改写路径。
- 从其他设备同步过来、或在服务端新建的重点，也走同一条绑定事务。

### 2.3 保存契约

`AnnotationMapping`（编辑日志）替换为 `AnnotationEditorState`，挂在保存请求原来的位置（`saveNoteContent(..., annotationMapping)`）：

```ts
interface AnnotationEditorState {
  formatVersion: 2;
  baseContentHash: string;
  baseStructureRevision: number;
  targetContentHash: string;
  // 编辑器块序列，前序遍历；服务端据此对齐 Markdown 块
  blocks: Array<{ id: string; type: EditorBlockType; textHash: string; depth: number }>;
  annotations: Array<{
    id: string;
    present: boolean;                      // false：mark 或根块已不在文档中
    rootBlockId?: string;                  // section / list
    startBlockId?: string; endBlockId?: string;   // blocks
    start?: { blockId: string; offset: number };  // selection：块内投影文本偏移
    end?: { blockId: string; offset: number };
    quoteText?: string;                    // selection：供服务端核对
  }>;
}
```

服务端处理顺序：

1. 核对 `baseContentHash` 和 `baseStructureRevision`，不一致返回 `NOTE_UPDATE_CONFLICT`，沿用现有冲突处理。
2. 核对 `targetContentHash` 等于本次提交的 Markdown。
3. 用 `alignEditorBlocks(projectMarkdown(markdown), state.blocks)` 得出 Markdown 块与编辑器 ID 的对应关系，生成 v2 结构表。对齐失败时整次保存退回外部改写路径（2.5 节），不丢弃正文。
4. 逐条重点计算：
   - `present: false` → `missing / sourceDeleted`。
   - `section`、`list`、`blocks`：按根块 ID 找到块，用现有的 `anchorForSection`、`anchorForListItem`、`anchorForBlock` 生成描述（这些函数从"跟随器"变成纯粹的"描述器"）。再拿成员 ID 集合与上次比较，判断是否待确认（见下文规则）。
   - `selection`：把块内偏移换算成源码偏移，交给 `anchorForSourceRange`，然后核对 `quoteText`。不一致时进入 `needsReview / mappingMismatch`，这种情况只影响这一条重点，可以检测到，不会静默出错。
5. 排除项（`AnnotationExclusion`）用同样的方式绑定块 ID 或块内偏移。

**用 ID 集合重写结构变化规则**（规则与列表方案一致，只是改成集合运算）：

| 成员变化 | 结果 |
| --- | --- |
| 新出现的成员 ID 是上次结构里没有的（新建内容） | 自动纳入 |
| 成员 ID 在文档里已被删除 | 自动缩小 |
| 文档中已有的块移入范围 | `needsReview`（范围待确认） |
| 原成员仍在文档中但移出了范围 | `needsReview` |
| 根块的父子关系或层级改变 | `needsReview` |
| 根块本身被删除 | `missing` |

### 2.4 共享对齐函数

在 `packages/content-anchor` 新增 `align-blocks.js`。它不依赖框架和 DOM，输入两个块描述序列 `{ type, depth, textHash }`，输出一一对应关系或失败原因。

- 类型映射：`paragraph↔paragraph`、`heading↔heading`、`listItem↔list_item`、`code↔code_block`、`math↔math_block`、`thematicBreak↔hr` 等。
- 已知差异与对应规则（S0 在真实语料上验证，见第 8 节）：
  - Markdown 的 `<br />` HTML 块对应编辑器里的空段落（真实语料中 18 处）。
  - 找不到 Markdown 对应块的编辑器空段落直接跳过（3 处，例如文末空段、空笔记）。
  - Markdown 必须带上公式扩展解析。现有 `projectMarkdown` 只用 gfm，会把 `$$` 公式块当成普通段落，导致 1 篇对不齐。S2 需要给投影补上 `micromark-extension-math`，配置与编辑器的 `mathRemark` 相同（`singleDollarTextMath: true`）。
  - 编辑器省略 Markdown 的 `definition`：它不在块类型集合里，天然被跳过。
- 对齐只在块这一层做，不涉及字符级换算，比现在的 `prosePositionForTextOffset` 稳定得多。字符级换算只剩选区的块内偏移，误差被限定在单个块内，并且有摘录核对兜底。
- 编辑器加载时和服务端保存时调用同一个函数，确保两端结论一致。

### 2.5 外部改写路径（保留推断，但只在这里使用）

以下入口改写正文时不会带 `AnnotationEditorState`：源码面板、Markdown 导入、AI 草稿写回、同步合并、以及未来可能的 MCP 写入。

- 块 ID：继续用 `updateStructure` 按 diff 继承，并删除其中的 `moveKind` 和 `cuts` 分支。
- `section`、`list`、`blocks`：根块 ID 继承成功就按 2.3 节规则重算范围；继承失败进入 `needsReview`。
- `selection`：在继承下来的起止块内搜索原摘录，块内唯一命中才认作 `resolved`，否则 `needsReview`。不再做全文搜索和 6 层回退。
- 编辑器下次打开时，以服务端结构表为准写回 ID。

这条路径比现在更保守，可能多出一些待确认，但不会把重点错绑到别处。

### 2.6 数据模型变化

| 对象 | 变化 |
| --- | --- |
| `Note.annotationStructure` | `formatVersion: 2`：`{ revision, contentHash, blocks: [{ id, type, depth, textHash }] }`。去掉 `cuts`；`path`、`sourceStart/End` 改为读取时从投影现算 |
| `ContentAnnotation` | 新增 `binding`：`{ formatVersion: 2, rootBlockId?, startBlockId?, endBlockId?, start?, end? }`。`anchor`、`quoteText`、`fromPosition/toPosition`、`headingPath` 保留为派生字段，分析范围快照、AI 读取工具和列表显示继续使用 |
| `AnnotationExclusion` | 同样新增 `binding` |
| `originSnapshot`、`AnnotationRevision`、`AnalysisScopeSnapshot` | 不改。历史和证据保持不可变 |
| local-json | `LOCAL_DATA_SCHEMA_VERSION` 7 → 8 |
| PostgreSQL | 新增迁移 `l_annotation_identity_v2`：`ContentAnnotation.binding Json?`、`AnnotationExclusion.binding Json?`。`annotationStructure` 已经是 JSON 列，只需迁移数据 |
| 桌面 SQLite | `sqlite-data-store.mjs` 与 local-json 使用相同的文档结构，跟随 schema 8 |
| 同步 | `batch-domain.js` 在 `contentHash` 匹配时信任设备提交的 v2 结构表（现有逻辑已经这样做）；不匹配时用 `updateStructure` 重建。旧格式客户端按现有"旧格式拒绝"处理 |

## 3. 旧数据迁移

迁移在加载 schema 7 文档时执行（local-json、SQLite），PostgreSQL 由迁移脚本执行。两种实现共用 `json-transformers.js` 里的同一个转换函数。

1. **结构表 v1 → v2**：v1 的 `nodes` 已经按 Markdown 块记了 `id`，直接沿用，补上 `depth` 和 `textHash`，丢弃 `cuts`。如果 `contentHash` 与正文不一致，先 `updateStructure(note.rawMarkdown, note.rawMarkdown)` 重建。
2. **`resolved` 的重点**：先用现有的 `resolveStoredAnnotation` 在当前正文上解析一次，再根据结果生成 `binding`：
   - `section`、`list` 取 `structurePath` 对应块的 ID。
   - `blocks` 取首尾块的 ID。
   - `selection` 把 `sourceStart/End` 换算成"块 ID + 块内偏移"。
   - 解析结果和存储的摘录不一致时，改为 `needsReview / migrationUnverified`，不能为了迁移成功而强行绑定。
3. **`needsReview`、`missing` 的重点**：`binding` 设为 `null`，状态保持不变。用户在界面上确认或重新选择来源时再写入 `binding`。
4. **旧 schema v1 的重点**（`legacyUnverified`）：不处理。
5. **非活动重点**（已取消、已归档）：同第 2 条，尽量生成 `binding`，这样编辑器打开时能挂上不可见的 mark。

迁移是只进不退的：schema 8 的数据不能被旧版本打开，与以往的 schema 升级一致。迁移前沿用现有的备份流程。

验收要求：用隔离数据目录复制一份真实资料库，统计迁移后 `resolved` 保持 `resolved` 的比例，并逐条列出降级为 `needsReview` 的重点及原因。

每个阶段都单独提 PR，并且都可以独立回滚。S1 和 S2 期间新旧两条链路并行运行，做影子比对，确认结果一致后再切换。

| --- | --- | --- | --- |

## 5. 测试与删除清单

### 5.1 新增与改写

| 层 | 用例 |

## 6. 风险与待决

1. **序列化前剥离 mark**：S0 已验证可行，性能可接受。S1 要保证所有序列化入口都经过剥离：自动保存、导出、复制为 Markdown、`getMarkdown()`。遗漏任何一处，就会重现 S0 观察到的代码块截断问题，所以需要一条测试断言"带 mark 的文档在所有入口的输出都和不带 mark 时一致"。
2. **块内偏移换算**：这是唯一剩下的字符级换算。范围被限制在单个块内，有摘录核对兜底，但行内 HTML、行内公式、图片需要专门的用例覆盖。S0 只验证了块级对齐，没有验证块内偏移。
3. **真实浏览器行为**：S0 在 jsdom 中运行。剪贴板走的是 ProseMirror 的序列化和 `pasteHTML`，拖拽是用"同一事务插入并删除"模拟的。真实的 Chromium／Electron 剪贴板、拖放和中文输入法要在 S1 的页面验收中补测。
4. **多设备并发编辑**：两台设备各自持有 ID 并同时改同一篇笔记时，沿用现有冲突副本机制，冲突副本里的块 ID 和 mark 全部换新。是否需要更细的合并，留到后续单独讨论。
5. **源码面板**：已确认接受。源码面板编辑后，选区重点更容易进入待确认。
6. **未来协作编辑**：mark 加块 ID 的模型与 Yjs 等协作方案兼容，但本方案不承担协作编辑。

## 7. 已确认的决定（2026-10-11）

1. **成员变化规则统一**：由 Claude 决定，采用第 2.3 节的 ID 集合规则表，章节、块、列表三类范围共用。理由：列表已经按这套规则验收过；章节和块现在靠边界指纹和文本比较判断，换成同一套规则后行为更一致，代码也更少。用户可见的差别只有一处：章节里把已有的段落拖进来，会提示"范围待确认"，而现在可能直接纳入。
2. **源码面板**：接受编辑后选区重点更容易进入待确认。用户不使用源码面板。
3. **先做 S0**：已完成，结论见第 8 节。

两条口径约束（审查后补充）：
- **体积**：快照大小只随块数和重点数线性增长，不随选区长度增长。保存时，快照超过 1 MiB，或者附带快照后按真实请求形状序列化的 JSON（UTF-8 字节，含反斜杠等转义）距服务端上限 `DEFAULT_JSON_BODY_LIMIT_BYTES`（8 MiB）不足 16 KiB，就省略快照，保存照常进行。V4 的同值常量由测试与共享包比对。第二轮审查发现，按正文原始字节估算会漏掉 JSON 转义：一个 8,000,321 字节的请求附带约 675 KB 快照后仍然触发 413。最初版本直接发送摘录原文，160 条重叠长选区会生成约 9.69 MB 的请求，触发 `413 PAYLOAD_TOO_LARGE`，导致保存失败。
- **表格**：服务端把表格作为一个整体块对齐，所以编辑器对单元格内的选区和块重点，统一报告所在表格的 ID。最初版本报告的是单元格内段落的 ID，位置完全一致时也会误记 `blockMismatch`。

- PostgreSQL 驱动暂不接入影子比对：项目规则禁止在 PostgreSQL 事务内做外部文件 IO。

- **只记录已提交的保存**：比对在保存所在事务内进行，读取旧链路跟随后的最终状态；写日志则通过存储新增的 `afterCommit` 推迟到最外层事务提交成功后，回滚即丢弃。JSON 与 SQLite 存储都实现了 `afterCommit`：嵌套事务推迟到最外层，事务外立即执行。第二轮审查用 SQLite 提交故障注入发现，最初版本在正文、版本和队列都已回滚时仍留下 `compared` 记录。第三轮审查又发现：SQLite 回滚时没有清空回调队列，之后事务外的独立提交（例如上传附件触发的 `flush()`）会执行失败保存留下的回调。现在所有回滚路径都会立即清空队列。

## 11. S2b-1 块身份持久化（2026-10-12）

### 11.1 前提变化

原计划在 S2b 之前，先统计一段时间的影子日志。但开发数据目录和 Mac 应用数据目录里都没有 `annotation-shadow.jsonl`，因为 Mac 应用还没装上带 S2a 的版本。用户决定直接推进 S2b，因此 S2b 继续保持影子模式：旧链路仍然是重点状态的权威来源，等积累了日志再调整 S3 的规则。

### 11.2 为什么不复用 `annotationStructure.nodes`

本地数据校验要求 `nodes` 与 `projectMarkdown` 的块逐一吻合（路径、类型、偏移），旧链路的列表跟随也用这些节点 ID 比较成员是否变化。如果影子阶段就把编辑器 ID 写进 `nodes`，旧链路会把 ID 变化误判为结构变化，把列表重点误标为待确认。

所以身份表放在新的可选子字段 `annotationStructure.identity`：

```ts
interface IdentityTable { formatVersion: 2; contentHash: string; blocks: Array<{ id: string; type: string }> }
```

`blocks` 与 `parseIdentityBlocks(rawMarkdown)` 逐一对应。这样做的好处：
- PostgreSQL 无需新增列（`annotationStructure` 本来就是 JSONB），本地数据 schema 不升级。
- 同步自动带上（`annotationStructure` 已在 `NOTE_FIELDS` 中）。
- 旧版客户端编辑时会生成新的结构对象，身份表随之被丢弃，平滑降级。

### 11.3 写入、读取与失效规则

| 情况 | 身份表 |
| --- | --- |
| 保存时带编辑器快照，且与本次正文对齐 | 用编辑器 ID 重写（`identityFromEditorState`） |
| 保存时正文没变 | 沿用原表 |
| 外部改写（源码面板、导入、AI 写回、无快照或快照过大的保存） | 失效，S3 再补推断继承 |
| 同步收到正文已变的笔记 | 服务端重算结构，身份表随之丢弃（原有行为） |
| 同步收到与正文不对应的身份表 | 丢弃身份表，不拒绝整批同步 |
| 读取 | `validIdentityTable` 校验哈希、块数、类型和 ID 唯一性；不合法视为不存在，不影响数据加载 |

编辑器侧：
- 加载笔记、以及整篇替换正文（远端同步应用）后，调用 `applyBlockIdentity`。身份表与当前正文对应时，用 `adoptIdentityIds` 把服务端 ID 交回编辑器块。
- 无论是否沿用，都会重置影子绑定，等重点按新正文重新解析后再按新 ID 绑定。这同时修复了 S1 的一个遗留问题：整篇替换后，影子绑定仍指向旧 ID，产生虚假的 `identityLost`。
- 加载之后编辑器是 ID 的权威来源。保存响应返回的身份表不会再写回编辑器。
