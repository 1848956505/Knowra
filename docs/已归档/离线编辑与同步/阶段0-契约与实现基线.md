## 1. 实施裁决

本地运行服务放在 `apps/desktop-runtime`，复用 API 应用服务、实体校验、版本生成与 V4 静态资源。V4 仍通过同源 `/api/*` 请求保存；在本地运行模式下，这些请求由本机服务处理，不需要云端或外网。

结构化数据使用 Node 内置 `node:sqlite` 的 `DatabaseSync`，启用 WAL 和 `synchronous=FULL`。运行时要求 Node >=24，具体使用的构造、同步 SQL 和关闭能力可查 [Node SQLite 文档](https://nodejs.org/download/release/v24.0.1/docs/api/sqlite.html)。本轮在 Node 26.4.0 验证，仓库 CI 使用 Node 24；不能把本轮结果写成 Node 24 的实机通过记录。

数据访问仍采用现有 repository 的内存数组接口，由 SQLite 适配器在领域事务结束时计算变化并提交；数据库只更新发生变化的实体行，不整体重写数据库。内存快照和一致性检查仍有随数据量增长的成本，后续按实测优化。

阶段 1 只记录本地操作，不开启网络发送。因此暂不新建共享同步包或云端同步模块，避免维护尚无调用者的框架。Mac 安装包与桌面窗口也不属于这两个阶段；当前入口可供后续桌面主进程调用，开发验收用本机浏览器显示同一 V4 页面。

本轮本地适配器遍历 `LOCAL_DATA_COLLECTIONS` 比较事务前后实体，统一记录全部实际变化，避免漏掉正文更新引发的来源副作用。云端 local-json 与 PostgreSQL 仍保持原状，阶段 2 需要在两种驱动的实际写事务中接入日志与幂等结果。

## 4. 本地事务契约 v1

本地库版本 `user_version=1`，领域快照 schema 仍为现有的 5；两者分别维护。

| 存储 | 内容 |
| --- | --- |
| `metadata` | 稳定 deviceId、独立 datasetId |
| `entities` | collection + id 主键、业务 JSON、local_revision |
| `local_revisions` | 包括已删除实体的本地修订及上次 operationId，防止修订归零 |
| `sync_base` | 预留已确认云端修订与快照；尚未连接时为空 |
| `sync_outbox` | 不可变 operationId、deviceId、protocolVersion、状态、事务变化集合、依赖与创建时间 |

一次 outbox 操作对应一次领域事务，`changes` 的每项包含 `collection`、`entityId`、`action`、`before`、`value`、`localRevision`、`baseRevision`。`action` 只有 `upsert` 和 `delete`；实体删除保留之前的内容。记录的是领域结果，不是可盲目重放的 HTTP 请求。

同一实体的后继操作依赖上一次操作；笔记、目录等当前实体引用也记录已存在的前置操作 ID。同组新建父子实体不形成自依赖。队列不压缩、不自动清理，阶段 2 负责根据确认状态筛选可发送操作。

新数据集和导入快照都处于未绑定云端状态，`baseRevision=null` 不等于“云端一定不存在”。阶段 2 必须先完成数据集绑定和逐项基线比较，再将本地变化转为网络操作；不能直接上传导入产生的全部记录覆盖云端。

本地修改与队列提交、游标与拉取数据提交、云端业务与日志及幂等提交，是三个分别需要保持原子的边界。阶段 1 只实现第一个。

## 5. 云端协议冻结边界

沿用总方案第 6 节的 status、bootstrap、snapshot、changes、push、附件 prepare/complete 接口，以及项目成功/失败封装。路径是待实现契约，当前服务没有伪造成功的同步端点。

- `serverRevision` 由云端生成；本机时间和 `updatedAt` 不能替代它。
- `cursor` 限定 owner、空间与 datasetEpoch，事务组不能半页应用后推进游标。
- 重试使用原 operationId 与相同负载；同 ID 不同负载拒绝。
- owner 由服务器决定，deviceId 不用于鉴权。
- 接受、冲突、依赖失败与永久校验失败逐项返回；不可分割的领域变化作为一个事务组。
- 所有云端写入口必须适配，旧网页写入不允许绕过修订检查。
- 服务器恢复备份后变更 datasetEpoch；客户端保留未确认内容再重建基线。
- 阶段 2 的客户端必须明确区分阶段 1 本地未绑定队列与可以发送的云端协议负载。

## 6. 数据备份与迁移基线

本轮在原本地资料库上只读导出，得到 `storage/exports/offline-phase0-20260910.json`，包含 18 篇笔记和 12 个附件；该目录受 Git 忽略保护，正文与附件不提交到仓库。

- 原 JSON SHA-256：`940d8c76b9c162464940ae7b9be7c810ce4de20735231ee5685bbaf036c19837`。
- 完整备份 SHA-256：`441a85ddd6b3dc49d486b1fd44af3244e887476d6543dca8ad99f683cb3cb803`。
- 在临时目录导入 SQLite 后，逐篇比较正文记录，逐个读取并比较 12 个附件字节，验证通过；原库未迁移覆盖。
- 这是本地开发数据基线，不是当前云服务器备份或 PostgreSQL 验收。

导出命令必须显式指定数据源、存储根与新的目标文件；导出过程中源 JSON 改变或附件哈希不符即失败。自定义上传目录部署需先通过已有整库导出接口获得包含附件的快照，不使用默认目录基线命令猜测路径。

## 7. 性能基线与准入

本轮环境为 macOS、Apple M5、Node 26.4.0。每种规模预置笔记后连续执行 20 次正文事务提交，包含版本生成、完整引用校验及 outbox 写入；不包含 UI 防抖、网络和大附件。

| 笔记数 | 本地事务 P95 | 最大耗时 |
| --- | --- | --- |
| 100 | 1.89 ms | 2.00 ms |
| 1,000 | 10.77 ms | 14.54 ms |
| 10,000 | 112.35 ms | 114.34 ms |

开发准入目标：在上述同级设备与数据构成下，1,000 篇笔记的正文事务 P95 不超过 100 ms，10,000 篇不超过 250 ms。该数字是本地工程基线，不是所有设备或长期日志增长后的产品承诺。后续增加同步日志、附件和大量版本后必须重测；Windows、Linux 和 Node 24 的专项运行验证留待相应环境执行。
