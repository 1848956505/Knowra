# 标注与保存机制诊断及修复方案

日期：2026-09-20。范围：当前工作区、现存 Mac 打包产物、本机退出日志、SQLite 只读样本、隔离数据库复现。本次没有修改业务代码或用户资料；工作区原有的保存相关未提交改动保留。

## 结论与证据边界

确认存在两个独立问题：标注的特定编辑场景能够使正文保存返回 500；正文版本冲突会让自动保存和退出进入无法自行恢复的状态。日志证明用户实际反复遇到后者，尚不能把当天首次 500 精确归因到已复现的标注场景。

本机 `~/Library/Application Support/Knowra/shell/logs/desktop.log`：

- 9 月 12 日已出现 `退出暂停：Note has changed since it was loaded`。
- 9 月 20 日北京时间 20:23:45 出现 `Internal server error`。
- 随后 20:24:01 至 20:26:04 连续七次出现笔记版本冲突。
- 20:26:11 本地服务退出，随后页面进程异常退出。

日志没有请求 ID、笔记 ID、实际版本比较值或那次 500 的异常堆栈，无法判断具体由哪次标注操作或哪次并发写入触发。不能据此断言数据库损坏、网络不稳定或云端同步是根因。

## 一、已复现的标注缺陷

调用链：`NoteEditorView.createCurrentAnnotation` 先 `autosave.saveNow`，再创建标注；正文 PATCH 经 `note-service.persistNote` 创建版本后，同步执行 `contentAnnotationService.reconcileForNote`，全部处于本地事务内。

复现步骤：

1. 在临时 SQLite 创建正文 `# 标题\n正文\n\n# 下一节\n结束`。
2. 给第一节创建 schema v2、scopeType=section 的章节标注。
3. 将正文改为 `# \n\n# 下一节\n结束`，即留下空标题并删除该节正文。
4. 向真实 HTTP 处理器 PATCH `/api/knowledge/notes/:id`，携带原 `expectedUpdatedAt`。

连续两次请求均返回 HTTP 500 / `INTERNAL_SERVER_ERROR`。底层异常为 `ANNOTATION_RANGE_INVALID: Source range has no projected content`。

根因：`packages/content-anchor/src/index.js:267` 的 `followSectionAnchor` 找到章节后直接调用 `anchorForSection`；空章节没有可投影内容，构造锚点抛出 RangeError。该异常没有转为标注 missing/needsReview 状态，经正文保存一路冒泡，在 API 层变成通用 500。

隔离数据库回读确认：失败后正文和 updatedAt 都保持原值，事务回滚有效。故此场景不能单独解释“先 500、再 409”的日志顺序。

本机数据库只读读取到 27 篇笔记、1 个有效标注，当前没有章节标注。对其内存副本做追加、清空、标题修改、前缀插入共 4 次重算均未抛错。已复现的章节缺陷是真实代码问题，但不是用户当天故障的已证实触发点。

## 二、版本冲突为何导致一直无法退出

`note-service.js:138` 使用整个笔记的 updatedAt 作为正文并发条件。重命名、收藏等元数据更新也能推进这个时间戳，即使正文不变也可能拒绝旧令牌。

`useNoteAutosave.ts:136` 在记录冲突后，后续保存直接抛出已记录错误；`updateDraft` 也不再启动自动保存。当前活跃编辑器没有“重新读取、核对正文基线、解除可恢复冲突”的完整流程。

桌面退出会调用编辑器保存参与者；只要保存抛错就拒绝退出。`desktop-shell/src/main.cjs:53` 的对话框只有“返回应用”。重复点击退出不会修复版本基线，因此重复遭遇同一个错误。

当前工作区已有未提交补丁：在 store 中对特定 NOTE_UPDATE_CONFLICT 回读一次，只有最新正文与已知正文一致时使用新令牌重试；恢复草稿时也放宽仅时间戳变化的判断。这些补丁早于本次调查，不能算本次修复；也没有证据证明它们已进入用户运行的 App。它们尚不足以覆盖所有活跃冲突、丢响应及退出恢复路径。

## 三、状态与恢复机制的问题

- 正文、标注、标签等共享单一 saveState。标注操作失败也显示“保存失败”；另一次操作成功又可能将它覆盖为“已保存”。它不能准确回答哪些内容尚未持久化。
- `noteDraftRecovery.ts` 使用内存和 sessionStorage，写入异常被吞掉。适用于同一会话恢复，不能作为 App 退出后可靠恢复的依据。
- 冲突界面已有导出草稿入口，但“导出草稿并加载远端”触发下载后立即清理草稿并刷新，没有文件保存成功的确认。
- API 会记录内部异常，但桌面主进程丢弃子进程 stdout/stderr，退出日志只留下通用错误，导致下一次排查缺少直接证据。

## 建议修复顺序

### P0：修复标注使正文保存失败

1. 空章节、删除来源、旧锚点超界等正常编辑结果统一返回 missing/needsReview；保留 originSnapshot 与历史锚点，不要求重新构造有效的非空锚点。
2. 正文保存时对单条标注的已知解析/范围失败做隔离，记录该标注需要重算，不让正常编辑被阻断。未知异常、磁盘失败及关系完整性错误仍需回滚，不能简单 catch 后返回成功。
3. SQLite、JSON 和 PostgreSQL 路径采用一致语义；正文、版本、标注降级状态和待同步记录保持原子提交。

### P0：完善冲突恢复

1. 保存时明确传递产生草稿时的正文基线及版本，不依赖可能已刷新的 store 正文猜测基线。
2. 遇到冲突先回读：最新正文等于本次待保存正文时，确认已保存并推进基线；等于草稿基线时，用新令牌有限重试；两者都不等时保留双方内容并进入真正的冲突处理。
3. 只对指定正文冲突码进入冲突锁定；超时、断网、服务器错误与其他 409 分别处理。
4. 活跃编辑器、路由切换后的草稿和退出保存共用相同状态机；恢复成功后清除旧错误及已完成的退出参与者。
5. 后续将正文版本条件与笔记元数据版本分开。若采用内容修订号或内容哈希条件，要同步调整 API/DTO、各存储驱动及客户端兼容，不能取消并发检查。

### P0：提供可恢复的退出

1. App 增加独立的持久草稿区，保存资料库 ID、笔记 ID、正文、原基线、草稿修订号及错误类别；不依赖正文标注事务成功才能写入。
2. 只有收到原子写入成功确认，才能提示“草稿已保存到本机”。存储失败必须显式显示。
3. 退出提供“重试保存”“保留恢复草稿并退出”“返回编辑”。第二项必须先确认所有待保存草稿已持久化，再退出；下次启动展示恢复入口。
4. 手动导出采用可确认完成的桌面文件写入；导出失败或取消时不删除恢复记录。

### P1：让状态栏与日志可诊断

按笔记及操作分别记录 dirty/saving/saved/error/conflict；聚合显示“正文已保存，标注待处理”等具体信息，并可打开失败详情与重试入口。云端同步状态继续独立显示。

保存日志记录请求 ID、操作类型、非敏感实体 ID、错误码、堆栈及版本比较信息；不记录正文、附件内容或凭据。桌面服务输出经脱敏、轮转后写入日志，避免只有 `Internal server error`。

## 实施结果（2.20.2）

已完成旧标注读取默认值、空章节/已存储无效锚点降级、显式正文基线核对、主动冲突重试、丢响应恢复、独立桌面原子草稿文件、失败退出恢复选项、启动恢复列表及脱敏错误栈。没有修改用户资料；旧记录在读取及下一次正常更新时兼容处理。

补充发现：本机旧标注缺失 revision/schemaVersion 等字段。新增 SQLite/JSON 真实 HTTP 测试覆盖缺失字段记录与空章节同时存在的情况，保存及重启回读成功。旧记录字段缺失是已验证的兼容缺陷，但现有日志仍不足以还原当天具体请求。

采用兼容修复而非升级 API 并发协议：继续使用 expectedUpdatedAt，并在前端保留独立正文基线做有限重试。网页保持原有会话草稿，桌面使用 recovery-drafts.json，未引入云端草稿同步或无条件覆盖。数据库写入失败仍回滚，未吞掉未知错误。

原来的前端、API 和本地运行时测试已通过；新增打包测试实际验证元数据冲突后的立即退出、500 时保留草稿退出、恢复文件损坏时拒绝退出、重启恢复后成功落盘及清理恢复文件。真实 PostgreSQL 环境未连接，异步服务使用同一锚点恢复逻辑并通过现有 API 回归。
