# 整改路线图与验收门槛

日期：2026-09-06；依据 B6 最终清单。本文是下一轮修复建议，不表示已授权或实施修复、部署、迁移或依赖升级。最终编号见 [18-最终问题清单](18-最终问题清单.md)。不按文件长短安排优先级，也不估算缺乏依据的人天。

## 1. 修复顺序与工作包

| 顺序 | 工作包 | 覆盖问题 | 完成条件 |
| --- | --- | --- | --- |
| A1 | 请求解码与超限协议 | R-03、R-11 | 每个UTF-8切点保真；直连及生产代理均能识别413；不破坏字节限额 |
| A2 | JSON 业务提交与重启恢复 | R-01、R-05 | 目录/批量导入失败不残留子提交；主文件缺失且有备份时有安全恢复入口；各原复现通过反向验收 |
| A3 | 跨路由草稿恢复 | R-02 | 409/断网离开后仍可恢复或导出草稿；所有应用导航入口一致，不覆盖服务端新版本 |

| B1 | 标签模型生命周期与查询契约 | R-06、R-08、R-09、R-10 | 缓存、新建组、新空间、文本+多标签均接入完整模型，双驱动契约一致 |

| C1 | 回归与工程门禁 | R-13、R-14；V5-05 | 原完整E2E修正后通过；表格失败稳定性有记录；CI实际运行边界命令 |

| D2 | 文档及职责维护 | R-15、R-16、R-19 | 当前文档和链接真实；重构只围绕已明确的职责边界，保持行为和单Store |

A1～A4 是第一优先级。C1 应随相关修复同步推进，使后续修复有可用的回归依据；不必等所有功能问题修完才补测试。A4 依赖隔离数据库，可以在其他工作包进行时准备，但不能把缺环境视为该项已关闭。

R-06 与 R-04 都暴露字段清单遗漏，可共享集合/快照契约的设计；仍分别验收浏览器缓存和PG恢复。R-03 与 R-11可同一请求解析工作包交付，但两组断言都必须通过。避免一次大重构混入所有标签、编辑器和存储修复。

## 2. 每个修复的最小验收证据

1. 固定修复前后基线，保留用户原有改动，记录实际修改文件。
2. 先让对应缺陷场景证明修复前失败，修复后符合预期。审查脚本中“成功复现缺陷”的断言要转成正确行为断言，不能直接沿用退出0当作修复成功。
3. 根据问题核查 HTTP 返回、当前内存、持久文件/数据库、重启读取和页面状态；不要只验证其中一层。
4. 运行受影响模块测试及架构/类型检查；跨模块或最终集成时运行标准检查、生产构建和原完整E2E。不要把副本测试通过替代正式用例。
5. 记录环境、命令、实际数量、失败/跳过及仍未验证部分；结构性变更进入唯一工程变更日志。

## 3. 发布前建议门槛

这些是本次审查提出的发布条件，未代替项目既有发布权限或批准流程：

- 目标部署会触及的 P1 全部关闭；特别是默认 JSON 的 R-01/02/03/05。若启用 PostgreSQL 或进行迁移，R-04 必须以真实隔离数据库往返证据关闭。
- 标准检查和原完整E2E在目标基线上通过；若存在保留失败，必须明确原因、影响与责任人，不能以本次诊断结果自动豁免。
- 生产配置的端口/代理/认证/健康检查经目标环境验证。当前本地生产冒烟不代表线上已经正确配置 Basic Auth。
- 备份实际恢复到隔离环境并核查内容/附件；代码回退与数据回退分别演练，不把 git 回退当作数据恢复。
- 按授权完成联网依赖审计与可达性复核，覆盖生产、开发和可选依赖的不同用途；不能因 audit未执行而填写“零漏洞”。
- 明确目标平台、Node最低版本和容量；未运行的平台或规模保留限制，不能继承本机Chromium结果。
