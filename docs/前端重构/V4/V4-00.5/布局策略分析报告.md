# 布局策略分析报告

**定位**：以 Markdown 记笔记为核心、未来扩展知识库/试题库/打卡/待办的中文 Web 应用 **分析参照**：Notion（文档+数据库混合体）、Craft（文档优先的编辑器体验）、Linear（极速工作台与命令驱动） **分析视角**：信息架构与布局模式，聚焦长期可扩展性，不涉及视觉风格

------

## 1) 应用外壳模式（App Shell）

**建议：三栏可变外壳 = 固定一级导航栏（Icon Rail）+ 上下文侧边栏 + 主内容区**，而非 Notion 经典的"单一大侧边栏"模式。

表格





| 参照   | 模式                                                         | 对本项目的启示                                              |
| :----- | :----------------------------------------------------------- | :---------------------------------------------------------- |
| Notion | 左侧一个可折叠 Sidebar 承载一切（工作区、页面树、模板、设置） | 单模块时简洁，但多模块后 Sidebar 变成"什么都塞"的熵增重灾区 |
| Craft  | 左侧三段的"文档 / 文件夹 / 收藏与标签"分层 + 顶部工具栏      | 文档型产品的侧边栏克制范例                                  |
| Linear | 左侧 Sidebar（团队/视图分组）+ 顶部面包屑，主区极窄工具栏    | 证明"导航分组语义化"可以支撑多视图而不拥挤                  |

**策略要点**：

- 采用 **Icon Rail（图标轨道，~56px）+ 可展开二级栏** 的双层导航外壳。Icon Rail 上是模块入口：笔记、知识库、试题库、打卡、待办（未来按上线顺序逐步点亮）。
- **外壳与模块解耦**：外壳只负责"模块切换 + 全局能力挂载点"，任何新模块上线不改动外壳骨架，只注册一个图标 + 一块二级栏内容。这是长期可扩展的关键——模块数量从 1 增长到 5 时，导航复杂度保持 O(1)。
- 顶部只保留**面包屑 / 当前位置 + 全局操作（搜索、命令面板、头像）** 的细条（Linear 式），不做重型顶部导航，把纵向空间让给内容。
- 整个外壳状态（各栏开合、宽度）应作为**可持久化的布局状态**处理，为后续"用户自定义工作区"留口。

## 2) 左侧一级导航与二级内容列表的关系

**建议：一级定模块（"我在哪里"），二级定内容上下文（"我在看哪类东西"），二者是父子但物理分层，不是一棵树。**

- **一级（Icon Rail）**：纯模块切换器。只承担"切换信息域"职责，不展示任何条目。hover/激活时展开对应二级栏。
- **二级（Contextual Sidebar，240–320px，可拖拽调宽、可整栏折叠）**：内容随一级选中模块整体替换：
  - 笔记模块 → 笔记本/文件夹树 + 标签区 + 最近/收藏快捷段（Notion 式分区）
  - 知识库 → 知识库列表 → 库内页面树
  - 试题库 → 学科/题型筛选树
  - 打卡/待办 → 清单/项目分组（Linear 式分组）
- **关键原则**：
  1. **二级栏是同构插槽（slot）**，各模块注入自己的树/列表组件，外壳不关心内部结构。新模块 = 新插槽内容，零外壳改动。
  2. **树形层级尽量浅**：笔记/知识库内部建议 2–3 级封顶，深层导航交给主内容区的面包屑和页内链接（Notion 的页内嵌套页面），避免侧边栏树无限膨胀。
  3. **二级栏顶部保留本模块作用域的搜索/新建按钮**（"在当前模块内找/建"），与全局搜索形成层级分工。
  4. 一级与二级**可合并降级**：窄屏或专注模式下只留一级 Rail，二级整栏收起（详见响应式策略），因此二者在实现上必须可独立显隐，不要耦合为一个组件。

------

## 3) 编辑器工作区布局

**建议：居中限宽文档栏 + 上方文档工具条 + 页内大纲入口，Craft 式文档优先，而非 Linear 式表格优先。**

- **内容列限宽居中**（正文 680–780px，可设置加宽至"全宽模式"）：Markdown 长文可读性的基础；同时"居中列 + 两侧留白"天然为未来左右面板预留了物理空间——宽度设置变化不影响面板布局。
- **顶部工具条**（粘性，随滚动收拢为单行）：面包屑（位置）+ 文档标题 + 状态操作（收藏、分享、历史、更多菜单）。参照 Craft：工具条属于"这份文档"，不属于全局——全局操作在外壳，文档操作在文档，职责清晰才可扩展（未来试题/待办详情页复用同一工具条骨架，只换操作项）。
- **正文即块编辑器**：Markdown 输入 + 块级操作（拖动柄 / 斜杠菜单）。斜杠菜单（`/`）是未来扩展点：今天插入标题/代码块，明天插入"试题块""打卡卡片""待办嵌入"——**块类型注册机制**应从一开始就按插件化设计。
- **页内大纲（TOC）**：默认作为右侧检查器的一个 Tab（见第 4 节），不做独立第三栏，避免三栏同时常驻造成的拥挤。
- **专注模式**：一键隐藏左右所有面板，只留正文列 + 最小工具条（Craft 的 focus 体验）。这对"记笔记"主场景是高频需求，也说明各面板必须是可独立关闭的独立单元。
- **多分栏/分屏（可选，中后期）**：参考 Notion 当前不支持、Obsidian 支持的差异——如果知识库/刷题场景需要"对照阅读"，预留"主区可拆成左右两个内容实例"的架构可能性，但不一期实现。一期只保证主区是"内容实例的容器"而非写死的单页组件。

------

## 4) 右侧面板/检查器策略

**建议：统一的右侧检查器容器（Inspector，~280–340px，可折叠），内容按"当前选中对象"切换，而非每个功能各自开面板。**

- **参照**：Linear 右侧详情面板（选中 Issue 出现上下文）、Craft 右侧 Info/大纲、Notion 的页面属性区。共同点是：**右侧面板 = 当前焦点的属性与元信息**，不是导航，不是主要操作区。
- **内容分层**（按优先级一期到后期）：
  1. **文档信息**：元数据（创建/更新时间、字数）、标签、反向链接/引用（知识库核心能力，建议尽早）
  2. **页内大纲 TOC**
  3. **AI 助手 / 评论协作**（若有规划，作为同容器的 Tab）
  4. 扩展到试题模块时：选中题目 → 右侧显示答案/解析/错题统计（同一 Inspector 容器，注入不同内容）
- **关键原则**：
  1. **一个容器，多种内容（Tab 或上下文切换）**：坚决避免"每加一个功能就多一个右侧悬浮按钮/抽屉"的失控路径（许多国产笔记产品的反面教材）。
  2. **右栏与二级左栏对称可折叠**：左栏管"找东西"，右栏管"看当前东西的详情"，用户可同时关闭两者进入纯净写作。两个栏的显隐逻辑、宽度持久化用同一套机制实现。
  3. **右栏不做全局导航**：搜索、通知、设置不进右栏（它们有更适合的位置，见第 6 节），保证右栏语义单一 = "检查器"。

## 5) 多模块扩展原则（核心章节）

这是本项目最需要提前布局的部分。五条原则：

1. **模块即插件（Module Registry）**：每个模块（笔记/知识库/试题库/打卡/待办）对外只暴露三样东西——Icon Rail 入口、二级栏插槽内容、主区路由与页面模板。外壳通过注册表渲染，新模块上线 = 注册一条记录。**验收标准：新增模块不允许改动外壳代码。**

2. **统一内容模型，差异化视图**：Notion 的根本优势是所有东西都是"块 + 数据库"。建议笔记、知识条目、试题、待办在数据层尽早抽象为"条目（Item）+ 属性（Properties）+ 视图（View）"：

   - 笔记 = 条目 + 文档视图
   - 试题 = 条目 + 结构化属性（题型/答案）+ 列表/刷题视图
   - 待办 = 条目 + 状态属性 + 看板/清单视图

   布局上这意味着：**主区应抽象为"视图容器"**（文档视图 / 列表视图 / 看板视图 / 日历视图可切换），而不是"笔记页组件"。一期只实现文档视图，但容器接口一期就定好。

3. **跨模块互通靠"嵌入与引用"，不靠页面缝合**：待办嵌入笔记、试题被笔记引用、打卡记录关联笔记——都用块级嵌入和双链实现（Notion 的 synced block / mention 模式）。这样模块间产生协同价值，但布局上各模块保持独立完整，不会出现"四不像混合页"。

4. **全局能力一次建成，模块免费继承**：搜索、命令面板、收藏、最近使用、回收站必须设计为跨模块的全局设施（见第 6 节），新模块只需把内容注册进全局索引。如果每个模块自己做搜索和收藏，三个模块后体验必然割裂。

5. **信息架构的渐进披露**：未上线/未启用的模块在一级 Rail 上可置灰或隐藏（Linear 的功能开关模式），避免一期用户面对一排空模块。模块启用状态按用户/工作区可配——这也为将来"不同用户只用不同模块组合"（纯笔记用户 vs 备考用户）留出产品空间。

## 6) 全局能力的位置建议

表格





| 能力                  | 建议位置                                                     | 参照与理由                                                   |
| :-------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **命令面板**          | `Ctrl/Cmd + K` 全局唤起，居中浮层                            | Linear/ Craft 的标准。它是终极扩展阀：跳转、新建、切换模块、执行命令全部汇聚一处。新模块上线只需注册命令，**功能再多也不挤压布局**。建议一期就上，哪怕命令很少——用户习惯要早养 |
| **全局搜索**          | 外壳顶部常驻搜索框（点击即转为 Cmd+K 同一浮层的搜索模式）+ 二级栏内的模块作用域搜索 | Notion 的 Quick Find 模式。全局搜索跨模块（笔记+试题+待办统一索引）；模块内搜索在二级栏顶部，两级分工 |
| **最近使用**          | 二级栏（笔记模块）顶部固定段 + 命令面板默认页（无输入时显示最近项） | Linear 的命令面板空态就是最近项，一举两得，不占额外布局      |
| **收藏**              | 二级栏固定段（跨模块收藏夹，可分组）                         | Notion 的 Favorites 在侧栏顶部。建议收藏是**跨模块**的（可收藏笔记、试题、清单），强化"统一工作台"心智 |
| **设置**              | Icon Rail 底部 + 头像菜单内，二级入口                        | Linear 模式：设置是低频功能，放最底部，绝不在顶部占位置。设置页内按"通用/编辑器/各模块"分 Tab——模块设置随模块注册自动出现 |
| **通知/协作**（若有） | Icon Rail 底部铃铛 + 下拉浮层                                | 不占栏位                                                     |
| **新建**              | 二级栏顶部"新建"按钮（创建当前模块内容）+ 命令面板"新建任意类型" | 就近创建（上下文内）+ 全局创建（命令面板）双通道，Notion 与 Linear 均如此 |

**原则总结**：全局能力集中走"**一个快捷键浮层（Cmd+K）+ 一个顶部入口 + Rail 底部低频区**"三条固定通道。任何新功能想暴露入口，先问能否进这三条通道，而不是新占一块界面。

## 7) 响应式策略

按三个断点层级的**渐进降级**（布局做减法，功能不减）：

**桌面宽屏（≥1280px）**：完整三栏——Icon Rail + 二级栏 + 主区（+可选右侧检查器）。右侧检查器默认开启。

**桌面窄屏 / 小窗口（768–1280px）**：

- 右侧检查器默认收起，变为按需唤出（覆盖式浮于主区之上，而非挤压主区宽度——Notion 的处理方式）
- 二级栏可整栏折叠成仅 Icon Rail（Linear 的 sidebar collapse），折叠态下 hover Rail 图标可临时浮出二级面板

**平板（≤768px）**：

- 单栏模式：二级栏变为抽屉（Drawer），从左侧滑出覆盖内容；Icon Rail 收进抽屉顶部或底部 Tab Bar
- 编辑器全宽，工具条精简为标题 + 更多菜单
- 命令面板浮层全屏化

**手机（如支持，≤480px）**：

- 底部 Tab Bar（最多 4–5 个模块入口，与 Icon Rail 同一数据源渲染——再次验证模块注册表的价值）+ 全屏内容 + 抽屉式二级导航
- 右栏检查器改为底部上拉 Sheet

**结构性原则**：

1. **栏位折叠能力是一期就要建的基础设施**（每个栏可独立显隐 + 状态持久化），响应式只是这套能力在不同视口下的默认值变化——不要为响应式单独写一套布局逻辑。
2. **主区优先**：任何断点下被牺牲的永远是导航和检查器，编辑器/内容视图永远保完整宽度——这符合"笔记应用内容为王"的本质，也意味着窄屏下功能完整性靠命令面板兜底（Cmd+K 在移动端同样可用，这是它必须一期做的另一个理由）。
3. **组件容器化**：所有栏位内容（文件树、检查器 Tab）实现为与容器宽度自适应的独立组件，使"从侧栏挪进抽屉/Sheet"只是换容器，不换实现。

------

## 总结：一张可扩展性的检验清单

布局决策的长期价值可以用四个问题检验，本报告的全部建议均通过：

1. **加模块不动外壳吗？** → Icon Rail 注册表 + 二级栏插槽机制 ✅
2. **加视图不动主区吗？** → 主区是视图容器（文档/列表/看板可扩展）✅
3. **加功能不挤界面吗？** → 命令面板 + 三条全局通道兜底 ✅
4. **窄屏功能不打折吗？** → 栏位折叠基础设施 + 命令面板跨端兜底 ✅

**核心心智**：Notion 证明了"统一内容模型 + 视图可换"的扩展力，Craft 证明了"文档优先、面板克制"的深度，Linear 证明了"命令驱动 + 导航语义化分组"的效率。本项目的最佳组合是：**Craft 的编辑器克制 × Notion 的模块/视图抽象 × Linear 的命令与导航纪律**，以三栏可变外壳为骨架，以命令面板为功能增长的泄压阀。
