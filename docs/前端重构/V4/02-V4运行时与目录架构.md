# V4 React 运行时与目录架构

## 1. 架构目标

1. V4 是独立 React 应用，不在 V3 DOM 内渐进挂载多个 React 岛。
2. V3/V4 迁移期可独立启动、构建、测试和回退。
3. 框架无关业务能力只有一个来源。
4. React 独占页面 DOM；Milkdown 只管理明确的编辑器宿主子树。
5. 切换 V4 时无需修改 API、存储和用户数据。
6. React Aria Components 提供无样式交互语义，Knowra UI 封装层提供稳定 API 与唯一视觉。

│       ├── tsconfig.json

│       ├── vitest.config.ts
│       ├── playwright.config.ts
│       └── src/
│           ├── app/
│           ├── components/         # Knowra 组件；ui/ 封装 React Aria
│           ├── features/
│           ├── hooks/
│           ├── store/
│           ├── editor/
│           ├── styles/
│           ├── test/

`packages/web-core` 只接受无 DOM、无 React、无 CSS 的模块。V3 在迁移某项能力时同步改为从该包导入，防止复制分叉。

## 3. React 应用分层

```text
App bootstrap
├── environment / API origin
├── initial workspace snapshot
├── application store
└── error boundary

Application store
├── workspace slice
├── navigation slice
├── library slice
├── editor slice
├── search slice
├── knowledge slice
├── training slice
└── ui slice

Feature layer
├── components subscribe with selectors
├── feature/page only consumes Knowra components/ui
├── actions call typed use cases/services
└── async outcomes update store explicitly

Adapters
├── API client
├── cache/storage
├── Milkdown
├── clipboard/file download
└── browser measurement

UI foundation
├── React Aria Components: interaction / focus / keyboard / ARIA
├── Knowra components/ui: stable props / composition / test contract
└── CSS Modules + tokens: all product visuals
```

## 4. 状态架构

### 4.1 单 Store + slices

使用一个 Zustand Store，按 slice 组织字段与动作，不创建八个互相引用的全局 Store。建议轮廓：

```ts
type AppStore =
  & WorkspaceSlice
  & NavigationSlice
  & LibrarySlice
  & EditorSlice
  & SearchSlice
  & KnowledgeSlice
  & TrainingSlice
  & UiSlice;
```

组件必须通过 selector 订阅最小状态：

```ts
const selectedNoteId = useAppStore((state) => state.selectedNoteId);
```

禁止在 App 根组件订阅整个 Store 后把全部状态层层传递。

### 4.2 状态类型

| 类型 | 示例 | 位置 |
| --- | --- | --- |
| Server data | notes、folders、tags、annotations | Store normalized data |
| Workspace state | selection、open tabs、filters | Store slices |
| UI state | menu/dialog/sidebar open | UI slice 或局部组件 state |
| Ephemeral DOM state | hover、测量、ref | 组件/hook，不进 Store |
| Editor engine state | ProseMirror selection/history | Milkdown 内部，不镜像到 Store |

菜单是否打开可根据跨组件需求决定放局部 state 或 UI slice；不得把所有 hover/focus 都塞进全局 Store。

### 4.3 异步动作

Store action 或 feature use case 应显式表达：

```text
idle → loading/pending → success | error
```

保存、删除、导入、附件上传等动作继续尊重 write guard 和失败保护。React optimistic UI 只能用于已有明确回滚语义的操作。

## 5. 数据与服务

### 5.1 API

V4 继续调用相对 `/api/*`。开发时由 Vite proxy 指向现有 API 端口；生产由现有反向代理或统一 Web 服务托管构建产物。

`api-client` 与 `knowledge-api/*` 优先迁入 `packages/web-core` 并 TypeScript 化。成功/失败信封保持不变。

### 5.2 初始加载

第一版 V4 不需要复制 V3 的自定义 HTML SSR。建议：

1. Vite 输出静态 app shell；
2. React 启动读取 cache；
3. 并行请求 live API；
4. API 不可用时使用 cache，再使用明确 mock fallback；
5. 若首屏性能需要，后续可由宿主在 `window.__STUDY_INITIAL_WORKSPACE__` 注入相同 snapshot，但不引入 React SSR 框架。

是否保留服务端 snapshot 注入在 V4-03 状态基线中用真实启动性能决定，不能因此引入 Next.js。

### 5.3 Cache

保留现有 cache key 和 snapshot schema，除非另有迁移决策。V3/V4 迁移期必须能够读取同一份兼容数据；如写入字段扩展，只能 additive 且 V3 可忽略。

feature 私有组件留在 feature 内；只有确实跨两个以上 feature 复用的组件才进入全局 `components/`。业务层只能从 `components/ui` 或 `components/composed` 使用公共组件；不得直接 import `react-aria-components`。

### 6.1 React Aria 封装规则

- `components/ui` 的公开 props 使用 Knowra 语义，不直接复制第三方全部 props。
- 通过 composition 保留必要的 `ref`、事件和无障碍扩展能力，避免封装成不可组合黑盒。
- 组件状态优先使用 React Aria 提供的 render props 与 `data-*`，再映射为 CSS Module 样式。
- Dialog、Popover、Menu、Tooltip 等 overlay 统一由 React Aria 管理 focus containment、Escape 和焦点归还。
- Tree、GridList、Table、Tabs 等集合组件使用稳定实体 ID，不以 DOM/class 反查业务对象。
- 版本升级先在 `components/ui` 的契约测试与组件展台验证，再进入 feature。
- 若 React Aria 无法满足某一业务控件，先记录缺口；不得临时混入第二套完整 UI 库。

## 7. 样式架构

- `tokens.css`：全局语义 Token 唯一来源。
- `reset.css`：最小浏览器归一化。
- `global.css`：body、root、基础排版与可访问辅助类。
- `*.module.css`：组件和 feature 样式。
- Milkdown/ProseMirror vendor CSS：作为明确 vendor 入口导入。
- 编辑器 skin：V4 自有 CSS Module/global editor layer，不导入 V3 自定义样式。

禁止：

- 导入 `apps/web/styles/**` 或 `apps/web/app/globals.css`。
- 复制 `knowra-*`、`ink-*` 兼容 Token。
- 用大范围 `:global` 重建旧 CSS。
- 使用 `!important` 掩盖所有权冲突。
- 在 React 代码中用视觉 class 查询行为节点。

CSS Module class 只用于视觉；状态使用组件 props、ARIA 或受控 `data-state`。
React Aria 自带的默认 class 名不得成为 Knowra 业务契约；封装层显式提供自己的 CSS Module class，并可使用库暴露的状态 `data-*` 完成视觉状态映射。

## 8. Milkdown React 边界

### 8.1 所有权

```text
React
└── <MilkdownEditor noteId markdown onChange ...>
    └── <div ref={hostRef}>             React 只管理宿主
        └── ProseMirror/Milkdown DOM     adapter/engine 管理
```

React hook 在 mount/note identity 变化时创建 adapter，在 cleanup 时销毁。必须处理异步 create/destroy 竞态和 Strict Mode 开发期 effect 重放。

### 8.2 Typed adapter

适配器至少提供：

```ts
interface EditorAdapter {
  ready: Promise<void>;
  setMarkdown(markdown: string): Promise<void>;
  getMarkdown(): Promise<string>;
  run(command: EditorCommand, options?: unknown): Promise<boolean>;
  focus(): Promise<void>;
  findAndSelectNext(query: string, previousIndex: number): Promise<FindResult>;
  setAnnotations(items: Annotation[]): Promise<void>;
  destroy(): Promise<void>;
}
```

现有 `MilkdownHost` 是重要输入，但需拆分：命令/插件能力复用，`document.getElementById`、全局 render 回调、V3 sidebar/status 调用不进入 adapter。

### 8.3 防循环更新

adapter 发出的 Markdown 变更带来源/identity；React 外部 `setMarkdown` 不得再次触发空白或同值保存。继续保留当前 noteId + markdown identity 与 mount token 思路，用 React ref/AbortController 或 generation token 实现。

## 9. 测试架构

| 层 | 工具 | 目标 |
| --- | --- | --- |
| web-core | Vitest/node tests | 纯函数、API、状态转换、校验 |
| Store | Vitest | slice actions、异步结果、失败保护 |
| Components | React Testing Library | 用户行为、ARIA、焦点、状态 |
| Editor adapter | Vitest + DOM environment | mount/destroy、identity、命令桥 |
| E2E | Playwright | 关键路径、真实浏览器、视口、IME 可替代路径 |
| V3 baseline | 现有 runner | 迁移期防止回退应用损坏 |

不再用读取 CSS 文本和正则匹配 JSX 作为主要 V4 质量证明。静态 import 隔离测试可以保留，但页面行为以 RTL/E2E 为准。

`components/ui` 需要额外覆盖：受控/非受控状态、键盘导航、Escape、overlay 焦点归还、禁用态、集合稳定 key、中文 accessible name，以及自定义 class 不破坏 React Aria 语义。

## 10. 开发与生产集成

### 开发

- `npm run dev:api`：现有 API。
- `npm run dev:web`：当前 V4 Vite React app，proxy `/api`。
- `npm run dev:web:v4`：V4 显式别名。
- `npm run dev:web:legacy`：仅在回归比较或紧急回退时启动 V3。
- 可选 `npm run dev:all:v4`：API + V4。

### 生产切换前

V3 与 V4 构建产物完全独立。V4 不通过 query 参数在 V3 服务中切换，也不在同一个 HTML 中隐藏一套 DOM。重构完成后 V4 已接管默认开发与生产入口，V3 仅保留显式 legacy 命令。

### 最终切换

V4-09 将生产 Web 入口指向 V4 `dist/`，保留一个 Git 回退点；随后删除 V3 workspace 或移入明确归档，不保留永久 generation 设置。

## 11. 工程门禁

1. `apps/web-v4` TypeScript strict 通过。
2. V4 依赖图不导入 V3 `src/controllers`、`lib/events`、renderer 或 CSS。
3. `packages/web-core` 不依赖 DOM、React、CSS 和 app workspace。
4. V4 React 源码禁止 `dangerouslySetInnerHTML`，Markdown 安全预览适配点除外且必须经 DOMPurify。
5. React 源码禁止无登记的 `innerHTML`、`document.querySelector` 和全局事件监听。
6. Milkdown adapter 的命令式 DOM 访问限定在 `src/editor/` 与共享 editor engine 白名单。
7. Store selector 与异步动作有测试；组件不直接突变 Store 对象。
8. V3 `V4-01-01` class 查询门禁迁移期继续通过。
9. V4 CSS/asset import 图不包含 V3 资源。
10. `react-aria-components` 的直接 import 仅允许出现在 `src/components/ui/` 与登记白名单，page/feature 违规即失败。
11. 不依赖 React Aria 默认 class、内部 DOM 层级或未公开实现细节。
12. 全仓测试、V4 unit/component/E2E 与 `git diff --check` 通过。

## 12. 回退与数据安全

- V3/V4 使用同一 API 和兼容 cache schema。
- destructive-path 使用隔离测试数据。
- 迁移不写数据库 migration。
- V4 切换失败通过回退 Web 构建/提交恢复，不恢复用户数据。
- 切换前对正式存储执行现有 export/完整性检查，切换后验证读写闭环。
