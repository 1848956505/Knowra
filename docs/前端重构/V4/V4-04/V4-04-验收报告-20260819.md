# V4-04 验收报告：Token 与基础组件

- 验收日期：2026-08-19
- 验收对象：`apps/web-v4` 的 V4-04 未提交实现
- 对照基线：`04-分阶段实施任务书.md` §8、`V4-00.5-印格视觉冻结规范.md`
- 验收结论：**不通过，需修复后复验；暂不领取 V4-05。**

## 1. 总体判断

V4-04 已完成较完整的组件库骨架，Token、React Aria 封装边界、类型检查、单元测试、构建和既有 Chromium 测试均能通过；桌面视觉也基本延续“印格”冻结方向。

但真实浏览器复验确认两项阻断问题：

1. Dialog 对外 API 没有提供关闭动作，展台中的“取消”按钮点击后 Dialog 仍保持打开。
2. 390px 下 GridList 仍压缩桌面四列表格并产生组件内部横向滚动，没有执行冻结规范要求的两行移动列表重排。

此外还存在空搜索清除按钮常驻、组件展台无条件请求工作区 API 并产生 502、缺少真正的 Playwright 截图基线、移动端展台头部拥挤及部分视觉签名绕开 Token 等 P1 问题。因此执行报告中的“准出门禁通过”结论目前不成立。

## 3. 阻断问题

### P0-1：Dialog 的“取消”操作无法关闭

证据：[`03-Dialog-打开.png`](验收证据-20260819/03-Dialog-打开.png)。

- `Dialog.tsx` 在内部取得 React Aria 的 `close()`，但只用于右上角关闭按钮，没有通过 `DialogFooter`、Context 或专用 `DialogClose` 暴露给调用方。
- 展台的 Dialog footer 使用普通 `<Button variant="ghost">取消</Button>`；真实 Chromium 点击后 `DIALOG_CANCEL_VISIBLE=true`。
- 这会使 V4-05/V4-06 的表单只能依赖右上角关闭或 Escape，业务无法通过语义化按钮完成取消。

准出要求：提供统一 `DialogClose` / `CloseButton`，或通过受控 `isOpen/onOpenChange` 明确关闭契约；展台与测试必须证明取消、确认、右上角、Escape 都按预期关闭并归还焦点。

### P0-2：390px GridList 没有执行冻结的移动列表契约

证据：[`07-展台手机-集合组件.png`](验收证据-20260819/07-展台手机-集合组件.png)、[`08-手机-GridList.png`](验收证据-20260819/08-手机-GridList.png)。

- 390px 实测：GridList `clientWidth=302`、`scrollWidth=326`，存在组件内部横向滚动。
- 状态列被压成纵向窄条，位置列截断，更新时间不可见。
- `Collection.module.css` 对 `.gridRow` 始终使用桌面 `gridTemplateColumns`，`.gridCell` 还固定 `white-space: nowrap`。
- 冻结规范 §5 明确要求 ≤767px 不得压缩桌面表格，必须改为两行紧凑列表，标题最多两行，第二行展示状态、位置与时间。

准出要求：为 GridList 提供明确的移动模式/响应式 row renderer；390px 不得横向滚动、逐字断行或隐藏关键列，且必须增加组件内部溢出断言，而非只检查 `documentElement.scrollWidth`。

## 4. 其他重要问题

### P1-1：空 SearchField 仍显示“清除搜索”按钮

证据：[`01-展台桌面-顶区.png`](验收证据-20260819/01-展台桌面-顶区.png)、[`02-输入与浮层组件.png`](验收证据-20260819/02-输入与浮层组件.png)。

`SearchField` 只要传入 `onClear` 就始终渲染清除按钮；空值实测 `EMPTY_SEARCH_CLEAR_VISIBLE=true`。这与组件注释及冻结契约“输入非空时显示清除”不一致，也增加了无效键盘停靠点。

### P1-2：组件展台无条件加载工作区 API

访问 `/#/showcase` 时，`App.tsx` 的顶层 effect 仍调用 `loadWorkspace()`。独立组件展台并不使用工作区数据，却在未启动 API 时产生：

```text
502 http://127.0.0.1:5173/api/knowledge/spaces
Failed to load resource: the server responded with a status of 502
```

桌面与移动重新加载各出现一次。展台应能独立、无控制台错误地运行；应把加载逻辑限制到工作区路由，或拆分 route-level 容器。

### P1-3：所谓“Playwright 视觉基线”实际没有视觉快照

- `e2e/component-showcase.spec.ts` 明确写着“所有断言都是结构性的，不依赖像素级截图”。
- `apps/web-v4` 内没有 snapshot 目录或基线图片，也没有 `toHaveScreenshot()`。
- 当前测试能证明部分行为，但不能防止 Token、间距、阴影、响应式布局发生视觉回退。

准出要求：补充稳定的桌面、390px、Dialog、Menu、集合组件视觉快照，并将动态内容、动画和字体差异做确定性处理。

### P1-4：390px 展台头部缺少响应式布局

证据：[`06-展台手机-顶区.png`](验收证据-20260819/06-展台手机-顶区.png)。

- Hero 仍强制横向 `display:flex; justify-content:space-between`，冻结状态 Badge 被压成多行并侵入说明文字区域。
- 顶部导航中的中文链接和当前路径被压成多行，扫描性与触控清晰度不足。

应在 ≤767px 将 Hero 改为纵向排列，并为应用头部提供可预测的折行或移动导航策略。

### P1-5：部分视觉签名没有通过 Canonical Token

冻结规范 §8.1/§8.2 要求颜色、字号、硬阴影等视觉签名由 Token 管理且不得新增设计语言。当前 CSS Modules 仍包含：

- `box-shadow: 1px 1px 0 var(--ink)`；
- `box-shadow: 3px 3px 0 var(--ink-danger)`；
- `box-shadow: 2px 2px 0 var(--badge-shadow, var(--ink))`；
- `background: rgba(26, 26, 26, 0.32)` 与 `rgba(249, 247, 242, 0.7)`。

这些值有些源于原型，但不在当前 Canonical Token 列表中，与执行报告“视觉签名一律引用 `var(--…)`”的描述不一致。若确属正式设计值，应先补充/勘误冻结 Token；否则应统一复用现有 Token。

### P1-6：GridList 的可访问表格语义不足

当前无障碍树显示可见表头只是普通 generic 节点，每一行的多列内容被合并在单一 `gridcell` 中。读屏用户不能获得明确的列标题、行列坐标关系。若它用于资料多列表格，应提供 Table/Grid 语义；若定位为可选择 GridList，应避免展示会被误认为完整表格语义的列头。

## 5. 已确认的优点

1. 18 个颜色 Token、字体、阴影、外壳尺寸和动效值与冻结规范主体一致。
2. `components/ui` 单一出口和 React Aria import 边界有效，未发现 V3 样式导入。
3. Button、Input、Select、Tabs、Menu、Dialog、Tree、GridList、TagGroup、状态组件的基本接口和桌面视觉覆盖较完整。
4. Dialog 的首焦点、焦点陷阱、Escape 和焦点归还通过既有 Chromium 测试及本轮复验。
5. Menu 的展开、方向键、Escape 和焦点归还通过测试；桌面浮层视觉与“印格”方向一致。
6. 页面级 390px 没有整体横向溢出，reduced-motion 与 200% zoom 的既有门禁通过。
